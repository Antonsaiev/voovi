# voovi

Основной репозиторий-обвязка для локального и production-запуска связки:

- `voovi.ru` - legacy PHP-приложение;
- `s.voovi.ru-api` - Django API;
- `analitic` - Django аналитика;
- `db` - MariaDB/MySQL-compatible база.

Код приложений подключен как git submodules.

## Первый запуск

```bash
git submodule update --init --recursive
./dev.sh restore-db  # только для первой загрузки исходного дампа
./dev.sh
```

`./dev.sh` и `./dev.sh start` сохраняют базу и запускают приложения без изменения её схемы.
Обычный `docker compose --env-file configs/env/local.env up -d` также сохраняет базу: сервис восстановления вынесен в профиль `tools` и не входит в зависимости приложений.
Только явная команда `./dev.sh restore-db` удаляет локальную базу `MYSQL_DATABASE` и загружает актуальный `voovi.sql`. Бэкап она не создаёт. Старый дамп автоматически не обновляется.

Адреса с текущими настройками `configs/env/local.env`:

- `voovi.ru` через nginx: http://voovi.localhost:8088
- `s.voovi.ru-api` через nginx: http://s.voovi.localhost:8088
- `analitic` через nginx: http://analitic.voovi.localhost:8088
- `voovi.ru` напрямую: http://localhost:8080
- `s.voovi.ru-api` напрямую: http://localhost:7005
- `analitic` напрямую: http://localhost:7001
- phpMyAdmin: http://localhost:8081
- MySQL на host-машине: `127.0.0.1:3308`

Домены `*.localhost` обычно резолвятся в `127.0.0.1` без правки `/etc/hosts`. Если в вашем окружении это не работает, добавьте `voovi.localhost`, `s.voovi.localhost` и `analitic.voovi.localhost` в hosts-файл.

Для общей PHP-авторизации локально заходите через nginx-домены `*.voovi.localhost`, а не через прямые `localhost`-порты. Cookie авторизации ставится на домен `voovi.localhost` и отправляется браузером также на `s.voovi.localhost`.

## Локальная разработка

```bash
./dev.sh             # build + старт, без удаления базы и изменения схемы
./dev.sh start       # то же самое
./dev.sh restore-db  # только полный restore базы из voovi.sql
./dev.sh logs        # логи всех сервисов
./dev.sh down        # удалить контейнеры и сеть, volume с БД оставить
```

Env-файлы лежат в `configs/env/`: `local.env` для локальной разработки и `prod.env` для production. Настройки API и аналитики читаются из этих файлов: адреса, токены, пароли, идентификаторы и переключатели.
Списки и словари хранятся в Python: `s.voovi.ru-api/settings_project/reference_data.py` и `analitic/utils/setting_info.py`.
Рабочие YAML-конфиги приложений удалены; PyYAML для них не требуется. Docker Compose и платформенные манифесты сохраняют свой штатный формат YAML.
После изменения env контейнеры нужно пересоздать через `docker compose --env-file configs/env/local.env up -d --no-deps svoovi-api analitic svoovi-api-tasks`.
 `voovi.sql` не хранится в git. Файл должен лежать в корне репозитория рядом с `docker-compose.yml`.

Текущий процесс выставления и присоединения счетов Контура, код, настройки и ограничения описаны в [интеграции Контура](docs/KONTUR_INTEGRATION.md). Счета используют [единое хранилище `bills*`](docs/KONTUR_UNIFIED_STORAGE_2026-10-26.md). Одноразовое обновление unmanaged-таблиц завершено; его скрипты удалены. Проверки описаны в [матрице тестирования](docs/KONTUR_PRODUCT_TEST_MATRIX_2026-10-25.md).

Датированные исследования интерфейса, API и модернизации в `docs/` сохранены как исходные материалы; они не заменяют текущие инструкции.

## Production

Первое обновление накопленных изменений выполнено 31 октября по [плану перехода](docs/PRODUCTION_RELEASE_PLAN_2026-10-31.md); результат и проверки — в [протоколе выкладки](docs/PRODUCTION_RELEASE_2026-10-31.md). Обновлён только `/root/docker/voovi`, домены `voovi.voovi.ru` и `analitic.voovi.ru`. Старые `voovi.ru` и `s.voovi.ru` сохранили web-код и маршруты. `apisvoovi_tasks` остановлен и исключён из обычного автозапуска; общую очередь обслуживает один обновлённый worker Docker-проекта. Восемь заменяемых внешних cron отключены. Первый cursor инициализирован значением `639290572440863787`; при последующих обновлениях текущее состояние в общих томах сохраняется.

Перед запуском production проверьте настройки целевого окружения в `configs/env/prod.env`, затем:

```bash
./deploy.sh
```

Production-compose использует уже существующий MySQL из `SQL_HOST`/`SQL_DATABASE`; базу, nginx и phpMyAdmin он не поднимает и дамп не импортирует.
Внешний reverse proxy завершает HTTPS и направляет домены на локальные порты: сайт — `127.0.0.1:18080`, API — `127.0.0.1:18001`, аналитика — `127.0.0.1:18002`. Он должен передавать исходный `Host` и `X-Forwarded-Proto`.

### Внешние скрипты Контура в Django

Перенесённые задачи, настройки и порядок замены cron: [инструкция](s.voovi.ru-api/basic/kontur_automation/README.md). Задачи выполняет общий сервис `svoovi-api-tasks`; расписание Контура явно устанавливается командой `kontur_schedule` и сохраняется в БД. Открытие сайта его не устанавливает, а перезапуск worker не сбрасывает существующее расписание и курсор. Перед включением нового расписания старые внешние cron-задачи нужно отключить.

Просмотр без выполнения задачи: `docker exec apisvoovi python manage.py kontur_automation schetmain`. Просмотр установленного/предлагаемого расписания без изменений: `docker exec apisvoovi python manage.py kontur_schedule`. Эти команды без `--execute` не меняют данные и не отправляют уведомления.

При старте того же worker регистрируются сверки по Москве: складские статусы ежедневно в **03:30**, реквизиты АВ ежедневно в **04:25**, проверка счетов **1-го и 15-го числа в 02:00**, начисление ЗП за предыдущий месяц **10-го числа в 20:00**, справочник продуктов Контура ежедневно в **05:30**. Существующие записи расписания сохраняются, повторный запуск не создаёт дубли. После обновления кода достаточно перезапустить `svoovi-api-tasks`; отдельных сервисов, cron и изменений схемы БД не требуется. Подробности переноса скриптов ЗП и годовой разбивки: [инструкция](docs/WAGE_AUTOMATION.md).

Складская сверка обрабатывает счета поставщиков всех действующих направлений. Ручная кнопка использует ту же функцию. Записывается только изменившийся статус; ошибка одного счёта фиксируется в журнале и не прерывает остальные. Ночная задача отправляет уведомление в VK только при изменениях или ошибках; ручной запуск также сообщает, когда все статусы актуальны.
