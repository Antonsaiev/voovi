# Банковские выписки и автоматическое разнесение Савоира

Банковская авторизация, Selenium, скачивание и получение файлов из `dockerbank`
остаются на сервере. Django обрабатывает только уже полученные TXT-выписки 1С.
Используется существующий `svoovi-api-tasks`, отдельного worker или cron не добавлено.
Связи и состояние счетов Контура при банковском разнесении не запрашиваются.

## Файлы и расписание

Задача `basic.tasks.task_import_bank_statements` выполняется каждые пять минут,
если `BANK_AUTOMATION_ENABLED=1`. Расписание регистрируется при старте общего worker,
не дублируется и не изменяет прежние задачи. Банковская блокировка работает на
отдельном соединении, включая MariaDB 5.5; блокировки Контура и ЗП не затрагиваются.

После загрузки через «Работу с оплатами» аналитика сразу вызывает авторизованный
`POST /api/v1/payment/bank-import`. Он ставит одноразовый запуск прежней задачи с
`uploads_only=True`, без ожидания очередного пятиминутного интервала. Такой запуск
обрабатывает только папку ручных загрузок. Работающий импорт не прерывается:
новый файл получает ожидающий запуск следом; одновременные запросы объединяют
один ожидающий запуск. Очередь защищена собственной короткой блокировкой на отдельном
соединении, текущая финансовая блокировка и регулярное расписание не изменяются.
После достижения квоты большого файла продолжение ставится автоматически при
фактическом прогрессе. Неизменившиеся недописанные файлы и временные ошибки БД
не вызывают бесконечного частого опроса.

| Вход | Production host | Worker |
|---|---|---|
| Полученные из банка | `/root/selenium-compose/files/Downloads` | `/usr/src/app/var/banking/incoming` |
| Подготовленные прежним конвертером | `/root/selenium-compose/files/file_for_process` | `/usr/src/app/var/banking/prepared` |
| Ручная загрузка аналитики | `/root/docker/voovi/analitic/uploads/payments` | `/usr/src/app/var/banking/uploads` |
| Загрузка прежней аналитики | `/root/analitic/uploads/payments` | `/usr/src/app/var/banking/legacy_uploads` |

Локально первые две папки — `var/bank/Downloads` и `var/bank/file_for_process`.
Ручная загрузка использует прежнюю папку аналитики; дополнительное копирование не нужно.
Архив, задания чеков и история находятся в постоянном Docker volume `voovi_banking`.
Входные папки и пути состояния заданы параметрами `BANK_*` в ENV.
Необязательная `BANK_LEGACY_UPLOADS_DIR` сохраняет работу прежней формы загрузки:
TXT читаются как внешние исходники с сохранением байтов и inode. Одноразовая
задача `uploads_only` по-прежнему обрабатывает только новую форму; старые загрузки
попадают в общий пятиминутный запуск.

Worker ждёт стабильного размера/времени изменения TXT и проверяет завершённость
структуры 1С. Для серверного файла создаётся ограниченный по размеру неизменяемый
снимок в соседней `.bank-processing`: исходный inode не переименовывается и не
удаляется, поэтому производитель может продолжать запись без потери выписки.
`.bank-seen.json` хранит активный снимок и подпись/хеш обработанной версии;
неизменный исходник повторно не обрабатывается, изменённая версия проверяется заново.
Повреждённый формат копируется в ручной архив с сохранением оригинала.
Недописанный захваченный файл остаётся для продолжения, а не удаляется как ошибка.

Ручная форма сначала сохраняет файл под временным именем `.uploading`, закрывает
и синхронизирует его, затем атомарно публикует `UUID.ready.txt`. Только для этих
файлов в `BANK_UPLOADS_DIR` ожидание стабильности не требуется; полная проверка
структуры 1С остаётся. Старые обычные TXT и банковские папки сохраняют прежнее
ожидание. Права `B`/`D` проверяются до записи. Если немедленная постановка недоступна,
исходник сохраняется, интерфейс сообщает об этом без требования повторной загрузки;
при включённой автоматике его подхватит регулярная задача.

Входные папки чередуются, курсор сохраняется. Длинная банковская выгрузка не
вытесняет ручные загрузки. Обработка ограничена числом файлов, документов и
`BANK_MAX_SECONDS=30`: время проверяется между финансовыми операциями, без
прерывания начатой транзакции. Одиночный SQL может занять больше этого времени.
Checkpoint позволяет продолжить файл после прерывания. Разбор поддерживает UTF-8,
Windows-1251 и DOS-866; оригинальные байты не изменяются. В результатах сохраняется
исходный номер документа, включая пропущенные ошибочные документы.

**Корректная выписка без документов допустима.** Она архивируется с нулевым
результатом; количество строк не используется как признак отсутствия платежей.

Оригинал и краткий результат сохраняются в
`BANK_ARCHIVE_DIR/{completed|manual}/ГГГГ-ММ-ДД/<uuid>/`. Повреждённые файлы и документы
не удаляются. Если даже дата или сумма не читаются, фиктивная платёжка не создаётся:
оператору остаётся исходник в ручном архиве и причина в журнале.

## Согласованные правила

- Автоматически распределяется полный платёж при совпадении суммы найденных счетов.
- При нескольких равных кандидатах сохраняется выбор первого в прежнем порядке.
- При явно указанном номере ИНН плательщика не становится дополнительным запретом.
- Организация получателя проверяется по ИНН, без новой проверки расчётного счёта.
- Любое существующее движение `kvobop` по входящему счёту оставляет платёж для ручного разнесения.
- Автоотгрузка определяется настройками первой позиции, как в прежнем скрипте.
- Прежнее условие жёлтой отметки оплаты по заполненности номера/суммы поставщика сохранено.
- Собственные внесения наличных пропускаются; обычные исходящие операции импортируются без разнесения.
- Правила сумм полного и частичного ручного разноса, ЗП и прежние наличные операции сохранены. Подготовка чека ручного безнала теперь использует те же сохранённые цены, что и банковская задача.
- Ошибки и неопознанные платежи остаются для ручной обработки; писем и VK-уведомлений эта задача не отправляет.

Исходящий возврат определяется по направлению и назначению. Автоматическая отметка
в `kvobop` создаётся **только при точном равенстве суммы возврата полной сумме
однозначно найденного неотгруженного счёта**. Без номера однозначность определяется
по клиенту, организации и равной сумме; два равных кандидата остаются ручными.
Прежний возврат по этому счёту также означает ручную проверку.

Если автоматический подбор не сработал, менеджер открывает возврат из списка
неопознанных платежей, выбирает один счёт и нажимает «Указать счёт возврата».
В списке операции различаются как «Оплата» и «Возврат»; у возврата показан клиент-
получатель и дата списания. Частичная сумма для возврата недоступна.
Список показывает последние 12 календарных месяцев до текущей даты включительно;
для оплаты используется дата поступления, для возврата — списания с резервной
датой документа. Возврат выделен бордовым в списке, заголовке, кнопке и результате.
Сервер заново проверяет направление, клиента, организацию, полную сумму и отгрузку;
при сомнении запись не создаётся. Обычные расходы и собственные внесения наличных
не могут превратиться во входящую оплату. Тип 5 старого импорта считается возвратом;
для типов 2/3 требуется слово «Возврат» в назначении.

Ручная операция использует авторизованный `POST /api/v1/payment/bank-refund`
и тот же банковский сервис, блокировку и сохранённое задание чеков, что импорт.
API и worker разделяют `voovi_banking` volume. Повтор того же выбора не создаёт
вторую KVO или чек; другое уже выполненное распределение не переписывается.
Если возврат сохранён, но публикация чека не завершена, результат прямо сообщает
о сохранённом возврате и необходимости проверки чека, даже при сбое записи
дополнительного ручного статуса. Входящая форма сохраняет прежние правила сумм.

Детального пересчёта поступлений, отрицательных корректировок и доступного остатка
нет. Частичная/большая сумма, неизвестный состав чека и другие сомнения не создают
движение и не меняют отметки счёта. Отказной клон не создаётся. Сумма банковской
операции сохраняется положительной, движение полного возврата — отрицательным.

## Повторы и прерывания

Финализация банковской задачи отделена от финансовой обработки. Запись завершения,
следующий повтор и удаление прежней задачи защищены короткой транзакцией; для
старых MyISAM-таблиц успешная попытка распознаётся по сохранённому захвату.
Восстановление завершает её финализацию без повторного исполнения тела и создания
второй постоянной цепочки. Одноразовые загрузки остаются отдельными задачами
с `repeat=0`. Платежи не удерживаются одной длинной транзакцией до конца файла.

`payment` сохраняется отдельно от разнесения. Идентичность банковской операции
учитывает документ, дату, номер, сумму и счета обеих сторон. Для прежних импортов
учитываются оба варианта `Счет`/`РасчСчет`, сохраняются исходные ID и `random_key`.
Неоднозначные исторические строки не приводят к созданию очередной платёжки.
Если у единственной найденной старой платёжки ключ пустой, ей присваивается
стабильный банковский ключ и ручной статус; автоматически она не распределяется.

Статусы новой обработки в существующем `payment.status`: `0` — импортировано,
`1` — закончено, `2` — ручная обработка, `3` — финансовая запись завершена,
осталась постановка подготовленных чеков. Платёж со статусом ручной обработки
автоматически снова не распределяется.

Технический сбой до сохранения `payment` или ручного статуса возвращает `retry`:
документ остаётся на прежней позиции файла до надёжного сохранения. Это повтор
импорта, а не повторное автоматическое разнесение спорного платежа.

Постоянные ошибки формата данных SQL не повторяются бесконечно: исходник и причина
остаются в ручном архиве, следующие документы выписки продолжают обрабатываться.
Если платёжку невозможно сохранить точно, фиктивная запись не создаётся.
Трёхбайтная `utf8` старой БД не поддерживает, например, эмодзи: в описаниях такие
символы явно заменяются на `?`, а платёж сразу становится ручным. Идентификаторы,
счета и суммы не подменяются; полные исходные байты сохраняются в архиве.
Слишком длинные идентификаторы и банковские реквизиты также остаются ручными,
без молчаливой обрезки. Проверка использует ограничения существующей модели;
их совпадение с фактическими колонками локальной `payment` подтверждено отдельно.
Временная недоступность БД, deadlock или неизвестная ошибка схемы по-прежнему
оставляют документ для повтора, не продвигая checkpoint.

Разнесение блокирует исходную платёжку, затем позиции счетов в порядке ID.
Ошибка до фиксации откатывает все движения текущего разнесения, сохраняя саму
платёжку. Повторная выписка не должна повторно создавать оплату или возврат.
Эти блокировки согласованы с ручным разносом Django. Прежние PHP-формы прямого
ввода движений не используют этот протокол; их одновременная запись без связи
с банковской платёжкой не получает такой же гарантии. Ручные PHP-правила здесь
не переписываются.

`chec` остаётся MyISAM. До финансового коммита сохраняется неизменяемое задание
чеков в постоянном volume; после коммита строки готовятся с `isset=2` и публикуются
через `isset=0` после подготовки полного состава. При неоднозначном прерывании
публикации повторная фискальная отправка не выполняется автоматически: требуется
ручная проверка. Это не подтверждение фактической фискализации кассовым агентом.

Перед подготовкой возвратного чека физлицу проверяется незавершённый прежний
чек того же счёта (`isset=0/2` или связанный платёж `status=3`). В таком случае
возврат остаётся ручным, новые KVO и задание чека не создаются. При публикации
число изменённых строк должно совпасть с подготовленным составом; несовпадение
фиксируется в outbox как `publish_error`, после чего повтор не объявляет чек
опубликованным и не отправляет его повторно.

Эта защита относится к общему банковскому механизму. Доступные старые исходники
AgentKKT подтверждают весь `rand`; для полной защиты от параллельных независимых
писателей агент должен подтверждать только выбранные им ID. Его установленная
сборка и настоящая фискализация в локальных проверках не запускались.

После аварии worker проверяет старый захват именно банковской задачи: захват
старше минуты снимается только при свободной банковской advisory-блокировке.
Проверка выполняется не чаще раза в 30 секунд. Активный банковский запуск держит
блокировку до окончания финализации записи очереди. Общий часовой таймаут ЗП,
Контура и остальных задач не изменяется. При выключенном банке восстановление
не открывает дополнительного соединения; timeout его отдельного соединения — 5 секунд.
Ошибка получения блокировки или записи отсрочки остаётся в банковском журнале
и не завершает общий worker. Занятость откладывает ту же задачу на 10 секунд,
без создания второй цепочки расписания.

## Стоимость чека

При выставлении и замене состава в существующем `schet.summa` сохраняется короткий
JSON-снимок стоимости строки: версия, тариф, количество, скидка, итог строки и
выезд первой позиции. Новых таблиц/полей и изменений схемы для этого не требуется.

Снимок v1 совместим с прежними строками; optional `b`/`r` хранят неизменяемую
базу тарифа/выезда. При обычном выставлении это точная цена на тот момент,
включая возможность снять исходную скидку 100%. При назначении произвольного
итога новой базой становятся фактически распределённые суммы. Старые v1 без
базы поддерживаются: первая правка закрепляет известную исходную пропорцию,
не используя новый прайс. Неизвестная цена до старой скидки 100% не выдумывается.
Повторные правки количества/скидки считают от этой базы и не накапливают
округление предыдущей редакции. Все снимки проверяются на лимит 200 символов
до записи новых строк.

Чеки, PDF/XML/DOCX, PHP-печать, доли ЗП и экспорт в Бухгалтерию используют
сохранённую построчную стоимость. Выезд включается в базу ЗП по прежнему
согласованному правилу. В Бухгалтерии выезд остаётся включён в тарифную
номенклатуру и распределяется по сохранённым долям; новые sync_id не вводятся.
Если `schet.summa` не содержит JSON-снимок (в том числе пусто, `0` или прежнее
числовое значение), применяется прежний расчёт по прайсу тарифа с количеством
и скидкой. Это правило действует для ЗП, документов, Бухгалтерии и подготовки
чеков при ручном и автоматическом разнесении оплаты. Итог остаётся сохранённым
`schet.price`: тарифные веса согласуются с ним, включая выезд. В смешанном
составе известные суммы JSON остаются неизменными, а остаток итога распределяется
только между строками без снимка по их прайсовым весам. Повреждённый JSON или
противоречащий составу снимок не подменяется прайсом.
Смена менеджера и отказной клон не заменяют сохранённые суммы текущим прайсом.

Цена за единицу в документах остаётся в копейках. Если её произведение на
количество не даёт сохранённую сумму строки после округления до копеек, только
печатная позиция разделяется на части с соседними копеечными ценами. Например,
100 ₽ за 3 единицы — `2 × 33,33 ₽ + 1 × 33,34 ₽`. Это не создание новых тарифов
или строк в БД: исходный состав, количество, сумма, НДС, оплата и база ЗП сохраняются.
Обычные позиции, у которых умножение уже сходится, не делятся. Для документов
с ценой без НДС части рассчитываются по сумме без НДС, а налог распределяется
с сохранением его общего итога; смысл существующих колонок не меняется.
В PHP-счёте и спецификации строка выезда выводится только при её наличии в
рассчитанном составе; нулевое количество и служебная отметка не создают пустую строку.

Новые банковские чеки используют снимок, а для строк без JSON — тот же прежний
расчёт по прайсу. Количество может быть дробным; сумма всех строк, включая выезд,
равна сохранённой сумме счёта. При наличии снимка текущий прайс его не заменяет.

Редактирование суммы, количества, скидки или выезда через API обновляет имеющиеся
снимки до первой записи в БД, на основании сохранённых стоимостей. Смена менеджера
и численно равные значения их не меняют. Старые счета целиком без JSON сохраняют
прежний порядок редактирования, без создания снимков из текущего прайса.
Если имеющийся снимок противоречит составу или для его изменения недостаёт
исторических данных, изменение отклоняется до сохранения. Подписи чека
заранее приводятся к длине старых колонок; кассовые ключи проверяются без обрезания.

Старые одно- и многострочные счета без снимков не блокируются только из-за
отсутствия JSON. Прайсовый расчёт не выдаётся за историческую цену: массового
заполнения старых строк сегодняшними ценами нет.

Ручной безнал Django (`analitic/utils/SqlQuery.py`, `go_to_check`) использует этот же
расчётчик через внутренний авторизованный `POST /api/v1/payment/receipt-prepare`.
Endpoint ничего не записывает и не отправляет кассе: получает уже прочитанный
аналитикой состав со снимками, готовит все строки в памяти и возвращает результат.
Текущий прайс в запрос не передаётся: для старых строк API читает его из справочника
тарифов. Права прежних операторов банка `B` и кассы `D`
сохраняются. Передавать токен в браузер не требуется.

При полном ручном разнесении сначала проверяются все выбранные счета и готовятся
все необходимые чеки, затем выполняются финансовые записи и постановка чеков.
На форме есть компактный Bootstrap-переключатель расширенного режима; текущая платежка
сохраняется, а список счетов и поля частичной оплаты обновляются после перехода.
Ошибка второго состава или недоступность API не оставляет первого чека, движения
или изменённой отметки. Правила полного разноса, частичной оплаты, автоотгрузки и
«Переплаты» сохранены. В прежней MyISAM-очереди остаётся отдельный риск частичной
записи при SQL-сбое/аварии публикации; предварительная подготовка не делает её
полностью транзакционной.

После закрытия счёта несколькими частичными оплатами формируется один чек на полный
сохранённый итог. Строки счёта блокируются на время подготовки; параллельная правка
стоимости ждёт окончания операции. Для старых KVO без банковского ключа используется
только фискальный ключ `manual-receipt:<rand>`, без создания Payment или изменения
KVO. Ошибка подготовки возвращается пользователю в понятном сообщении. Переключение
существующего чека на возврат сохраняет его исходные строки и суммы.

В поиске оплат показываются все движения `kvobop`, включая записи без ключа
или исходной платёжки. Такие движения не исчезают из итога; возвраты вычитаются.
Ошибки поиска выводятся текстом, незавершённый предыдущий запрос отменяется.
Переключение чека требует права `B`, явно выбранного действия и показанного
состояния строк. Чеки с `isset=0` ожидают кассу, `isset=2` ещё готовятся банком,
`isset=1` обработаны агентом. Незавершённая банковская подготовка и ручная проверка
источника запрещают переключение; дата `dt_isset` не считается доказательством
фискализации. Повтор запроса после изменения состояния получает 409 и обновляет
поиск вместо противоположного действия. Банк и переключение используют общую
блокировку, отдельное соединение сохраняет её поведение на MariaDB 5.5.

Состав `AllInfoSchet` упорядочен по `schet.id`, чтобы снимок выезда всегда находился
в первой позиции. Старые PHP-формы и отдельный наличный путь `workWcash` не меняются.
При обновлении сначала устанавливается API с подготовщиком, затем аналитика;
новых таблиц, сервисов и изменений Docker для ручных чеков не требуется.

## Просмотр распределений

В расширенном режиме страницы банковской платежки под её реквизитами показаны
сохранённые распределения из `kvobop`: номер из `schet.ns`, организация, тип и сумма
конкретного движения. Для старой записи без найденного счёта используется сохранённый
`kvobop.nschet`; неоднозначные старые связи помечаются для проверки. Состав счёта
не дублирует строки оплаты. Данные загружаются семью пакетными запросами.

У каждой привязки можно раскрыть другие оплаты и возвраты того же счёта, в том числе
наличные и записи без сохранившегося исходного платежа. Для найденной другой
банковской платежки доступен переход к ней. Общая сумма движений рассчитывается
из сохранённых `kvobop.summa`, с вычетом возвратов, без текущего прайса.

Значок чека означает наличие его строк по счёту, а не подтверждение фискализации.
Чек может объединять несколько частичных платежей, даже если сохранён с ключом
только последней платежки. Блок распределений предназначен только для просмотра.
Нажатие на номер счёта открывает поиск его оплат в новой вкладке с автоматической
подстановкой номера и запуском поиска.

## Отдельная история разнесения

Файлы `BANK_LOG_DIR/ГГГГ-ММ.log` содержат начало обработки, номер/дату банковской
операции, ID платёжки, найденные счета, суммы, записанные движения и результат.
Исключения также остаются здесь. Банковский logger не дублируется в общий журнал.
Пароли и токены из ENV маскируются; исходные выписки в журнал не печатаются.

Хранится текущий месяц и четыре предыдущих. Более старые **месячные журналы**
удаляются автоматически; платежи, возвраты и исходные выписки этим не удаляются.
Срок задаётся `BANK_LOG_RETENTION_MONTHS=4`.

## Проверка и включение

Просмотр настроек без финансовых действий:

```bash
docker compose --env-file configs/env/local.env exec svoovi-api-tasks python manage.py bank_statements
```

Явный локальный запуск той же обработки:

```bash
docker compose --env-file configs/env/local.env exec svoovi-api-tasks python manage.py bank_statements --execute
```

Production-конфигурация подготовлена с `BANK_AUTOMATION_ENABLED=0`.
При отключённом банке отсутствующие входные каталоги не блокируют общий worker.
При включённом банке `deploy.sh` проверяет банковские источники **до** сборки и
замены контейнеров; папка ручных загрузок создаётся заранее.
Перед включением нужно сверить фактические пути серверного копирования и отключить
старые cron конвертации/импорта/разнесения, включая ручное копирование после
проверки всех действующих форм загрузки. Вход в банк, скачивание и получение файлов
из Docker остаются. Старый и новый финансовые обработчики одновременно не работают.
