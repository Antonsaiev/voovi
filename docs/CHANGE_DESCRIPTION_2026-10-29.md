## 1. Что изменилось в архитектуре

Сохранена действующая система: PHP-сайт `voovi.ru`, Django API `s.voovi.ru-api`, Django-аналитика `analitic` и общая MariaDB. Переписывания на React и переноса данных в PostgreSQL в этих изменениях нет. Новая интеграция встроена в текущую систему; старые счета, платежи, АВ, документы и склад продолжают опираться на прежние основные таблицы.

Распределение ответственности стало следующим:

| Часть | Что делает сейчас | Для чего выделена |
| --- | --- | --- |
| PHP-сайт | Создаёт и редактирует счёт Voovi; показывает форму Контура и сохранённый состав | Сохранить существующий пользовательский процесс и связи |
| `basic/kontur` в API | Проверяет доступ, готовит каталог, рассчитывает, создаёт и присоединяет документ Контура | Собрать прикладные правила интеграции в одном месте |
| `utils/api_skb.py` | Выполняет обращения к внешним API | Не размножать HTTP-код, настройки и правила повторов |
| `basic/kontur_automation` | Принимает учётные новости, дополняет документы, обновляет оплаты и запускает вторичные действия | Перенести предоставленные внешние скрипты в управляемое приложение |
| Аналитика | Обрабатывает платежи, кассовые действия, отчёты и агентские начисления | Сохранить прежние функции с более строгим выбором документа и безопасным SQL |
| Шаг подготовки схемы | Проверяет структуру установленной базы перед запуском приложений | Поддержать базы, которые ранее не обновлялись миграциями Django |

Пользовательская цепочка: **сначала сохраняется счёт Voovi → затем создаётся либо присоединяется счёт Контура → состав хранится локально → последующие учётные сведения приходят через новости**.

Документ Контура не принадлежит исключительно одной карточке Voovi. Один `bills.BillId` может быть связан с несколькими `schet.rand`. Поэтому общий состав и общий итог хранятся у документа Контура, а старые суммы отдельных счетов Voovi сохраняют своё значение.

Обычные HTTP-запросы приложения не устанавливают расписание и не обновляют структуру базы. Эти действия вынесены в явные команды развёртывания и обслуживания.

## 2. Постоянный номер и идентичность счёта Voovi

### 2.1. Проблема и новое правило

Ранее часть страниц собирала номер из года, текущего менеджера, отдела и счётчика при показе. После смены менеджера один и тот же счёт мог выглядеть по-разному в карточке, списке, печати и документах. Независимые способы выдачи номера также создавали риск совпадения `rand` и номера у разных счетов.

Теперь номер выдаётся при создании и записывается в **`schet.ns`**. Для новых счетов и проверяемых сохранений все строки состава одного счёта получают одинаковые `ns` и `rand`. Существующие неоднозначные исторические группы автоматически не перенумеровываются. Смена менеджера не должна менять эти значения. Наличие нескольких строк `schet` с одним `ns` само по себе нормально: это позиции одного документа; недопустимо использование номера разными группами `rand`.

Основная реализация — [schet_identity.php](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/voovi.ru/schet_identity.php:24):

- `voovi_schet_stored_number()` проверяет единство номера и клиента в группе, а также отсутствие того же номера у другой активной группы.
- `voovi_allocate_schet_identity()` нормализует год, атомарно увеличивает годовой счётчик и резервирует номер с `rand`.
- `schetnum` имеет уникальный год; увеличение выполняется через `LAST_INSERT_ID(num + 1)`, без блокирования всей таблицы счетов.
- `schet_identity_keys` содержит занятые идентификаторы и поля владельца — группу, номер и клиента; у прежних резервов поля владельца могут оставаться `NULL`. Общий аллокатор не выдаёт повторно занятый ключ; прямые старые писатели этот реестр не соблюдают автоматически.
- При совпадении с уже занятым значением выдача пробует следующий номер. Пропуски после неуспешного создания допустимы; повторное использование резерва — нет.

Внешний формат номера сохранён: год + код менеджера + код отдела + годовой порядковый номер. В обновлённом коде эти части используются **один раз при выдаче**. `rand` формируется отдельно из порядкового значения и даты; общий аллокатор резервирует его в реестре. Без триггеров реестр не защищает от коллизий произвольного прямого SQL старых программ.

### 2.2. Где изменён показ номера

На `ns` переведены списки, поиск, карточки, формы, печать, назначение платежа и ссылки на документы. Основные PHP-файлы: `call.php`, `divoplata.php`, `docpage.php`, `inctoha.php`, `kartklients.php`, `komnete.php`, `leha.php`, `regkartkli.php`, `schet.php`, `schetdataedit.php`, `searchschet.php`, `setschet.php`, `specifik.php`, `toha.php`, `tohha.php`, `tovarnaklad.php`, `uliya.php`, `vika.php`.

Ряд прежних страниц больше не пытается «исправлять» номер записью в базу во время просмотра. Номер договора — отдельная сущность: его прежние формулы не заменялись номером счёта.

В API номер и группа защищены от общего редактирования: `ns` и `rand` включены в `read_only_fields` в [SchetAllEditSerializer](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/s.voovi.ru-api/basic/serializers.py:144). Смена клиента сохранённого счёта в этом обработчике запрещена: нужен отдельный документ.

### 2.3. Единый выбор документа

В API появился [utils/invoice_identity.py](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/s.voovi.ru-api/utils/invoice_identity.py:8); в аналитике — [одноимённый модуль](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/analitic/utils/invoice_identity.py:11). Они проверяют, что найденные строки действительно относятся к одному документу. Старый повторяющийся номер больше не должен молча превращаться в произвольный `.first()` в переведённых обработчиках.

Выбор применяется в редактировании, части оплат и кассовых действий, определении типа платежа, документах, ЭДО и бухгалтерской синхронизации. Там, где уже известен `rand`, используется он. При неоднозначности возвращается ошибка до изменения данных.

Для существующих данных предусмотрена команда [check_invoice_numbers](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/s.voovi.ru-api/basic/management/commands/check_invoice_numbers.py:34): по умолчанию она проверяет, а не перенумеровывает. Заполнение пропущенного номера разрешается только при однозначном восстановлении. Автоматического переименования спорных старых счетов нет.

**Эффект:** номер перестал зависеть от последующего изменения менеджера; проверенные операции перестали выбирать случайный документ по старому дублирующемуся номеру. **Ограничение:** общий валидатор ещё не охватывает все старые PHP-входы; ограничения и исторические дефекты перечислены в разделе 17.

## 3. Сохранение, редактирование и отказ

### 3.1. Повторная отправка формы

В [myogrn.php](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/voovi.ru/myogrn.php:845) и [otherogrn.php](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/voovi.ru/otherogrn.php:409) подключён общий механизм создания. Ошибки сохранения теперь перехватываются общим обработчиком: транзакция откатывается, причина показывается без SQL/технических деталей, загрузочный экран снимается. Введённые значения восстанавливаются, при этом подпись формы остаётся актуальной. Подписанный токен связан с пользователем, клиентом и областью формы. Ключ операции и именованная блокировка различают повтор того же сохранения и новое создание.

Ключ операции позволяет вернуть ранее созданный результат вместо повторного создания. В `myogrn.php` проверка тарифов выполняется раньше проверки ключа: если после первого сохранения тариф стал недоступен, повтор может завершиться ошибкой валидации, хотя первоначальный счёт уже существует. Дубль при этом не создаётся. Две независимо открытые формы могут создать два разных счёта. Таким образом, уникальность номеров дополнена защитой от повторного бизнес-действия: это разные задачи.

В основной форме `myogrn.php` перед записью проверяются выбранные тарифы, количество, скидка и суммы. `otherogrn.php` использует общую нумерацию, защиту от повторов и транзакцию, но не вызывает этот же валидатор тарифов. Сохранение состава и связанных данных идёт в транзакции; при ошибке откатываются участвующие записи. Для этого проверяется InnoDB у нужных таблиц. Завершение PHP-запроса с незакрытой транзакцией вызывает откат.

### 3.2. Замена тарифов в API

Переработан [SchetEditSerializer.create()](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/s.voovi.ru-api/basic/serializers.py:66). Раньше старые строки могли быть скрыты до успешного создания нового состава, а дальнейшая ошибка оставляла документ без активных позиций.

Текущий порядок:

1. Заблокировать и проверить группу счёта.
2. Если заменяется состав — проверить привязанные товары, включая старый формат связи.
3. Проверить непустой список тарифов, один продукт Voovi, положительное количество, корректную цену и скидку.
4. Проверить согласованность наследуемых номера, суммы и ссылки Контура между прежними строками.
5. Создать новые строки, сохранив идентичность документа и переданные общие реквизиты.
6. Скрыть прежние строки и синхронизировать АВ.
7. Зафиксировать всё одной транзакцией; ошибка на любом этапе откатывает всю замену.

Совместная передача тарифов и реквизитов теперь применяется к новому составу целиком. Проверка товаров учитывает как `jurnalskzi.schet_id`, так и старую связь через `jurnalskzi.schet = rand`, включая исторические строки.

**Эффект:** исправлены потеря состава при ошибке и частичное применение реквизитов при замене тарифов. Старый PHP-edit также обновлён: новая строка наследует все поля актуальной исходной записи, затем заменяются только явно редактируемые значения. Флаги оплаты/отгрузки, даты, автор и дополнительные метаданные не теряются из-за узкого INSERT. **Ограничения:** общий PATCH всё ещё допускает обход части проверок; дробное количество требует согласования округления с печатью.

### 3.3. Отказ и клонирование

[otkazschet.php](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/voovi.ru/otkazschet.php:4) переведён на авторизованный POST с проверкой подписанного токена. Все 32 внутренних AJAX-вызова в [tablschetosn.php](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/voovi.ru/tablschetosn.php:3) обновлены под этот контракт.

У отгруженного исходного счёта отказ оформляется отдельным клоном с новым номером и `rand`. Клон наследует связь с тем же документом Контура; сам `bills` не дублируется. Переносится и ожидающая связь с пустым `BillId`. Если у исходного документа есть только старый внешний номер, создаётся ожидающая связь клона. Копируются даты и тип документов, но не идентификаторы уже отправленных сообщений ЭДО.

Автор исходного счёта и сотрудник, выполняющий отказ, не смешиваются. Повтор операции не размножает клон и его связанные записи. Ошибка откатывает отказ вместе с составом и связями.

**Исправление 29 октября:** выбор типа договора вынесен в общее правило: с 2024 года — оферта, для прежних дат — договор либо контракт бюджетной организации. Это правило использует и обычная выдача документов, и отказной клон без `document_data`. Ошибка AJAX отказа теперь показывает понятную причину и позволяет повторить действие.

## 5. Каталог, лицевой счёт и расчёт

### 5.1. Где находится логика

В [basic/kontur/views.py](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/s.voovi.ru-api/basic/kontur/views.py:27) находятся HTTP-входы; [services.py](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/s.voovi.ru-api/basic/kontur/services.py:32) организует сценарий; [domain.py](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/s.voovi.ru-api/basic/kontur/domain.py:56) проверяет состав; [utils/api_skb.py](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/s.voovi.ru-api/utils/api_skb.py:73) обращается к Контуру.

PHP-прослойка [kontur_api.php](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/voovi.ru/kontur_api.php:9) проверяет допустимые действия, методы, CSRF и размер тела. [kontur_common.php](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/voovi.ru/kontur_common.php:16) получает контекст авторизованного сотрудника и счёта. Серверный токен Контура не передаётся в браузер.

### 5.2. Автоматический подбор клиента и лицевого счёта

Плательщик ищется по данным клиента Voovi. Если найдено несколько подходящих записей, сервер не выбирает произвольную первую. Подготовка лицевого счёта выполняется по плательщику и продукту под блокировкой. Если подходящего счёта нет и продукт поддерживает регистрацию через доступный API, выполняется создание автоматически.

Явный отказ Контура не блокирует повторную попытку навсегда. Неопределённый результат сетевого запроса обрабатывается отдельно: нельзя бездумно повторять создание, если оно могло уже пройти на стороне Контура.

Недоступный партнёру продукт не становится доступным от автоматической регистрации. Интерфейс показывает прикладную причину ограничения. Предварительная проверка не равна полной гарантии: некоторые ограничения зависят от клиента, тарифа и всего сочетания продуктов и обнаруживаются лишь дальнейшим запросом.

### 5.3. Снимок и справочники

Продукты, предложения и схемы параметров запрашиваются у Контура. Сохранённый состав конкретного счёта — отдельный снимок, а не постоянно меняющаяся ссылка на текущий тариф. В рамках этой версии полный локальный каталог тарифов заранее не заполняется; будущая таблица актуальных тарифов не подменяет снимок уже выставленного документа.

Короткий кэш предложений составляет 15 секунд, схем параметров — 300 секунд. Общий контекст ключей включает адрес API, учётные данные и партнёра. Предложения дополнительно разделены по плательщику и продукту; схема параметров — по продукту, без отдельного ключа плательщика.

### 5.4. Количество и смешанный состав

Проверяются количество, выбранные параметры, дополнения, допустимая ручная цена и ограничения размера состава. Там, где внешний API ожидает отдельные пакеты, количество разворачивается в единицы с собственными GUID пакетов. Из-за этого несколько одинаковых строк в учётных данных могут соответствовать одной пользовательской позиции с количеством больше единицы.

Количество пакетов и множитель ресурсов — разные внешние понятия. Интерфейс объединяет их представление в подходящем случае, а код переводит значение в требуемый параметр API. Короткая подпись поля не означает, что все виды количества отправляются одинаково.

Расчёт смешанного состава организован по продуктам, с повторным использованием уже полученного плательщика и метаданных. Порядок позиций сохраняется. Это уменьшает повторные запросы. Проверка окончательной совместимости остаётся на стороне Контура: успешные отдельные расчёты продуктов ещё не гарантируют создание одного общего документа.

### 5.5. Общий клиент внешних API

В `KonturClient` собраны обращения к заказам, учётным сведениям, каталогу, отгрузкам и документам. У запросов есть тайм-ауты и общий временной бюджет; для `services.calculate()` общий бюджет расчёта составляет 85 секунд. Это не единый лимит регистрации лицевого счёта, создания документа и всех фоновых задач; у транспорта действуют свои тайм-ауты. Повторы разрешены для чтения, но создание не повторяется автоматически после неопределённого ответа. Значения тайм-аутов и повторов находятся в коде согласно выбранному правилу конфигурации.

Отдельный выбор D/DV-агента в текущую форму не добавлен. Хранение пришедших учётных полей менеджеров не означает, что их можно назначить через используемый запрос создания.

## 6. Создание документа Контура и защита от повторов

### 6.1. Последовательность

Основной код — [services.py](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/s.voovi.ru-api/basic/kontur/services.py:643).

1. Сотрудник собирает состав и получает расчёт. Сервер сохраняет текущий снимок и его ревизию.
2. При нажатии «Выставить счёт Контур» повторно проверяются права, плательщик, актуальность расчёта и ревизия. Расчёт допускается к выставлению в течение 15 минут; затем нужен свежий результат.
3. До внешнего запроса сохраняются идентификатор документа, тело запроса, его хеш и состояние отправки.
4. Выполняется один запрос создания. Идентификатор известен Voovi заранее и используется для дальнейшего сопоставления.
5. При подтверждённом успехе документ получает состояние созданного; сохраняется ссылка на Биллинг по идентификатору, даже если учётный номер ещё не присвоен.
6. Номер, окончательная учётная сумма, оплата и недостающая детализация поступают через обработчик новостей.

**Ссылка и номер — разные данные.** Ссылку можно сформировать по `BillId` сразу; `Number` может появиться позже. Поэтому отсутствие номера не означает отсутствие созданного документа и не является основанием создать его заново.

### 6.2. Состояния и восстановление после прерывания

Локальное `bills.status` описывает ход создания: черновик, отправка, подтверждённое создание, неопределённый результат, отказ или удаление. Точные условия переходов заданы сервисом и обработчиком новостей; пользователю показываются более простые подписи.

Внешнее учётное `bills.State` имеет другое назначение — состояние документа и оплаты по сведениям Контура. Локальный статус не подменяет его.

Если процесс прервался после отправки, документ не создаётся повторно автоматически. [reconcile.py](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/s.voovi.ru-api/basic/kontur_automation/reconcile.py:16) умеет сопоставить пришедшие сведения с сохранённой отправкой, проверить принадлежность и пакеты и завершить восстановление. Неполное событие может дополнить данные, не публикуя преждевременно финансовые изменения; обработка следующей новости при этом продолжается.

Поздний HTTP-ответ не должен перезаписывать уже подтверждённое новостями состояние, включая удаление. Хеш и ревизия защищают от отправки устаревшего состава и от смешивания результатов разных расчётов.

### 6.3. Кто выставил счёт

`bills.created_by` фиксирует локальный ID сотрудника Voovi, который инициировал создание счёта Контура. Это не обязательно первоначальный автор счёта Voovi в `schet.kto`. Поля `ManagerId`, `CreateManagerId`, `CreateManagerPerson` отражают сведения Контура и не заменяют локальный ID.

Когда новость не содержит внешнего менеджера, известный локальный автор не обнуляется. Индивидуальная настройка номера СЦ у пользователя отменена; персонального поля и соответствующего SQL в текущем решении нет. Партнёр задаётся общей настройкой `KONTUR_PARTNER_CODE`. Запись `created_by` решает локальный учёт авторства, но не назначает сотрудника менеджером документа в самом Биллинге.

### 7.5. Почему `bills_operations` всё ещё нужна

Таблица не хранит полную историю всех экранных изменений. Она содержит необходимый контекст внешнего создания и восстановления после прерывания, актуальный расчёт, подготовку лицевого счёта и событие статистики. Обычный приём учётной новости не журналируется отдельной операцией. Например, отсутствие HTTP-ответа нельзя безопасно разрешить только по одному тексту ошибки — нужно знать, какой запрос уже был отправлен.

Диагностика сокращена: нет отдельного сохранения всех HTTP-статусов, трассировок, ответов и номеров попыток. Промежуточные расчёты заменяются актуальным состоянием.

## 8. Присоединение существующего счёта

Реализация — [linking.py](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/s.voovi.ru-api/basic/kontur/linking.py), форма и поиск — `kontur_invoice.php` и `kontur-invoice.js`.

1. Сотрудник ищет документ среди уже полученных **локальных** учётных счетов по номеру, ИНН или названию.
2. Точное совпадение номера показывается выше; выдача ограничена 20 записями.
3. Если документ найден, сохраняется связь с его `BillId`, показывается имеющийся состав.
4. При несовпадении реквизитов выводится предупреждение; явное подтверждение позволяет присоединить документ. Совпадение ИНН/КПП не стало жёстким обязательным условием.
5. Если документ ещё не найден, разрешено сохранить введённый номер и ожидающую связь с пустым `BillId`.
6. При сохранении поиск повторяется. Если между открытием формы и нажатием сохранения документ успел появиться, связь сразу завершается.
7. Иначе её завершает обработчик последующих новостей. При неоднозначном номере нужен явный выбор документа, а не случайное присоединение.

Принцип сумм: **ранее сохранённый `schet.priceks` не заменяется общим итогом Контура**, в том числе когда его значение равно нулю. Заполнение отсутствующей суммы допускается только при предусмотренных условиях, включая отсутствие нескольких связей, на которые ошибочно размножился бы полный итог.

При подготовке старой базы `link_saved_invoices()` добавляет отсутствующие однозначные связи. Для дальнейших записей старого PHP, который вообще не вызывает новый API, добавлен `LegacyLinkService`: он сверяет реквизиты при чтении нового статуса, редактировании, присоединении и при обработке новости. В начале `schetmain` выполняется отдельная сверка изменившихся/неразрешённых связей, даже если новых новостей нет. При смене только номера или только ссылки прежний второй реквизит не удерживает старый состав; неизвестный документ остаётся ожидающим.

**Эффект:** старый и новый документ можно использовать через один механизм состава; неизвестный на момент ввода `BillId` не мешает сохранить номер; один документ не дублируется по числу привязанных счетов Voovi.

## 9. Новости, оплаты, удаление и продление

### 9.1. Приём учётной ленты

[accounting_feed.py](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/s.voovi.ru-api/basic/kontur_automation/accounting_feed.py) получает страницы новостей, [reconcile.py](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/s.voovi.ru-api/basic/kontur_automation/reconcile.py:16) применяет документ, [jobs/schetmain.py](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/s.voovi.ru-api/basic/kontur_automation/jobs/schetmain.py:51) организует проход и дальнейшие действия.

Первичное сопоставление идёт по `BillId`. Поиск по номеру оставлен только для совместимых старых случаев и допускается при однозначном результате. В [queries.py](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/s.voovi.ru-api/basic/kontur_automation/queries.py) собраны эти правила выбора и чтения сохранённого документа.

Обработчик объединяет два источника: сведения, уже известные из создания в Voovi, и пришедшие учётные данные. Недостающие поля и состав дополняются; известный локальный автор, сохранённые условия и старые суммы Voovi не обнуляются только из-за отсутствия поля в новости. Вместе с тем состояние оплаты, видимость, дата оплаты и метка времени действительно обновляются: правило «дополнить отсутствующее» не превращает статус документа в неизменный снимок.

Повторная или устаревшая новость не должна повторно публиковать те же изменения. `TimeStamp` используется для защиты от более старого состояния. На границе страницы учитывается, что несколько событий могут иметь одинаковую метку времени: нельзя продвинуть курсор так, чтобы потерять оставшиеся события той же группы.

### 9.2. Курсор и устойчивость

[runtime.py](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/s.voovi.ru-api/basic/kontur_automation/runtime.py:19) хранит `last_tick` в рабочем каталоге задачи. Курсор записывается атомарной заменой JSON-файла после успешной обработки соответствующей порции. Ошибка основного применения не позволяет пропустить проблемный диапазон. Именованная блокировка базы исключает одновременную работу двух проходов и конфликт с изменением расписания. Ограничение числа страниц защищает один запуск от бесконечной работы.

При восстановлении дампа нужно согласовывать и курсор: актуальный курсор поверх старой базы не восстановит уже пропущенные этой базой новости.

### 9.3. Финансовые изменения и вторичные действия

Сначала сохраняются документ, связь и основное финансовое состояние. При запуске с разрешёнными уведомлениями (`--notifications`) затем в очередь ставится отдельное последействие по `BillId`: комментарии, письма, сведения о закрывающих документах и другие вторичные операции. Очередь хранит ID, а не старую копию новости. Перед выполнением читается текущее состояние: устаревшее задание не должно вновь обработать уже удалённый документ. Признаки отправленного комментария или уведомления фиксируются после успешного действия. Ошибка последействия журналируется и может быть повторена очередью, не останавливая получение следующих финансовых новостей.

В основной ветке `schetmain` сохранены сценарии оплаты, условной оплаты, отсутствующего в Voovi счёта, служебных комментариев и продления. Дата фактической оплаты обрабатывается здесь же. Отдельный скрипт повторного обхода дат оплаты исключён; двух независимых проходов для одного назначения больше нет.

### 9.4. Удаление в Биллинге

Отвязка выполняется после проверенного учётного признака скрытия/удаления подходящего неоплаченного документа. Обработчик не делает вывод об удалении только из того, что один поисковый запрос ничего не вернул.

Очищаются предусмотренные реквизиты Контура у связанных Voovi-счетов и удаляются связи. Сам счёт Voovi, его состав и собственные платежи не удаляются. Общий учётный документ остаётся в `bills` с состоянием удаления — для согласованности последующих событий. Если позднее документ снова виден, это не восстанавливает автоматически прежние пользовательские связи.

При отвязке проверяются сохранённые исходные значения `legacy_number_before` и `legacy_amount_before`, чтобы не стирать чужое последующее изменение вслепую. `legacy_published_at` используется как маркер публикации для других проверок, но непосредственно в проверках отвязки не участвует. Политика отсоединения не равна безусловному удалению любых оплаченных документов.

### 9.5. Дата продления

Для мультипродуктового документа нельзя брать дату окончания первого попавшегося тарифа. [functions.py](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/s.voovi.ru-api/basic/kontur_automation/functions.py) определяет дату по относящимся к операции тарифам. Автоматическая дата выбирается только при согласованном результате. Разные окончания не угадываются: обновление пропускается с объяснимым результатом.

**Эффект:** счёт дополняется по идентификатору, не требуется пользовательская кнопка проверки; прерывание создания и сбой уведомления не должны блокировать весь нормальный поток. Независимое изменение номера или ссылки старой формой теперь разрешается общим сервисом связи; неоднозначные реквизиты переводятся в ожидание с предупреждением вместо показа прежнего состава.

## 12. Аналитика, авторизация и SQL

### 12.1. Авторизация до выполнения страницы

В [middleware/middleware.py](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/analitic/middleware/middleware.py:7) проверка сотрудника выполняется **до вызова обработчика страницы**. Проверяются формат ID, непустой хеш, соответствие хеша через `compare_digest` и признаки недоступного пользователя. Результат используется повторно при заполнении прав и контекста.

До изменения view мог уже выполнить запросы или действие, после чего middleware отклонял ответ. Широкий перехват исключений также мог маскировать настоящую ошибку страницы под проблему авторизации. Сейчас отсутствие доступа останавливает выполнение заранее; исключение view не подменяется такой проверкой.

Это исправление авторизации, но не полная переработка разграничения прав: проверка доступа к конкретному направлению/документу ещё не присутствует во всех финансовых действиях. Проверки Контура также не подменяют проверку собственной оплаты Савоира: это два независимых источника финансового состояния.

### 12.2. Параметризованный SQL

В обработке оплат и отчётов входные значения передаются отдельными параметрами SQL вместо форматирования внутрь строки. Затронуты [SqlQuery.py](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/analitic/utils/SqlQuery.py:67), [SqlQueryReports.py](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/analitic/utils/SqlQueryReports.py:11), [ORM.py](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/analitic/utils/ORM.py:4), `payments/views.py`, а также основные запросы `utils/SqlQuerySELECTgeneral.py` API.

Особые случаи обработаны явно: пустой список не превращается в выборку без ограничения; отсутствующий платёж возвращается как пустой результат и обрабатывается понятной ошибкой вместо прежнего сбоя чтения; неоднозначный документ отклоняется. Изменение условия групп выполняется через разрешённый набор полей, с сохранением прежних правил пустого/первого значения.

## 13. Импорт агентского отчёта

### 13.1. Защита от удвоения начислений

Основная реализация — [utils/skbpasre.py](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/analitic/utils/skbpasre.py:100). Раньше повторный импорт мог создать новые записи начислений для того же отчёта. Теперь сравнивается содержимое за точный период и принципала, а не имя загруженного файла.

Из строк основного отчёта, дополнений и штрафов строится нормализованное представление. Порядок строк и имя файла не меняют его отпечаток; две одинаковые строки внутри одного настоящего отчёта сохраняют кратность и не сливаются в одну. Пустые числовые значения нормализуются. Сравнение со старым хранилищем учитывает его точность FLOAT32.

Текущий алгоритм сохранения:

1. Взять именованную блокировку для принципала и точного периода; проверить транзакционный движок таблицы `avkontur`.
2. Прочитать уже сохранённые записи, включая старые импорты со случайными UUID.
3. Если содержание совпадает — завершить как повтор без новых начислений. Существующие UUID, комментарии, автор, обработанность и связи сохраняются.
4. Если за тот же точный период есть другой или неполный состав — вернуть конфликт, ничего не дописывая и не затирая.
5. Для нового содержания вычислить устойчивые UUIDv5, учитывающие повторяющиеся строки, и пакетно записать параметризованным SQL.
6. При ошибке откатить весь импорт.

Новая таблица журнала импортов для этого не создавалась. Проверка повторности использует существующие данные и содержимое отчёта. Защита относится к определённому точному периоду, а не доказывает автоматически отсутствие любых пересечений двух произвольных периодов.

**Закрыто в этом проходе:**

- Старые PHP-записи номера/ссылки подхватываются общим `LegacyLinkService`, включая фоновой проход без новых новостей. Новый и старый входы используют одну связь с документом.
- Смена одного внешнего реквизита больше не оставляет прежний состав. При неоднозначности показывается ожидание и предупреждение; лента продолжает обработку других корректных групп.
- Готовность финансовых данных проверяет номер, сумму и соответствие документа; нулевая сумма не считается отсутствующей. Draft и ожидающие связи не трактуются как отсутствие Контура.
- Позднее добавление неоплаченного документа не стирает прежние платежи и отгрузку. Унаследованная отметка не разрешает новые автоматические действия до подтверждения оплаты этого BillId. Отдельно закрыта автоотгрузка неоплаченного Контура при первом платеже только Савоиру.
- Исторический тип договора выбирается общим правилом и при отказном клонировании без `document_data`.
- PHP-формы показывают безопасную причину ошибки, снимают загрузку и восстанавливают введённые значения; AJAX отказа обрабатывает ошибку и неопределённый сетевой результат.
- Старый PHP-edit сохраняет поля исходных записей, флаги, даты, автора и дополнительные метаданные; ошибочная вставка откатывает состав и АВ.
- Результат агентского импорта сохраняется и показывается автору в интерфейсе независимо от VK, включая прерывание процесса.
- Production-env заполнен и проверен без внешних вызовов; стандартные Django-приложения читают сильный production-ключ из env.

**Остаются отдельными задачами:**

1. **Округление дробного количества.** API, печать и бухгалтерская передача используют не полностью согласованные правила; возможна разница в копейку. Нужен общий расчёт с единым округлением.
2. **Проверки всех изменяющих входов.** Общий PATCH допускает обход части проверок состава; не везде проверено направление/состояние пользователя. Часть старых PHP-входов ещё обходит общий проверенный поиск документа.
3. **Параллельное распределение одной оплаты.** Проверка документа не заменяет блокировку платежа на время распределения.
4. **Частичная отгрузка смешанного документа.** Условие исходного скрипта оценивает первую отгрузку; несколько результатов требуют общей политики готовности.
5. **Старые и неизвестные внешние писатели.** Триггеры идентичности временно отключены; прямые старые записи не обязаны резервировать номер и `rand`, поэтому возможны новые коллизии и изменение клиента вне проверок обновлённого кода. Нельзя подтвердить работу непредоставленных программ, согласованность всех счётчиков и досев реестра для добавленных ими записей. Принятое снятие триггеров не устраняет неатомарный старый edit и различия финансовых правил.
6. **Приоритет общей очереди.** Большое число медленных последействий может задерживать финансовое задание.
7. **Фактическое production-развёртывание.** Заполненный env и offline-проверки не подтверждают доставку SMTP/VK, внешний HTTPS-прокси или отключение старого cron. Рабочие интеграции этим проходом не запускались; версии платформы остаются отдельным техническим долгом.

Дополнительная граница: сопоставление одинаковых учётных тарифов с разными параметрами и агрегированным `TariffCount` ещё не подтверждено реальным ответом API во всех комбинациях. Это не доказанная ошибка, но сценарий для отдельной сквозной проверки.

## 19. Словарь полей и идентификаторов

| Обозначение | Значение | Что с ним нельзя путать |
| --- | --- | --- |
| `schet.id` | ID одной строки состава Voovi | Не ID всего многострочного документа |
| `schet.rand` | Группа строк одного счёта Voovi | Не визуальная группировка нескольких счетов |
| `schet.ns` | Однажды выданный номер Voovi | Не вычисление из текущего менеджера |
| `schet.kto` | Сотрудник счёта Voovi | Не обязательно создатель позднее добавленного Контура |
| `schet.nomerschetks` | Прежнее поле номера Контура у Voovi-счёта | Не `BillId` и не гарантия завершённой связи |
| `schet.priceks` | Согласованная сумма Контура для конкретного Voovi-счёта | Не обязательно полный итог общего документа |
| `BillId` | Уникальный идентификатор общего документа Контура | Не отображаемый учётный номер |
| `Number` | Номер, присвоенный в учётной системе Контура | Может отсутствовать сразу после создания |
| `bills.id` | Локальный числовой PK записи | Не внешний GUID |
| `bills.status` | Локальный жизненный цикл создания | Не внешняя оплата |
| `bills.State` | Учётное состояние Контура | Не локальный статус отправки |
| `bills.created_by` | Известный создатель из Voovi | Не внешний `ManagerId` |
| `quote_amount` | Предварительный рассчитанный итог | Не окончательный учётный `Amount` |
| `revision` | Версия текущего состава для проверки актуальности | Не сохраняемая история всех расчётов |
| `request_hash` | Отпечаток отправляемого состава | Не API-токен и не номер документа |
| `TimeStamp` | Метка изменения учётных данных | Не дата оплаты |
| `PaidDateTicks` | Учётная дата оплаты | Не время получения новости |
| `last_tick` | Позиция чтения ленты | Не счётчик счетов |
| `BillTariffId` | Внешний ID учётного тарифа | Не локальный `bills_tariffs.id` |
| `bills_voovi_links` | Связи многих Voovi-счетов с общими документами | Не копии состава по каждому счёту |

Для проверки изменений по исходникам удобнее начинать с интересующего пользовательского сценария, затем переходить к его сервису и таблицам. Для оценки готовности к production следует читать этот документ вместе с отчётом совместимости и инструкцией подготовки схемы: описание реализованного механизма не означает, что все перечисленные открытые вопросы уже закрыты.
