# Исправления после проверки совместимости, 30 октября 2026 года

Изменения внесены в локальные исходники. Production-сервер, его БД, контейнеры и cron в этом проходе не изменялись. Проверки с записью выполнялись только в отдельных тестовых базах. Новые рабочие таблицы и поля не добавлялись.

## Принятые правила

- Отгрузка, оплата и просчёт ЗП не зависят от наличия `bills_voovi_links`, готовности API Контура или найденного BillId. Сохраняются прежние бизнес-условия — например, существующая отметка оплаты и правила периода отгрузки.
- Номер/ссылка могут относиться к другому поставщику или не находиться в локальном справочнике. Это обычное состояние: автоматическую связь не создаём, предупреждение об ошибке не выводим, основные операции не запрещаем.
- Явно созданная ожидающая привязка из ручной формы сохраняется до появления документа. Она также не ограничивает финансовые действия.
- Недоставка информационного сообщения в VK или вспомогательного уведомления по почте не отменяет основную операцию.
- При печати исторического счёта итогом служит сохранённый `schet.price`. Печать не перезаписывает старый счёт и не заменяет его итог расчётом по текущему каталогу.

## Денежный расчёт

API использует общий `utils/create_pdf/billing_calc.py` для сохранения нового состава, PDF, XML и строк Бухгалтерии. PHP использует общий `invoice_money.php` с точными вычислениями DECIMAL на существующем MySQL. Дополнительные расширения PHP не требуются.

1. Цена, количество и скидка читаются без промежуточного преобразования денег во float.
2. Скидка вычисляется до округления. Новый итог округляется до двух знаков HALF_UP.
3. Для сохранённого счёта итог берётся из `schet.price`. Историческая запись не переписывается при печати.
4. Копейки распределяются между строками по наибольшим остаткам. Сумма строк точно равна общему итогу.
5. НДС распределяется тем же способом. Сумма НДС строк равна НДС итога, сумма без НДС плюс НДС равна сохранённому итогу. Разница не переносится целиком в одну маленькую строку, создавая отрицательную стоимость без НДС.
6. В прежних печатных формах и PDF/XML отдельно учитывается сохранённый выезд специалиста. Служебное значение `goroddd=162534` выездом не считается.

В старой схеме нет полного исторического снимка цены каждой позиции Voovi. Поэтому при расхождении каталога с сохранённой общей суммой печатное распределение восстанавливается пропорционально стоимости позиций; это не изменение данных БД. Общий итог остаётся прежним. Для выгрузки старого отдельно сохранённого выезда в Evrika полноценной отдельной позицией понадобится известное соответствие её номенклатуре; произвольный SKU в этом исправлении не придумывается.

Примеры проверок: 120 ₽ × 1,01 со скидкой 1,25% даёт 119,69 ₽ при новом сохранении; старый сохранённый итог 119,68 ₽ печатается как 119,68 ₽. Для ста строк по 0,01 ₽ при НДС 22% итог 1 ₽, НДС 0,18 ₽; ни одна строка не получает отрицательную стоимость без НДС.

## Оплаты и чеки: что пока не изменено и как исправлять

Сейчас `schet`, `kvobop`, `payment` и `payment_nal` в проверенной локальной схеме используют InnoDB, а `chec` — MyISAM. Поэтому транзакционный откат оплаты не откатывает уже вставленный чек. Исправление конкуренции банковского разнесения этого свойства не меняет. Кассовый процесс целиком в этом проходе не переписывался.

Предлагаемый отдельный этап:

1. На полной копии проверить перевод `chec` в InnoDB и совместимость писателей очереди чеков. Конвертацию рабочей таблицы не выполнять незаметно при запуске: она требует отдельного плана, резервной копии и согласованного окна с учётом фактической MariaDB 5.5.
2. В кассовом действии открывать одну транзакцию, захватывать `PaymentNal` по первичному ключу и повторно проверять статус обработки под блокировкой. Затем согласованно записывать `kvobop`, очередь `chec` и финансовые флаги.
3. Повторная обработка того же кассового задания должна возвращать сохранённый результат, а не создавать новые записи. Использовать устойчивый идентификатор операции и одинаковый порядок захвата строк.
4. Отправлять задание физической ККТ после фиксации БД. У уже пробитого фискального чека нет обычного SQL-отката: после тайм-аута нужно выяснять результат по сохранённому идентификатору, а не пробивать чек повторно.
5. Проверить два одновременных кассира, повтор запроса, сбой второй строки, обрыв до/после commit и обрыв после принятия задания ККТ.

DDL и перезапуск production для этого этапа в текущем исправлении не выполнялись.

## Что за отчёт по активным организациям

Это сохранённый Excel/VK-отчёт, не удалённый отчёт Google Sheets. Он доступен в аналитике `/reports/order` по кнопке «Заказать отчет». Пользователь выбирает год, направление и режим ячеек — количество счетов или суммы.

- Строка Excel — организация: ИНН, КПП, наименование.
- Столбцы — продукты выбранного направления.
- Ячейки — число уникальных групп `rand` либо суммы за выбранный год.
- Отбор делается по `schet.date_op`. Для направления Контура используются `priceks`, для остальных — `price`.
- Готовый XLSX отправляется в VK и удаляется только после успешной доставки.
- В рабочее время будней формирование откладывается на 20:00; вне этого окна ставится в очередь сразу. Существующая реализация тяжёлая: число SQL-запросов примерно равно числу организаций, умноженному на число продуктов.

Проблема находится в `utils/report.py`: `wb.save()` пишет в `BASE_DIR/tmp`, но каталог перед этим не создаётся. На чистой установке возникает `FileNotFoundError` ещё до отправки в VK. Исправление небольшое: создавать каталог либо использовать `tempfile`; бизнес-выборку менять для этого не требуется.

По текущему поручению сам алгоритм формирования этого отчёта не менялся: пользователь запросил пояснение. Отказ VK после постановки задачи уже не возвращает ложную ошибку основного запроса. В старой выборке также нет отдельных фильтров del/отказа/черновика: фактическое значение «активные» определяется датой и суммами; пересмотр состава отчёта — отдельное бизнес-решение.

## Проблема первой отгрузки мультипродуктового документа

В `basic/kontur_automation/jobs/status_delivery.py` есть два места с выбором первого элемента:

- `all_shipments[0].State` участвует в решении об автоматической отгрузке всей группы Voovi;
- `shipments[0].State == 2` может привести к записи «Акт подписан» для всей группы.

Дополнительно используются состояния заданий закрывающих документов и стратегия отгрузки. То есть первый элемент — не единственное условие, но остальные отгрузки в этих ветках не проверяются. Сообщение о нескольких отгрузках отправляется уже после принятия решения и не отменяет его.

Пример: у общего BillId две части — A завершена (`State=2`), B ещё не завершена. Если A стоит первой, одна из веток может разрешить отгрузку/поставить отметку подписанного акта целиком. Если API вернёт B первой, результат будет другим при тех же данных. Когда один BillId связан с несколькими счетами Voovi, тот же общий список используется для каждой группы без определения, какая часть относится именно к ней.

Несколько отгрузок не обязательно равны нескольким продуктам: это могут быть этапы, разные документы или корректировки. Поэтому простая замена `[0]` на `all(State == 2)` тоже не является доказанно правильным правилом.

Для исправления нужно определить:

1. Какие актуальные отгрузки/закрывающие документы относятся к каждому продукту либо конкретной группе Voovi.
2. Какие отменённые/заменённые документы не участвуют в готовности.
3. Когда разрешается закрыть группу целиком, а когда отражать частичное завершение.
4. Как поступать, если API не даёт однозначно сопоставить отгрузки с группой.

В этом проходе данный алгоритм не менялся — пользователь запросил подробное объяснение. Исправленное ранее определение единого срока тарифов не решает эту проблему: согласованная дата и завершённость всех относящихся документов — разные признаки.
