# Проверка страницы «Компании»: продления и отказы

Дата: 02.11.2026. Исследован текущий локальный код и локальный сайт. Код и бизнес-данные
не изменялись; использованы чтение исходников, SELECT-запросы и просмотр фильтров.
Production не проверялся. GET-запросы сайта могут писать обычный журнал `aaa_log`
и сохранять выбранные фильтры в cookies/session.

## Как устроено

`check.php` проверяет cookies пользователя и загружает вкладки AJAX-запросами.
«Таблица счетов» — `tablschet.php` (организация, даты, новый/продление), затем
`tablschetog.php` (счётчики категорий), затем `tablschetosn.php` (список и действия).
Продление открывает `newschet.php` с `oldns`. Отказ отправляет POST в
`otkazschet.php`; бронь и звонок сохраняются через `bron.php`.

## Подтверждённые проблемы

### 1. [P1] Не все обработчики закрыты авторизацией и правами организации

`tablschet.php:1–16`, `tablschetog.php:1–47` подключают конфигурацию без проверки
пользователя. Конфигурация только подключает БД и журналирует запрос, но не
авторизует. Параметры `id`/`users` поступают от клиента; при `ogrn=0` фильтр
организации вообще убирается. `users_access` применяется к выпадающему списку,
но не ограничивает SQL счётчиков.

Проверено без cookies: `/check.php` отвечает 302, а `tablschetog.php` с обычными
параметрами фильтра — 200 и возвращает счётчик 176.

`bron.php:14,33` изменяет бронь/звонок по GET без авторизации, CSRF-токена и проверки
доступа к счёту. В SQL непосредственно вставляются параметры запроса. Аналогично
в SQL счётчиков напрямую вставляется `ogrn` (`tablschetog.php:40`). Это также
потенциальные SQL-инъекции. Эксплуатация и реальные изменения не выполнялись.

`tablschetosn.php` и `otkazschet.php` уже требуют авторизованного сотрудника, но
проверки его доступа к организации конкретного счёта в этой цепочке нет.

Исправление: общий серверный контекст пользователя, проверка организации на чтении
и записи, POST + CSRF для изменений, валидация и экранирование параметров SQL.

### 2. [P1] Счётчик продлений и список используют разные условия

`tablschetog.php:47` требует `shetold=''`, а `tablschetosn.php:1032` допускает
и пустой, и непустой `shetold`. На локальных данных ИЦ «SAVOIR» (`ogrn=12`),
01–30.11.2026: счётчик **176**, запрос подробного списка **248** уникальных `rand`.
В браузере подтверждено 248 строк `tr.schetprodlenie` при счётчике 176.

Исправление: единое правило отбора для счётчика и списка с группировкой по `rand`.

### 3. [P1] Смена организации/типа оставляет старые строки и кнопки действий

В `tablschet.php:164–197` смена организации или типа обновляет только
`#tablschetog`; `#tablosn` не очищается и не перезагружается. Очистка есть только
в обработчиках изменения дат. Пользователь видит новые фильтры/счётчики над
старым списком и может выполнить действие над счётом прежней выборки.

Исправление: сбрасывать или обновлять подробный список при любом изменении фильтра;
отменять устаревшие AJAX-запросы, чтобы поздний ответ не подменил актуальный список.

### 4. [P1] Аналитика отказов считает позиции вместо счетов

В `tablschetosn.php:189,292` используются `COUNT(schet.prichotk)` и
`SUM(schet.price)` с группировкой только по причине. Несколько тарифов одного
`rand` считаются несколькими отказами, а сохранённая общая цена счёта повторяется
для каждой позиции. В локальной контрольной выборке отказов с `dateotkaz` за
2026 год 1930 строк соответствуют 1711 счетам. Это проверка структуры данных,
а не воспроизведение точного фильтра графика: график фильтрует по дате создания.

Дополнительно запрос количества требует `cher=1`, запрос суммы — нет; в этих
запросах отсутствует исключение удалённых строк. Поэтому составы выборок также
неодинаковы.

Исправление: сначала получить одну запись на `rand` с суммой счёта, затем
агрегировать по причине; явно согласовать период по дате создания или отказа.

### 5. [P2] Первичная загрузка использует другие даты, чем поля на экране

В `tablschet.php:93` первый запрос получает даты из PHP-session, хотя поля
заполняются из cookies, а вычисленные в JavaScript `datastart/datafinish` не
используются. Значения текущего месяца устанавливаются уже после запроса
(`150–156`). При пустой session `tablschetog.php` обрабатывает пустую дату через
`strtotime`, что даёт эпоху Unix вместо выбранного месяца.

Без cookie `tip` рендерится пустой выбранный пункт (`tablschet.php:72`), и
счётчики не получают ни одну из веток `tip=1/2`. Пустой тип и незаполненные
счётчики наблюдались в браузере до ручного выбора «Продление».

Исправление: сначала задать и проверить единые значения по умолчанию, затем
послать первый запрос с фактическими значениями полей.

### 6. [P2] Составные продления фильтруются по месяцам концов диапазона

SQL `tablschetosn.php:1032` отбирает по точным датам, но далее строки «Сер/Пос»
дополнительно фильтруются через `stristr` по месяцу/году. В `1298` месяц берётся
из `naf` (конец периода), год — из `nay` (начало). При переходе через Новый год
это неверная пара. В `1541` проверяются только месяцы начала/конца, без середины
длинного периода. После отказа AJAX-перезагрузка (`1477`) не передаёт `naf/nayf`,
хотя эти поля нужны данным условиям.

Кроме того, SQL требует одновременно `prodlens=0 AND prodlenks=0`, скрывая
составной счёт, когда одна часть уже продлена, а другая ещё ожидает. В текущей
локальной ноябрьской выборке таких частично продлённых счетов не найдено;
условие всё равно исключает этот сценарий.

Исправление: отбирать каждую часть по её точной дате и её собственному флагу;
передавать единый набор параметров при любой перезагрузке.

### 7. [P2] Защита отказа от дублей ограничена одним токеном формы

`otkazschet.php:24–34` для отгруженного счёта использует идемпотентность по
токену и блокирует исходные строки, но после блокировки проверяет только `akt`.
Уже выполненный отказ/закрытое продление не проверяются. Две независимо открытые
формы с разными токенами могут создать два отказных клона того же источника.
Для неотгруженного счёта повтор может переписать причину, дату и автора отказа.
Это вывод из кода, реальные отказы для воспроизведения не выполнялись.

Исправление: после блокировки проверять допустимость перехода состояния и
наличие уже выполненного действия независимо от токена конкретной формы.

## Что уже защищено

`otkazschet.php` принимает только POST, проверяет сотрудника и подписанный токен
формы. Транзакция и повтор с тем же токеном для создания отказного клона уже
реализованы через `schet_identity.php`. Эти механизмы следует сохранить.

## Порядок исправления

1. Доступ к обработчикам, права организации и изменения через GET.
2. Единый отбор/агрегация по `rand`, синхронность фильтров и списка.
3. Начальные значения фильтров и составные продления.
4. Допустимые переходы отказа и конкурентные действия из разных форм.

Эти исправления можно проектировать без изменения текущей схемы базы данных.
