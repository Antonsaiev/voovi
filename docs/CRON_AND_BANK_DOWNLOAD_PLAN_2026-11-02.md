## Предлагаемая архитектура скачивания

Рекомендуется Django management-команда и отдельная очередь/worker банковского скачивания плюс отдельный Selenium Firefox. Общий worker должен явно исключать эту очередь: одной настройки нового worker недостаточно. Сначала проверить поддержку и маршрутизацию именованных очередей текущей библиотеки. Без Celery и без Docker socket в Django.

Альтернатива — оставить host cron для браузера, исправив контейнер и безопасную передачу файлов. Это меньше изменений, но сохраняет два независимых механизма расписания. Переносить браузер внутрь web/API-контейнера не рекомендуется.

Django вызывает Selenium по внутренней Docker-сети. Порт WebDriver не публикуется наружу; диагностический noVNC — только при необходимости через ограниченный доступ. Секреты берутся из ENV, не передаются аргументами команд и не попадают в логи. Доступ браузера ограничен нужными каталогами. Никаких действий по созданию/подписанию банковских платежей: только вход и экспорт выписок.

### Порядок реализации

1. Сохранить исходники, ENV, cron, список счетов профилей, параметры периода и последний успешный файл. Исследовать причину отсутствия dockerbank; создать воспроизводимую конфигурацию Firefox с проверкой готовности и restart policy.
2. Перенести текущий BankStatementDownloader в модуль Django. Сохранить профили mi/ai, их счета и экспорт за предыдущий день. Для ручного повтора — явные профиль и дата; дата фиксируется при постановке задачи, а не вычисляется заново после задержки.
3. Сохранить отдельную банковскую сессию для каждого расчётного счёта, ограниченные повторы и закрытие браузера. Ограничить общее время задания. При SMS/подтверждении/изменении интерфейса — понятный отказ и диагностика, без обхода банковской защиты и бесконечного ожидания.
4. Разнести незавершённую загрузку и готовые файлы: staging и ready на одной файловой системе. Firefox пишет только в staging; после завершения, стабильности размера, проверки заголовка 1С и целостности формата файл атомарно публикуется в ready. Django-импортёр сканирует только ready. Общий том должен соответствовать каталогу существующего импортёра. Сейчас /root/selenium-compose/files/Downloads уже подключён в production compose.
5. Учесть пустые корректные выписки без платежей, частичные .part/.tmp, прямую допись .txt, повтор имён и повтор экспорта. Сохранять исходник, контрольную сумму и результат по профилю/счёту/дате. Само скачивание не изменяет финансовые записи.
6. Взаимное исключение загрузок на одном браузере, защита от двойной постановки и ограниченные повторы. При частичном успехе повторять только неуспешные счета. Разрешать осознанную повторную загрузку за ту же дату, если банк дополнил выписку; существующая защита импорта должна исключать дубли платежей.
7. Сохранить ежедневные 06:00 mi и 06:10 ai, выполнять последовательно при наложении. Готовый файл передавать существующему импортёру; не запускать второй разнос и не менять его правила. Ошибки скачивания/VK не останавливают общий worker.
8. Отдельный журнал скачивания: профиль, маскированный счёт, дата выписки, время, попытка, файл, успех/ошибка. Секреты и полный банковский документ в журнал не выводить. Скриншоты ошибок ограничить по правам и сроку хранения. Использовать существующий механизм удаления старых банковских журналов либо явно согласовать отдельный срок.

### Приёмка и переключение

- Локальные тесты с заменой Selenium/VK: успех/ошибка входа, зависание, частичный файл, пустая выписка, обрыв, повтор, параллельный запуск, границы дат, несколько счетов и частичный успех.
- Проверить, что новый worker не забирает общие задания, а общий не забирает браузерные. Тесты разнесения банка, ЗП и существующих расписаний не должны регрессировать.
- Production: сначала флаг нового скачивания выключен. Реальный пилот — один профиль/одна дата, экспорт только для чтения. Сравнить счета, период и состав файлов; проверить отсутствие повторных финансовых записей. Само скачивание не доказывает полноту всех банковских операций.
- После успешной приёмки закомментировать только три host cron: mi, ai, docker cp/очистка. Включить новое расписание, проверить оба профиля и все счета на первом плановом запуске. Отключённые исходные команды сохранить для возврата.
- Откат: сначала остановить новые браузерные задания, затем вернуть работоспособный старый контейнер/cron с безопасной передачей файлов. Не возвращать прежнюю массовую очистку Downloads: сейчас она выполняется даже при ошибке docker cp. Не включать обе цепочки одновременно.

## Решения до реализации

Нужно принять архитектуру отдельного Django worker + Selenium и уточнить два условия месячного контроля (сумма поставщика и опись при нуле). Никакие новые правила, отключения cron или реальные банковские запуски этим документом не выполняются.
