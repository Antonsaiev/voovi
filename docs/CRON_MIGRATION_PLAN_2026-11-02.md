## 2. Ежемесячный контроль: что требуется исправить при переносе

Источник: `/var/www/toha/data/python_scripts/opoveshenie/opovesheniya_onlkas_nosum.py`.

1. **Несколько тарифов в маркировке.** Старый код считает все неудалённые строки выбранного `rand` и при количестве больше одной отправляет требование поместить отгруженный счёт в черновик и выставить заново. Это не проверка ошибки конкретного тарифа. Многотарифность сейчас поддерживается, поэтому такой общий запрет нельзя переносить. Предлагается исключить это правило из новой задачи; если есть отдельные запрещённые сочетания, сначала перечислить именно их.
2. **Сумма поставщика у онлайн-касс.** Сейчас проверяется пустая строка `priceks` у всего отдела 24. Номер поставщика и необходимость второго счёта не проверяются, NULL обрабатывается небезопасно. Нужно согласовать, для каких счетов сумма действительно обязательна. Отсутствие поставщика/связи с Контуром само по себе не должно становиться ошибкой, а наличие связи не должно влиять на отгрузку, оплату или ЗП. Не требовать `BillId`.
3. **Исполнитель описи.** Сейчас выбираются счета маркировки и проверяется `sos_opis == 0`; количество описей `kol_opis` получено из БД, но в условии не используется. Нужно определить, требуется ли уведомление при `kol_opis=0`. Предлагается проверять исполнителя только когда есть описи либо тариф прямо требует их оформления. Самостоятельно менять правило без этого решения не следует.
4. **Месяц отгрузки.** Сейчас это `schet.akt_date` в формате YYMM, а не дата выставления, поступления оплаты или дата выполнения задачи. В новой команде период задавать явно как `--month YYYY-MM`; отдельно тестировать январь/декабрь. Не заменять источник периода другой датой без отдельного решения.
5. **Группировка.** Старые запросы группируют по `ns` и выбирают произвольные остальные поля. Новые выборки должны сохранять строки тарифов и объединять только один документ по `rand`; разные исторические счета с одинаковым `ns` не склеивать. Признаки разных строк оценивать явно, не брать произвольную первую строку мультипродуктового счёта.
6. **Побочные действия.** Это контроль и уведомления. Не менять состав, суммы, отгрузку, распределение оплат, ЗП или состояния счетов.

Агрегатная проверка production за октябрь 2026 (`akt_date='2610'`): 10 счетов онлайн-касс, среди них нет пустой суммы поставщика; в прежнюю выборку маркировки не попало ни одного счёта. Это проверка конкретного месяца, а не доказательство полноты правил для всех данных.

## 3. Что установлено по двум Google-отчётам

### dvizh.py

Результат — только лист `движение_заявок_за_MM.YYYY` и уведомление VK. Email в основном скрипте не используется; записей отчёта в БД и сохранения локального файла нет.

Показывает заявки принципала 12: дата счёта, клиент, продукт, номер, суммы поставщика/Савоира, менеджер и состояние. Несмотря на название, SQL не ограничен предыдущим месяцем: берётся текущий портфель, а прошлый месяц используется для отметки отгруженного акта. Это не исторический снимок всех состояний на конец месяца.

При возможном создании самостоятельной замены нельзя повторять: перепутанные подписи `cher`/`otk`, группировку по номеру, строковую сортировку даты, построчную допись Google при повторе. Старый try/except оборачивает `1 == 1` после основной работы и не обрабатывает её сбои.

### autootchet.py

Результат — только Google-лист `Оплаченные_<месяц>`. Письмо содержит период и ссылку без вложения; VK сообщает успех/ошибку. Скрипт выполняет SELECT, но не сохраняет отчёт в БД или XLSX. Найденный рядом `otchet.xlsx` имеет дату изменения 30.09.2020; текущий скрипт и его Google/DataModul-модули на него не ссылаются. Его наличие не означает второй действующий формат отчёта.

Содержание: поступления по трём расчётным счетам и кассам, направления услуг, неотгруженные оплаченные счета, частичные оплаты, детализации и нераспределённые платежи. Полная стоимость счёта в разделе частичных оплат намеренно не равна фактическому частичному поступлению — это нужно различать, а не молча менять значение столбца.

При возможной самостоятельной замене потребуется переработка:

- В основных банковских выборках нет явного отбора только входящих платежей, новые `payment_refund_links` не учитываются. Нельзя смешивать оборот поступлений, возвраты и остаток нераспределённого платежа.
- Денежные формулы используют текущий `tarif.price`, float, местами int; прошлые результаты меняются при изменении прайса и теряют копейки.
- Для наличных есть JOIN по одному счёту вместо конкретного движения, что может размножать строки при нескольких оплатах. В одной ветке в список ID строк записывается сумма вместо ID.
- У условий маркировки смешаны and/or без необходимых скобок; часть дат и границ периода берётся неверно.
- Уже сделанные ранее исправления пустого IN() и одной итоговой записи Google с overwrite присутствуют в источнике. Их не нужно выдавать за новые задачи.

**Вывод:** по ранее установленному правилу Google-only оба cron исключаются, а не переносятся механически. Если эти расчёты всё-таки нужны как самостоятельный результат, отдельным пунктом согласовать состав нового отчёта в аналитике/XLSX. Создание такой замены расширяет объём работ и не следует автоматически из отключения Google.

### Существующая аналитика не гарантирует полного совпадения

Можно переиспользовать `/reports/incoming`, `/reports/incoming-group`, `/reports/paid-bills` и существующие функции расчёта строк. Но не объявлять их готовой проверенной заменой старому большому отчёту без сравнения разделов.

Найденное конкретное расхождение: `s.voovi.ru-api/utils/func_payments.py`, `payment_r_s()` считает нераспределённый остаток только как `payment.sum − сумма kvobop`. Таблица `payment_refund_links` не используется. Полностью возвращённое поступление без kvobop может отображаться нераспределённым в отчёте входящих оплат, хотя список нераспределённых оплат в `analitic/payments/views.py` уже учитывает новые связи возвратов. Исправление этого чтения включить отдельным пунктом до расширения финансовой аналитики; сами движения оплаты и связи при этом не изменять.

## 4. Реализация переноса ежемесячного контроля

### Шаг 1. Зафиксировать только недостающие правила

Подтвердить исключение общего запрета нескольких тарифов; область обязательности суммы поставщика; необходимость исполнителя при нулевом количестве описей. Зафиксировать тестовую матрицу до изменения поведения. Уточнить, нужны ли самостоятельные замены двух Google-отчётов; по действующему требованию исходное предложение — не создавать их.

### Шаг 2. Переиспользовать установленный механизм

Добавить месячные правила в существующий API-проект и django-background-tasks worker. Переиспользовать `basic/reminders`: отдельные параметризованные выборки, чистое планирование письма, журнал `voovi_reminder_notifications`, SMTP вне транзакции и постоянный том результатов. Новые таблицы, Celery и второй планировщик не нужны.

Команда вида `python manage.py invoice_monthly_checks --month 2026-10 --dry-run`; без `--execute` не пишет в БД/файлы и не отправляет письма. Это предлагаемая команда, сейчас её нет. Идентификатор уведомления: вид проверки + rand + расчётный месяц + получатель; месяц можно хранить первым числом в существующем occurrence. У разных правил должны быть разные стабильные имена.

Отдельный результат запуска: период, начало/окончание, success/partial/error, количества проверенных и выявленных счетов, отправленных/пропущенных/неопределённых уведомлений, безопасная причина ошибки. Использовать текущую защиту от дублей и неизвестного результата SMTP, а не дублировать код отправки. Ошибка VK/SMTP не должна останавливать другие фоновые функции. Проверки ничего не блокируют в финансовых процессах.

### Шаг 3. Расписание и повтор

Сохранить 1-е число 07:00 МСК, проверять предыдущий календарный месяц. Не использовать интервал 30 дней. Период конкретного запуска должен быть зафиксирован, чтобы отложенное выполнение/повтор не начало проверять другой месяц. Регистрация без дублей, флаг по умолчанию выключен. После простоя обрабатывать только предназначенный периоду запуск, не рассылать автоматически все старые месяцы.

Повтор с тем же месяцем не отправляет уже подтверждённые письма. failed допускает управляемый повтор; unknown требует проверки фактической доставки. Эти ограничения показывать в результате и инструкции эксплуатации.

### Шаг 4. Тесты и приёмка

- Пустой месяц; январь/декабрь; отдельный rand при одинаковых ns; несколько тарифов/продуктов; нулевые/пустые/NULL суммы; счета без поставщика; поставщик не Контур; 0/положительное число описей; уже выбранный исполнитель.
- Зафиксировать ожидаемые отличия от старого отбора именно для согласованных правил, остальные выборки сравнить на одном снимке данных. Не требовать слепого равенства старому коду с известным ложным запретом.
- Запуск по умолчанию и dry-run не пишут и не отправляют. Реальные SMTP заменить в тестах; проверить отказ/обрыв, повтор, конкуренцию и сохранение суточных фоновых цепочек.
- Проверить MariaDB 5.5, очередь, общий worker, работу остальных расписаний и пользовательских страниц. Production preview только чтением. Проверочные реальные письма — только по явно согласованному получателю.

### Шаг 5. Переключение

Сохранить конкретные cron-строки, исходники, конфигурацию и время последнего запуска. Установить проверенную версию с выключенным месячным правилом. После успешного preview и тестов закомментировать только `opovesheniya_onlkas_nosum.py`, убедиться в отсутствии старого процесса, включить новое расписание. Проверить период, время, отсутствие дублей и первый реальный результат. Следующий ожидаемый ежемесячный запуск при переключении до декабря — 01.12.2026 за ноябрь.

Отдельно закомментировать пустой `ot_leter.php` и два Google-only задания после утверждения этого плана. Исходные команды сохранить в комментариях для быстрого возврата. Не удалять исходники и имеющиеся Google-таблицы в рамках переключения.

Откат: сначала выключить новое правило и дождаться окончания активного запуска, затем вернуть только соответствующую старую строку с учётом уже отправленных за период писем. Не включать два обработчика одновременно и не восстанавливать старый дамп поверх production.

## 5. Что должно остаться на хосте

| Задача | Расписание, МСК | Причина |
| --- | --- | --- |
| Вход и скачивание банковских файлов `bank_downloader.py mi/ai` | Ежедневно 06:00 / 06:10 | Ранее согласовано оставить браузер банка на хосте |
| Получение файлов из dockerbank | Ежедневно 06:30 | Подготовка файлов для подключённых к Django папок |
| `backup_all_db_s3.sh` | Ежедневно 00:20 | Резервное копирование всех БД и S3 независимо от Django |
| Restart `newfocus orderskb` | Ежедневно 03:00 | Другой проект |
| `docker system prune -f` | Воскресенье 00:00 | Обслуживание всего Docker-хоста, не бизнес-задача Django |
| ISPmanager, сертификаты, мониторинг, RAID, antivirus, sysstat, logrotate, системные timers | Разные | Обслуживание сервера и других сайтов |

**Отдельная серверная проблема:** получение файлов из dockerbank по-прежнему использует `docker cp ... ; docker exec ... rm ...`: очистка Downloads выполняется даже при неуспешном копировании. При отдельной доработке хоста удалять только подтверждённо скопированные и завершённые файлы. Это не переносить внутрь Django и не исправлять попутно в задаче отчётов без отдельного этапа.

Django не должен получать docker.sock или root-доступ для обслуживания этих задач.

## Итоговый порядок

1. Согласовать три условия месячного контроля.
2. Перенести нужные месячные уведомления, используя уже установленный журнал и worker; протестировать и переключить один cron.
3. Закомментировать пустой PHP-cron и два Google-only отчёта по принятому требованию.
4. Отдельно исправить расхождение чтения возвратов в существующем отчёте входящих оплат; при необходимости согласовать недостающие экраны/XLSX, без копирования старых ошибочных расчётов.
5. Отдельно доработать безопасное получение банковских файлов на хосте. Остальную инфраструктуру оставить на месте.
