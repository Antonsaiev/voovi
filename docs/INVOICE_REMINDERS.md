# Уведомления о заполнении счетов

Три проверки перенесены в существующий Django API/worker. Сначала устанавливаются с `REMINDERS_ENABLED=0`; без `--execute` команда не пишет в БД, не меняет контакты, не отправляет письма и не создаёт файлов состояния.

| Правило | Время, Europe/Moscow | Действие |
| --- | --- | --- |
| contacts | 06:40 ежедневно | Вчерашние активные неотгруженные счета отделов 10/12/22/24 без контакта; статус65 исключён. Единственная связь контакта заполняется во всех активных строках группы. При нескольких связях — письмо, при отсутствии связей — прежнее поведение без письма |
| address | 06:50 ежедневно | Вчерашние активные неотгруженные счета с тарифом road=1 и пустым фактическим адресом |
| booking | 09:30 ежедневно | Письмо за три дня до брони и в день звонка при отсутствии даты оплаты; прежнее совместное условие messageb/messagez сохранено |

Общие условия отказа/черновика/удаления для address/contacts сохранены. Для booking новые фильтры удаления/отказа не добавлялись: этот перенос не переосмысливает старые правила. Номера выводятся из schet.ns. Строки объединяются по rand, а не по потенциально повторяющемуся номеру. Разные счета с одинаковым номером не сливаются.

Ручной контакт не заменяется. Перед автозаполнением группа блокируется; единственная связь проверяется повторно и непосредственно в UPDATE (это защищает READ COMMITTED от добавления второй связи между SELECT и UPDATE). Получатель contacts/address — REMINDERS_EMAIL_TO, для менеджера26 — REMINDERS_MANAGER26_EMAIL, booking/call — REMINDERS_BOOKING_EMAIL_TO. Ссылки задаёт REMINDERS_VOOVI_URL; сохранён прежний voovi.ru, пока используются обе версии.

## Хранение и отправка

Новый пустой журнал создаётся вручную `basic/reminders/schema.sql`, без изменения определений финансовых таблиц. Таблица voovi_reminder_notifications содержит event_hash, rule, schet_rand, occurrence, recipient, payload, status, attempts, created_at, updated_at, sent_at, last_error и id. Уникальный SHA256 события строится из правила, rand, даты события и получателя. Индексы совместимы с MariaDB5.5; длинный rand не входит в уникальный составной индекс.

Состояния: pending → sending → sent/failed/unknown. SMTP вне транзакции. Успех означает принятие DATA почтовым сервером, не гарантирует попадание во входящие. Ошибка соединения/авторизации/оболочки до DATA — безопасный повтор (failed в журнале); при недоступности SMTP оставшиеся письма сохраняются failed без повторения соединения для каждого счёта. При потере подтверждения после начала DATA — unknown, автоматической повторной отправки нет. Отказ адреса/данных сервера — failed. Сбой quit после принятия DATA не превращает успех в отказ. Оставшийся после аварии sending переводится в unknown.

Сбой одного письма не останавливает цикл. Суточная цепочка сохраняется и при partial/error: подробный результат остаётся в `<rule>.result.json` в томе voovi_reminders, ошибка видна в журнале worker. Отдельные ошибки отправки требуют проверки и при необходимости повторного запуска команды с тем же --date. Для unknown сначала требуется проверить фактическую доставку; повтор без этой проверки запрещён.

## Команды

```
python manage.py invoice_reminders contacts --dry-run --date 2026-11-03
python manage.py invoice_reminders address --dry-run --date 2026-11-03 --details
python manage.py invoice_reminders booking --dry-run --date 2026-11-03
```

`--date` — дата запуска проверки: contacts/address проверяют предыдущий день. `--details` в dry-run показывает подготовленные письма. Для реального выполнения добавить `--execute` вместо `--dry-run`. Это меняет контакты и отправляет внутренние уведомления; выполнять осознанно. Повтор не отправляет уже подтверждённые письма повторно.

## Переключение production

1. Сохранить API/worker, ENV/compose, crontab пользователей voovi/toha и журналы. Добавить пустой журнал уведомлений.
2. Установить проверенные образы с флагом0. Проверить preview сегодняшнего/завтрашнего дня, SMTP-авторизацию без отправки и отсутствие записей/изменений контактов.
3. После успеха закомментировать ровно три старые строки: voovi/brzvleter.php, toha/opovesheniya_no_kontakt.py, toha/opovesheniya.py. Убедиться, что процессов этих скриптов нет.
4. Установить REMINDERS_ENABLED=1 и перезапустить общий worker. Регистрация добавит по одной суточной задаче contacts/address/booking и не изменит остальные расписания.
5. Проверить будущие часы запусков, отсутствие дублей, состояния контейнеров и доступность сайтов. Первые реальные уведомления приходятся на следующий плановый запуск; smoke не отправляет тестовые письма клиентам или сотрудникам.

Месячные проверки/отчёты, банковские cron, системное обслуживание и старая PHP-версия не меняются. Для отката сначала выключить Django-задачи и дождаться завершения worker, затем вернуть только три сохранённые строки с учётом уже отправленных писем. Нельзя включать два обработчика одновременно или восстанавливать старый дамп поверх текущих данных.
