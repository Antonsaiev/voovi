# Развитие Voovi на текущей БД с последующим переходом на PostgreSQL

Дата: 16.10.2026. Это разбор альтернативы с одной рабочей БД на переходном этапе. Изменения приложения, DDL и перенос данных не выполнялись.

**Статус:** пользователь выбрал этот путь модернизации: постепенное развитие текущего продукта, React и улучшение серверной логики/структуры на существующей БД, затем подготовленный переход на PostgreSQL. Конкретные этапы и схемы таблиц требуют дальнейшего проектирования.

## 1. Вывод

**Такой путь реалистичен и позволяет избежать длительной синхронизации двух рабочих БД.** Можно развивать текущий продукт, заменять интерфейсы на React и постепенно улучшать серверную архитектуру и структуру данных в MariaDB. Затем перенести уже подготовленную модель в PostgreSQL.

Условие: развитие означает не только замену HTML на React, но и перенос операций в проверяемый API, централизацию правил и устранение прямых обращений к таблицам из старых страниц, задач и интеграций. Миграция PostgreSQL остаётся отдельным проектом, но перестаёт требовать переписывания всей бизнес-логики одновременно.

Это отдельный допустимый вариант к [предыдущему сравнению](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/docs/MODERNIZATION_DECISION_2026-10-16.md). Его отличие от «только новые экраны поверх старой схемы»: серверный слой и схема действительно меняются, а PostgreSQL регулярно проверяется как будущая цель.

## 2. Разделить три изменения

| Изменение | Можно выполнять отдельно? | Зависимость |
|---|---|---|
| Старые экраны → React | Да, по разделам | Стабильный API и серверная проверка прав |
| Старая модель данных → нормальная структура | Да, по предметным модулям, ещё в MariaDB | Учёт всех старых читателей/писателей, миграция данных и переключение |
| MariaDB → PostgreSQL | Да, после подготовки | Переносимые запросы, совместимые типы, испытанный импорт, сверка и окно переключения |

Смена СУБД сама по себе не разделит таблицу schet на шапку и позиции. Нормальная структура, FK, точные деньги и транзакции доступны и до PostgreSQL. React не должен зависеть от физического вида таблиц.

Цепочка развития:

```text
Старые экраны + старые обработчики → MariaDB
                         ↓
React и старые экраны → единый API/бизнес-операции → MariaDB
                         ↓
React и оставшиеся экраны → API → улучшенные таблицы MariaDB
                         ↓
Тот же контракт React/API → подготовленный backend → PostgreSQL
```

На последнем шаге меняются конфигурация, физическое хранилище, миграционный импорт и оставшиеся реализации запросов; frontend должен продолжать работать по прежнему контракту. Это цель проектирования, не обещание, что достаточно заменить одну строку ENGINE.

## 3. Сначала — серверная граница

Для переносимого модуля выделяются операции с предметным смыслом: создать счёт, изменить состав, распределить платёж, сделать возврат, сформировать документ. Их входы и ответы не повторяют все колонки schet и не разрешают клиенту менять любое поле модели.

Операция отвечает за права, валидацию, расчёт, транзакцию и журнал. Доступ к данным находится в одном понятном месте — Django ORM и небольших явно выделенных запросах/адаптерах. Отдельный универсальный слой абстракций поверх каждого вызова ORM не обязателен; важнее не размножать SQL и правила по views и шаблонам.

Первоначально эта операция работает со старой схемой. После улучшения таблиц меняется её работа с данными; контракт React сохраняется. Старые PHP-экраны при необходимости могут вызывать тот же API. Переписывать каждый экран до переноса БД необязательно, но все живые пути чтения/записи должны поддерживать новую цель либо быть отключены.

Не достаточно перевести только новый экран создания: старый редактор, getstatusschet, импорт bills и фоновая синхронизация av всё ещё могут менять тот же счёт. Для каждого модуля нужен полный список потребителей и писателей.

## 4. Как улучшать структуру, оставаясь в одной БД

Порядок «добавить → заполнить → проверить → переключить → удалить старое»:

1. Добавить новые таблицы/поля совместимо со старым кодом; не переименовывать используемые колонки преждевременно.
2. Создать повторяемое преобразование старых записей и соответствия ID. Старая модель пока остаётся источником, новая копия используется для проверки.
3. Сверить суммы, связи, документы, историю и отчёты. Проверить обновления, случившиеся после начальной загрузки.
4. Ограничить старые изменения модуля на время конечной сверки; переключить все его команды на новые таблицы и единый серверный обработчик.
5. Старым читателям предоставить временный совместимый ответ/представление, где это выполнимо. Обратное представление старой структуры не всегда восстанавливается однозначно; это проверяется отдельно.
6. После отключения зависимостей архивировать/удалить старые структуры в отдельной миграции.

Не оставлять две независимо редактируемые модели счёта даже в одной БД. Одна база упрощает транзакцию, но не разрешает логический конфликт владельцев.

### Пример: schet

Вместо добавления всё новых полей в 111-колоночную schet создать, например:

- invoice — одна шапка с номером, клиентом, датами и общими состояниями;
- invoice_item — позиции с версией тарифа, количеством, ценой, скидкой и итогом;
- invoice_status_history — история;
- invoice_external_link — связи с внешними счетами;
- document — документы и версии;
- legacy_invoice_mapping / legacy_item_mapping — связи старых rand, ns и ID позиций с новыми сущностями.

Названия условные. Связанные оплаты, распределения и складские записи учитываются в преобразовании; нельзя просто перенести шапку и забыть jurnalskzi.schet_id или kvobop.schet. Номер сохраняется как исторический реквизит; неоднозначности старых ns нельзя разрешать произвольной склейкой.

Состав внешнего счёта Контура, его пакеты и данные для АВ можно сразу хранить в нормальных новых таблицах **этой же MariaDB**. Не требуется вначале сжимать их до номера/ссылки, чтобы позднее расширить на PostgreSQL. [Целевая модель внешнего счёта](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/docs/KONTUR_BILLING_DOMAIN_2026-10-16.md).

## 5. Текущее окружение тоже нужно подготовить

«Оставить существующую БД» здесь означает сохранить данные и временно СУБД, но не навсегда оставить MariaDB 10.2, PHP 5.6 и Django 3.2.

Например, Django 5.2 поддерживает MariaDB от 10.5. Это нижняя граница совместимости, а не рекомендация поставить именно 10.5. Нужно подобрать поддерживаемую ветку MariaDB и совместимые серверные зависимости, проверить обновление на копии, SQL mode, кодировки, драйверы, аутентификацию подключения и старый PHP. [Официальные требования Django к БД](https://docs.djangoproject.com/en/5.2/ref/databases/#mariadb-notes).

Новые таблицы проектировать транзакционными. Перевод старых критичных MyISAM-таблиц в InnoDB — отдельное проверяемое изменение: важны нумерация, блокировки, индексы, DDL и работа старых запросов. Наличие новых InnoDB-таблиц рядом с MyISAM не делает всю смешанную операцию атомарной.

У существующих Django-моделей managed=False. Для новых таблиц сразу нужен управляемый цикл миграций. Для старых — сверка фактического DDL и согласованная базовая история схемы, затем управляемые изменения. Простое массовое managed=True не является миграцией или проверкой схемы. inspectdb даёт начальные модели и не гарантирует готовую предметную модель. [Работа Django с существующей БД](https://docs.djangoproject.com/en/5.2/howto/legacy-databases/).

## 6. Что заранее исправлять ради PostgreSQL

| Особенность текущего кода | Подготовка |
|---|---|
| SQL с подстановкой строк | Параметры запросов и ORM; это также вопрос безопасности |
| Выбор несгруппированных полей вместе с GROUP BY | Явно определить нужную строку/агрегат; например последнюю версию, а не случайные поля группы |
| DATE_FORMAT, STR_TO_DATE, CAST AS UNSIGNED, REGEXP | Заменить на переносимый ORM/прикладное преобразование либо небольшой запрос для каждого backend |
| LOCK TABLES и MAX+1 при нумерации | Явный алгоритм конкурентной выдачи номеров, уникальность и тесты; не менять исторические номера |
| Строковые деньги и float | Decimal/DECIMAL, явные единицы и округления |
| Нулевые/невалидные даты, текстовое время | Очистка с сохранением оригинала; неизвестное не превращать в выдуманную дату |
| Строковые флаги и отсутствие FK | Типизированные состояния, очистка осиротевших ссылок, затем ограничения |
| Неявные преобразования MySQL и collation | Проверить сравнение строк/чисел, регистр, сортировку, поиск и уникальность |
| ID, ключи и исторические версии | Сохранить соответствия; после импорта настроить последовательности и проверить ссылки |

Примеры найдены в [SqlQuerySELECTgeneral.py](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/s.voovi.ru-api/utils/SqlQuerySELECTgeneral.py:4), [SqlQuerySELECTsampling.py](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/s.voovi.ru-api/utils/SqlQuerySELECTsampling.py:244) и [schet_identity.php](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/voovi.ru/schet_identity.php:84). Полагаться только на ORM недостаточно: нужны интеграционные проверки реальных денежных операций и запросов на обеих СУБД.

## 7. Как в итоге переключить базу

PostgreSQL поднимается заранее как проверочная цель, а не в последний день. По мере переноса модулей туда регулярно загружается обезличенный/разрешённый тестовый набор и проверяются новая схема, запросы, расчёты, права и документы. Единственной рабочей БД пока остаётся MariaDB; постоянная двунаправленная синхронизация не нужна.

Когда все активные обработчики готовы:

1. Создать целевую схему PostgreSQL и выполнить репетицию преобразования/переноса.
2. Измерить длительность, сверить записи, итоги, распределения, остатки, связи и документы.
3. Получить согласованный начальный снимок; для смешанных MyISAM/InnoDB нельзя обещать его согласованность только опцией транзакционного дампа.
4. На конечном переключении остановить старые записи и соответствующие задачи/импорты/внешние исполнители, перенести последние изменения и повторить сверку.
5. Переключить backend и workers на PostgreSQL, открыть запись и наблюдать.
6. MariaDB оставить защищённым архивом для проверки на согласованный срок, затем завершить вывод из эксплуатации.

Если полный перенос укладывается в допустимое окно, достаточно управляемой остановки записи. Если нет — нужен отдельно проверенный односторонний захват изменений до конечного переключения. Импортировать только новые id недостаточно: нужны UPDATE, DELETE, связи и порядок изменений.

После появления новых операций в PostgreSQL простое возвращение на старую копию MariaDB теряет эти операции. Граница отката и способ сохранения новых данных определяются до переключения. Реальные счета, документы и кассовые действия не выполняются дважды ради сравнения.

## 8. Оценка этого варианта для Voovi

Плюсы: одна рабочая БД, меньше временной синхронизации, улучшения доступны постепенно, схему можно нормализовать до смены СУБД. Это разумный выбор, если приоритет — непрерывное развитие текущего продукта и ограниченная команда.

Цена: временно надо поддерживать совместимость со старым кодом, обновить окружение, перенести многочисленные прямые обращения к БД и испытать второй backend. PostgreSQL нельзя откладывать без проверок, иначе специфичный SQL снова накопится.

Успех измеряется не числом React-страниц, а сокращением прямых SQL-путей, единством бизнес-операций, качеством новой схемы и прохождением проверок на PostgreSQL. Если очередной новый экран продолжает напрямую зависеть от schet из 111 полей и обновлять её как раньше, будущая миграция почти не приближается.
