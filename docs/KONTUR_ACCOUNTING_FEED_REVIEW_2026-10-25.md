## 2. Что приходит помимо номера

Лента содержит шапку, участников, партнёра, продавца, состояния и даты, Tariffs, Services и OrderPackages. Для нашего тарифа получены две расчётные строки:

| Строка | Amount в этой записи | VatRate |
|---|---:|---:|
| Право использования Контур.ОФД на 14 дней | 119,00 | 0% |
| Обработка фискальных данных на 14 дней | 51,00 | 22% |

Для этого ответа: 119 + 51 + 51 × 22% = 181,22. Это объясняет отличие 170,00 из пакета/предложения от итога счёта. Проверка выполнена точными десятичными числами. Нельзя распространять эту формулу и смысл сумм без проверки на все товары, количества и алгоритмы: ответ содержит также PricingVatAlgorithm и FromCountAlgorithm.

Сохранять нужно весь ответ. Для будущего АВ полезны не только tariffId, но и расчётные строки, ставки/суммы, возвраты, роли/участники, сценарии и связи прежних/новых пакетов. Для нашей записи некоторые роли менеджеров отсутствуют; их нельзя выдумать по автору Voovi. Правил и фактических начислений АВ этот ответ не подтверждает.

## 3. Как устроен скрипт

### Источник новостей

`funcBilly.py:5–11` формирует `/product/bills?inclusiveStartTicks=...&count=100`. `ReqSchet` на строках 45–57 обращается к `https://api-accounting-billing.kontur.ru` с x-Auth-CustomToken. В архиве для этого рабочего источника используется тот же токен, который пользователь передал для Orders API.

### Текущая обработка

`schetmain.py` читает LastTicks.yaml, получает пачки, проверяет IsVisibleToPartner и обрабатывает State. Счёт Voovi ищется функцией AllInfoSchet по **номеру** новости. Далее выполняются обновление оплаты/даты, комментарии, уведомления и работа со сроками. Для нового Bill, у которого номер ещё не записан в schet, текущий поиск не построит связь сам.

### Сохранение учётного счёта

В `SqlQuery.py` уже есть:

- `PoiskBillid(BillId, bd)` — поиск в локальной bills именно по GUID, возврат Number/Amount/State и прочих полей.
- `InsertBills(info, bd)` — запись шапки через INSERT ... ON DUPLICATE KEY UPDATE.
- Запись Tariffs в bills_tariffs.
- Запись Services в bills_tariffs_services.
- Запись OrderPackages в bills_order_packages.

Это важное дополнение к прежнему плану: **не нужно заранее проектировать дубли этих таблиц**, прежде чем проверить существующий импорт, фактический DDL и полноту хранения.

В `schetmain.py:75–77` сохранение bills закомментировано. Причём показанный закомментированный вызов не передаёт bd; просто убрать символ комментария недостаточно. Рабочий вызов `InsertBills(i, bd)` есть в `updating_the_payment_date.py:32`. Этот файл начинает выборку с фиксированного начала 2025 года и меняет даты оплаты, поэтому его нельзя запускать ради проверки одного номера. Какой файл реально запускается по cron и с какой периодичностью, из архива не установлено.

## 4. Точная доработка без перестройки схемы счёта

Перед внешним POST сохранить связь:

```text
BillId Контура → существующий schet.rand
```

В обработчике новостей добавить узкую ветку для таких связей **до поиска по Number и до решения «счёт не найден, отправить уведомление»**:

1. Прочитать и надёжно сохранить запись ленты/её версию.
2. Найти ожидающую операцию по BillId; проверить среду, партнёра, плательщика, ожидаемые пакеты и правильную локальную группу.
3. Сохранить шапку, тарифы, услуги и пакеты существующим совместимым путём; сохранить исходный JSON для истории и ещё не разобранных полей.
4. Если номер/сумма получены, опубликовать настоящие Number и Amount в nomerschetks и priceks нужной группы. Проверить все её активные строки, ручные изменения и конфликты.
5. Для этой API-ветки продолжать работу с **точным rand**, не искать группу повторно только по номеру: одинаковый номер может встречаться в разных группах. Существующий поиск по номеру остаётся для записей без новой связи.
6. Отдельно применить согласованные правила состояния оплаты/доставки. Получение реквизитов не должно автоматически запускать лишние письма/повторные комментарии или перепроводить начисления.
7. Отметить получение реквизитов у операции. При сбое повторить обработку/публикацию, не выставление Bill.

Для нашего проверочного Bill внутренняя группа schet этим тестом не создавалась. Поэтому номер и сумма зафиксированы локально в результатах проверки; привязывать их к произвольному счёту Voovi по одному ИНН нельзя.

Приоритет для получения: сначала проверить уже загруженную bills по BillId; затем дождаться штатного обновления/запустить разрешённую точечную сверку с отдельным курсором. Изменять глобальный LastTicks назад или вперёд ради одного ожидающего Bill нельзя. Не предполагаем наличие прямого GET по BillId в accounting API: подтверждена фильтрация полученной ленты на нашей стороне.

## 5. Что проверить в цикле и сохранении перед внедрением

1. **Одна запись — допустимая пачка.** На строках 53–54 schetmain.py проверка len(info) < 2 прерывает цикл до обработки. Наш ответ содержит ровно один реальный Bill. Его нельзя объявлять пустой пачкой. При inclusiveStartTicks одиночная запись также может оказаться повтором границы — решение должно опираться на обработанную версию, а не длину.
2. **Курсор и сбои.** info[-1] после пустой пачки даёт ошибку. Переход по TimeStamp, повтор границы и сохранение курсора требуют обработки пустого ответа, повторов, одинаковых меток и отсутствия прогресса. Не использовать слепое «+1»: можно пропустить записи с той же меткой. Продвигать курсор после надёжного сохранения/обработки либо явного сохранения отложенной записи.
3. **Перезапуск и публикация.** Если курсор уже прошёл Bill до появления связи с rand, запись из bills/сохранённой истории всё равно должна завершить реквизиты. Нельзя ждать обязательной новой новости по тому же счёту.
4. **Уникальность.** ON DUPLICATE KEY UPDATE защищает от дубля только при подходящих реальных уникальных индексах. Проверить индексы BillId/BillTariffId/BillTariffRowId/Id пакета, существующие дубли и возможность повторных версий.
5. **Точность и формат.** Данные сумм читать/сохранять через Decimal и параметры SQL. int-преобразования суммы и ноль при ошибке в старой статистике не использовать для публикации реквизитов. Проверить фактический тип bills.Amount и путь через Django, где модель объявляет decimal_places=0.
6. **Версия и полнота.** Устаревшая новость не должна затереть более свежие реквизиты; изменения состава и пропавшие строки требуют правил согласования. Текущая запись через upsert сама по себе не сохраняет историю и не удаляет исчезнувшие дочерние элементы.
7. **Побочные действия.** Оплата, сроки, документы, уведомления и статистика должны переживать повтор одной версии без повторного действия. Сохранение реквизитов работает и для неоплаченного Bill, а не только внутри State=2.

Это конкретные условия совместимости расширения, а не предложение переписать весь скрипт. Реальные расписание/версия на сервере и остальные внешние задания всё ещё требуют сверки.

## 6. Изменение архитектурного плана

Цепочка теперь подтверждена чтением API:

```text
Voovi создаёт Bill через Orders API и сохраняет BillId ↔ rand
       ↓
Учётная лента accounting API возвращает BillId + Number + Amount + состав
       ↓
Существующее хранилище bills / тарифы / услуги / пакеты
       ↓
Сопоставление по BillId → заполнение привычных полей schet
       ↓
Действующие процессы Voovi по проверенным правилам
```

Получение номера больше не является неподтверждённой возможностью или обязательной заявкой на новые права Orders API. Остаются проверки надёжности импорта, задержки, прав/видимости других счетов, точности и безопасного обновления существующих групп. Пользовательская ссылка, PDF, правила АВ и вся полнота других продуктов из одного ответа не следуют.

Исследован предоставленный пользователем архив внешних скриптов; секреты в этот документ не переносились.
