# Изучение интерфейса Биллинга Контура и перенос удобства в Voovi

25.10.2026. Исследован рабочий интерфейс `billy-partners.kontur.ru` в авторизованной сессии для разрешённого пользователем ИП 261809572092. Выводы сопоставлены с текущим кодом Voovi и ранее проверенными схемами публичного API. Дополнительно выполнены только расчёты через API. На этапе исследования код приложения и схема БД не менялись; новые реальные счета не создавались, оплат, отправки сообщений и документов не выполняли.

**Последующая реализация:** после указания пользователя применить выводы в код перенесены поиск тарифов, готовые карточки, группы, начальные значения, восстановление состава, дополнения с расчётной ценой, ошибки у полей, закреплённый итог и переход в Биллинг. Подробнее — [реализованная версия](KONTUR_INTEGRATION.md). Полный набор возможностей Биллинга не объявляется доступным публичному API.

## Что проверено непосредственно

- Карточка клиента → «Выставить счет» → выбор продукта.
- КЭП для ЕГАИС: добавление тарифа, автоматическое заполнение срока, выбор 12 месяцев, включение дополнения «Сопровождение сертификата (3 раза)», пересчёт.
- Вкладка контактов: автоматическое заполнение данных уведомлений, получатель из контекста клиента.
- Добавление совместимого продукта «ПО и носители» в тот же состав; КриптоПро CSP 5.0 на год; изменение количества с 1 до 2.
- Отдельная форма ОФД: каталог, группировка тарифов, выбор «Контур.ОФД-13», список акций, секция получателя.
- Карточка **существующего**, ранее созданного счёта `w2693175477`: номер, состояние, товары, детализация услуг и НДС, доступные переходы к документам.

Финальную кнопку создания нового счёта в Биллинге не нажимали. Послесозданное представление изучено на уже существующем счёте. Раздел документов завершился ошибкой `timeout exceeded`; фактическое скачивание документов в этом исследовании не проверено. Обнаруженные кнопки печати, отправки по почте и ЭДО не доказывают доступность таких операций нашему API-токену.

## Как устроен рабочий процесс

1. Клиент выбран до входа в форму. В оформлении показан плательщик, повторно искать его не нужно. Лицевой счёт в проверенных сценариях вручную не выбирается.
2. Продукт представлен компактной вкладкой/меткой. В совместимых случаях есть «Добавить продукт».
3. Основной элемент добавления — поиск «Введите название тарифа». Не создаётся промежуточная пустая позиция, для которой затем ещё нужен выбор тарифа.
4. В списке тарифов видны названия и доступные цены; есть группы «Основные тарифы», «Рабочие места», «Прочие услуги». Для параметризуемого тарифа цена может появляться после добавления.
5. Выбор сразу добавляет готовую строку: название, количество, цена за единицу, сумма, удаление. Доступные настройки находятся внутри этой строки. Для КЭП ЕГАИС уже было выбрано 6 месяцев; затем срок менялся на 12.
6. Дополнения находятся внутри тарифа, в раскрываемом разделе. Для сопровождения сразу видна собственная цена. Включение дополнения обновляет итог.
7. Для нескольких продуктов есть итог текущего продукта и общий итог всего счёта. При изменениях кнопка выставления временно отключается, затем становится доступной.
8. Контакты и получатели вынесены отдельно и во многом заполняются автоматически. В проверенной форме ОФД был получатель из карточки клиента и возможность добавить контакт для входа в продукт.
9. Создание запускается одной кнопкой. В проверенных формах отдельного подтверждающего чекбокса не было.
10. В существующем счёте видны номер и состояние; краткий список товаров раскрывается в детальный состав услуг, цен и налогов.

Из совпадения одного выбранного состава не следует, что проверены все тарифы, скидки, налоги и сценарии.

**Цена из offers не должна автоматически считаться окончательной ценой строки.** Для выбранного срока и состава итог нужно получать через calculate. Нельзя для всех продуктов прибавлять одинаковый процент НДС.

На существующем тестовом счёте один тариф разделён на право использования программы — 119,00 ₽ — и услугу обработки данных — 62,22 ₽, включая НДС 11,22 ₽. Общий итог — 181,22 ₽. В интерфейсе он показан как «Оплачено безвозмездно», без дат поступления денег: это отдельный смысл состояния, который нельзя трактовать как денежную оплату клиента.

## Существенные ограничения самого Биллинга

Добавление нескольких продуктов не универсально даже в собственном интерфейсе Контура. В счёт с КЭП ЕГАИС получилось добавить «ПО и носители». ОФД, Экстерн, Маркет и другие продукты были показаны как недоступные для добавления в этот состав. Причину совместимости по одному интерфейсу не устанавливаем.

В ОФД виден отдельный выбор акций («месяц», «два месяца», «квартал» в подарок). В КЭП есть количество и поле скидки; доступность редактирования не нужно выводить только из наличия подписи поля. В Биллинге также представлены промокод и DV-агент. Ни один из этих элементов не следует автоматически включать в Voovi как уже поддержанный публичным API.

## Что можно перенести на нынешних возможностях

| Удобство Биллинга | Опора в нашем API/коде | Предложение для Voovi |
| --- | --- | --- |
| Поиск тарифа с немедленным добавлением | `scale` + доступные `offers` | Заменить пустую позицию и её селект на поиск «Найти и добавить тариф». Выбор добавляет заполненную карточку |
| Группы тарифов | Метаданные тарифной сетки, включая `TariffType` | Разделять основные тарифы, услуги и рабочие места, когда тип определён. Модификаторы показывать внутри связанных тарифов |
| Подстановка настроек | Свойства, допустимые значения, `initialDuration` | Восстанавливать сохранённый актуальный выбор. Для нового тарифа брать явно определённое API начальное значение или единственное допустимое; не выбирать случайное значение многозначного обязательного свойства |
| Понятные настройки прямо в строке | `name`, `title`, единицы и ограничения свойств | «Длительность, мес.», подписи вариантов, проверка обязательности и диапазона рядом с полем |
| Дополнения с ценой | Связи модификаторов, offers, calculate | Раздел «Дополнения к тарифу» с названием, пояснением и достоверной ценой. Итог выбранного состава — из calculate |
| Автоматический пересчёт | Уже реализован | Сохранить. Объединять быстрые изменения, ограничить частоту расчёта; не брать готовность из устаревшего ответа |
| Один финальный шаг | Уже реализован | Кнопка «Выставить счёт Контур» активна после успешного актуального расчёта. Без чекбокса и промежуточного экрана |
| Автоматический клиент и ЛС | Уже реализовано | Сохранить. При неоднозначности — сообщение о привязке, а не случайный выбор первого ЛС |
| Краткая и подробная информация после создания | Структурированные данные актуального состава и `bills` | Кратко показать номер/ожидание, сумму, состояние и состав; услуги и налоги раскрывать по запросу |
| Переход в исходную систему | Наблюдаемый маршрут карточки по BillId | Отдельная ссылка «Открыть в Биллинге». Не записывать её в legacy `schet.url` как будто это прямая ссылка на PDF |

Цены в поиске и у ещё не выбранных дополнений требуют аккуратного источника. Значения offers нельзя подписать как окончательные суммы с налогами без проверки. Не нужно вычислять их единым коэффициентом или массово рассчитывать весь каталог как одну покупку: скидки и состав могут изменить результат. Для первого улучшения достаточно надёжного итога после добавления и настройки тарифа.

## Что требует отдельной проверки

- **Количество больше одного.** В calculate есть quantity, а в текущем публичном теле создания Voovi генерирует отдельный GUID пакета для каждого тарифа и не передаёт quantity. У нас сейчас техническое ограничение «один пакет на позицию». Это ограничение реализации, а не доказанный запрет публичного API на опт. Прежде чем показывать полноценный счётчик, проверить корректное представление нескольких пакетов в создании и последующих учётных данных.
- **Несколько продуктов.** Публичная схема создания содержит productId у каждой позиции, поэтому однопродуктовость нынешнего Voovi нельзя выдавать за универсальное ограничение API. Однако нужны проверка совместимости, раздельный контекст ЛС и корректный расчёт. Нельзя обещать произвольное объединение и комплектные скидки простым суммированием отдельных расчётов.
- **Промокоды, акции и ручные скидки.** Часть полей есть в схемах, но сквозной путь calculate → public create → биллинг нашим модулем не проверен. До проверки соответствующие элементы не показываем как работающие.
- **Иной получатель, регистрация ЛС, коды активации, смена и докупка.** В нашей первой версии проверен путь Create с существующим ЛС и получателем-плательщиком. Не нужно имитировать другие варианты только потому, что Биллинг показывает соответствующие тарифы.
- **Мгновенный номер, документы, письма и ЭДО.** Создание у нас подтверждается по BillId, номер и итог дополняются из действующего импорта `bills`. Ранее вспомогательные методы Orders возвращали 401 с нашим токеном; новых прав этот просмотр UI не подтверждает. Не используем внутренние запросы веб-интерфейса как недокументированный backend Voovi.

## Предлагаемый следующий вариант формы

Сохранить согласованный порядок: сначала обычный счёт Voovi, затем отдельная форма Контура из его карточки.

```text
Клиент и счёт Voovi уже определены
Продукт: [поиск и выбор]

Состав счёта
[ + Найти и добавить тариф... ]

Название тарифа                           Расчётная сумма  Удалить
Длительность: [значение из API]
Дополнения к тарифу: [доступные варианты]

[ + Найти и добавить ещё тариф... ]

Итого с налогами / без НДС / НДС           [Выставить счёт Контур]
```

Итог остаётся внутри блока состава — отдельную третью панель не возвращаем. Для длинного состава можно закрепить нижнюю строку итога и кнопки. Историю и подтверждающий чекбокс не возвращаем; хранится только актуальный состав. Не вводим соответствия направлений и продуктов, новые роли, предварительный справочник тарифов или новый курсор новостей.

Очередность: (1) поиск и добавление готовой карточки тарифа; (2) восстановление текущего состава и безопасные начальные значения; (3) ясные группы/дополнения и цены; (4) понятные ошибки рядом с параметром и состояние пересчёта; (5) компактный результат с переходом в Биллинг. Количество, многопродуктовый состав и акции расширяются после проверки контракта и полномочий API.
