# Интеграция счетов Контура

Этот документ описывает текущий код Voovi. Схема и обновление БД — в [описании единого хранилища](KONTUR_UNIFIED_STORAGE_2026-10-26.md), запуск фоновых задач — в [инструкции автоматизации](../s.voovi.ru-api/basic/kontur_automation/README.md), сценарии тестирования — в [матрице продуктов](KONTUR_PRODUCT_TEST_MATRIX_2026-10-25.md).

## Выставление и присоединение

1. Менеджер сначала сохраняет обычный счёт Voovi. Его номер, `rand`, строки и прежние связи формируются существующим механизмом.
2. Из карточки открывается `kontur_invoice.php?rand=…`. Клиент определяется по группе `schet`; повторный ручной выбор плательщика и лицевого счёта не требуется. Проверяются действующая авторизация Voovi и доступ ко всем направлениям группы.
3. Менеджер выбирает продукты и находит тарифы через поиск. Форма получает предложения и параметры от Контура; доступные продукты показываются раньше недоступных. При отсутствии лицевого счёта поддерживаемого продукта форма автоматически запускает его подготовку отдельным POST. GET-запросы ничего не регистрируют; неоднозначная связь останавливает операцию.
4. В составе доступны свойства, дополнения, количество и открытая цена, если их разрешает предложение. Изменения запускают автоматический расчёт; продукты рассчитываются отдельно, затем объединяются в один запрос создания. Каждая оплачиваемая единица получает собственный GUID пакета. Неподдерживаемые комбинации могут быть отклонены Контуром при создании.
5. Перед единственной отправкой сервер сохраняет точный запрос, GUID документа и пакетов, ID менеджера Voovi и состояние `sending`. При неопределённом ответе повторное выставление блокируется. После явного отказа можно изменить состав и получить новый расчёт; устаревший расчёт не отправляется.
6. При подтверждённом создании сразу сохраняется ссылка на Биллинг по `BillId`. Номер, учётная сумма, услуги, пакеты и оплата дополняются из новостей задачей `schetmain`. В карточке Voovi состав раскрывается таблицей с группировкой по продуктам и итогом.
7. Вместо создания можно найти существующий счёт по номеру, ИНН или плательщику в локальной `bills` и присоединить его. При несовпадении реквизитов показывается предупреждение; явное подтверждение разрешает привязку. Если номер ещё не найден, он сохраняется в `schet.nomerschetks`, а связь — с `BillId=NULL`. Сервер повторяет поиск при сохранении, поэтому появившийся после открытия формы документ присоединяется сразу. Иначе связь завершает следующая подходящая новость.

Документ Контура хранится в одном экземпляре по уникальному `BillId`; к нему могут относиться несколько групп Voovi. Введённый ожидающий номер не дублируется в таблице связей. Существующие суммы `schet.priceks`, включая ноль, не заменяются общим итогом Контура. Лента дополняет отсутствующие данные общего документа, сохраняя ранее заполненный состав; оплата и видимость обновляются отдельно.

Поля `schet.nomerschetks`, `url` и `priceks` могут относиться к другому поставщику. Если локальный документ Контура не найден, обычное сохранение этих полей не создаёт ожидающую связь, ошибку или финансовое ограничение. Явная ожидающая связь создаётся только отдельным действием присоединения Контура. Наличие такой связи и состояние Контура сами по себе не являются условием отгрузки или начисления ЗП; прежние правила этих действий сохраняются.

Старый PHP может по-прежнему сохранять только `schet.nomerschetks` и `url`. Общий `LegacyLinkService` разрешает такие записи при работе нового API и обработке новостей. В начале `schetmain` он также сверяет изменившиеся и ожидающие связи без новых новостей. При открытии карточки сохранённая связь или старый номер без связи однократно сверяются через локальный `status` API: найденный документ получает состав, неизвестный остаётся обычным номером поставщика без предупреждения. Внешний Контур при этом не опрашивается. До ответа старый состав не показывается. Смена только номера или только ссылки убирает прежний состав, если новый документ не удалось однозначно определить.

Если Контур добавлен к уже оплаченному/отгруженному Voovi, старые платежи и отметки не стираются. Подтверждённая оплата Контура показывается по его документу, а не выводится из оплаты Савоира. Явное снятие прежней отгрузки остаётся доступным по существующим правилам периода.

Подтверждённое удаление счёта в Контуре снимает его связи с Voovi. Сохранённый документ со статусом `deleted` защищает от восстановления связи запоздавшей новостью. Конфликт ручных данных или отметки оплаты останавливает автоматическую отвязку для разбора.

## Код и API

| Область | Файлы |
| --- | --- |
| Форма, авторизация и серверный прокси | `voovi.ru/kontur_invoice.php`, `kontur_common.php`, `kontur_api.php` |
| Редактор и раскрываемый состав | `voovi.ru/js/kontur-invoice.js`, `kontur-form-core.js`, `kontur-card.js`; соответствующие CSS |
| Операции и проверка состава | `s.voovi.ru-api/basic/kontur/services.py`, `domain.py`, `views.py` |
| Единое хранилище и связи | `basic/kontur_models.py`, `basic/kontur/storage.py`, `linking.py` |
| Совместимость старых реквизитов | `basic/kontur/legacy_links.py`, `basic/kontur/compat.py`; согласованные проверки аналитики и PHP |
| Общий клиент Контура и Диадока | `s.voovi.ru-api/utils/api_skb.py` |
| Лента, поставки, расписание и Бухгалтерия | `basic/kontur_automation/`, `utils/evrika/synchronization.py` |

Django обрабатывает `/api/v1/kontur/<rand>/` и `/api/v1/kontur/<rand>/<action>`. Браузер обращается через `kontur_api.php`; пользовательский токен API Voovi и токен Контура остаются на сервере. Записывающие действия требуют серверной авторизации; PHP-прокси также проверяет CSRF.

| Метод | Действие | Назначение |
| --- | --- | --- |
| GET | `state`, `status` | Подготовка формы или чтение сохранённого состояния; `status` не опрашивает Контур |
| GET | `catalog`, `availability` | Предложения, свойства и доступность продуктов |
| GET | `search` | Поиск существующих документов в локальной БД |
| POST | `account` | Подготовка лицевого счёта поддерживаемого продукта |
| POST | `calculate` | Проверка, расчёт и сохранение актуального состава |
| POST | `issue` | Единственная попытка создания с сохранёнными GUID |
| POST | `attach` | Присоединение найденного документа или сохранение ожидающего номера |

## Настройки и запуск

Скалярные настройки читаются из общих `configs/env/local.env` и `prod.env`. Отдельного файла Контура и настроек кода СЦ в пользователе нет. Общие env версионируются по принятому в проекте решению; значения секретов в документацию не копируются.

- `KONTUR_TOKEN`, `KONTUR_PARTNER_CODE` — токен и общий код партнёра.
- `KONTUR_ENVIRONMENT`, `KONTUR_ORDERS_BASE_URL`, `KONTUR_ACCOUNTING_BASE_URL` — площадка и адреса API. Среда не хранится в документах и связях БД.
- `api_s_voovi` — адрес Django API для PHP-прокси.
- `KONTUR_AUTOMATION_VOOVI_TOKEN`, `KONTUR_AUTOMATION_VOOVI_URL`, `KONTUR_AUTOMATION_STATE_DIR` — доступ фоновых задач к Voovi и постоянное состояние ленты.
- `DIADOC_DEVELOPER_KEY` — ключ разработчика Диадока; он не заменяет токен Orders API.
- Параметры почты и [уведомлений VK](VK_NOTIFICATIONS_2026-10-25.md) задаются в том же env.

Тайм-ауты и правила повторов находятся в коде общего транспорта. Создание счёта и регистрация лицевого счёта автоматически не повторяются. Логирование API и worker использует общий `utils/logger.py`.

После изменения env контейнеры нужно пересоздать. Недостающие части unmanaged-схемы подготавливает отдельный шаг развёртывания по [инструкции хранилища](KONTUR_UNIFIED_STORAGE_2026-10-26.md#применение-sql); миграции Django для них не запускаются. Расписание устанавливается явно командой `kontur_schedule` и хранится в существующей очереди. Все задачи выполняет общий `svoovi-api-tasks`; открытие сайта расписание не устанавливает. Перед переходом старые внешние cron-задачи отключаются, поскольку их блокировки с Django не общие.

## Границы реализации и проверка

- Отдельной кнопки и автоматического прямого опроса созданного счёта нет. Номер и учётные данные поступают через ленту. Уже известный локально документ можно присоединить без новой новости; неизвестный документ ожидает появления в ленте.
- Доступные возможности Биллинга Контура шире используемого публичного API. В форме не реализованы назначение менеджера Контура, выбор Д-агента, отдельное удаление через API и самостоятельное редактирование созданного документа. Автор отправки в Voovi сохраняется в `bills.created_by`; внешние поля менеджера из новости остаются отдельными.
- Предложения загружаются при оформлении. Постоянного полного справочника тарифов и автоматического расчёта АВ по ним пока нет. Наблюдения о ценах в старых исследованиях не являются действующим прайсом.
- Подготовка схемы переводит изменяемые таблицы счетов на InnoDB. Замена состава и локальные связи сохраняются транзакционно. Внешние API и уведомления остаются за границей транзакции: вторичные действия повторяет существующая очередь. Насыщенная граница ленты из одинаковых `TimeStamp` останавливается без пропуска событий.

Серверные сценарии используют отдельную БД `voovi_kontur_v1_test` с актуальной схемой и подменёнными HTTP-ответами. Тесты проверяют разные продукты, смешанный состав, свойства, количество, повторную отправку, частичные новости, ручные и ожидающие связи. JavaScript-тесты проверяют правила формы. Команды и условия запуска приведены в [матрице тестирования](KONTUR_PRODUCT_TEST_MATRIX_2026-10-25.md); задачи и уведомления дополнительно имеют автономные тесты в своих модулях.
