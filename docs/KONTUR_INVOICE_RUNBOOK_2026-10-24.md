# Инструкция: первый счёт в Контуре из Voovi

Актуализировано 24.10.2026 по [официальной документации Orders API](https://developer.kontur.ru/doc/orders.public) и доступной на этой странице OpenAPI: 33 пути, 72 схемы. Это инструкция и проект интеграции; запросы с авторизацией не выполнялись, счета не создавались. Доступность методов именно нашему партнёру ещё предстоит проверить тестовым токеном.

Подробное исследование: [Orders API](KONTUR_ORDERS_API_2026-10-16.md). Требования к хранению полного счёта, документам и АВ: [модель данных](KONTUR_BILLING_DOMAIN_2026-10-16.md).


**Дополнение 25.10.2026:** [учётная лента из внешнего скрипта](KONTUR_ACCOUNTING_FEED_REVIEW_2026-10-25.md) реально вернула номер и окончательную сумму нашего BillId. Новые права на GET Bill в Orders API не являются обязательным условием получения этих реквизитов; в актуальном плане используется accounting API и совместимое сохранение существующей схемы.

Порядок работы реализованной формы, настройки и ограничения приведены в [текущей интеграции](KONTUR_INTEGRATION.md). Ниже сохранён первоначальный порядок изучения API.

## 1. С чего начинаем

Для внешнего интегратора документирован `POST /public-orders/v0/bills/{id}`. Для первого прогона выбираем одного тестового плательщика, один продукт, один доступный тариф и покупку `Create`, без опта и ручных скидок. Если выбранному тарифу нужны свойства, модификаторы или получатель, передаём их полностью.

Путь через корзину пока не выбираем: её создание в v0/v1 прямо обозначено как внутреннее. Больший номер версии API сам по себе не означает доступность партнёру.

Принцип работы: Voovi получает допустимые предложения → рассчитывает стоимость → сохраняет состав и идентификаторы операции → отправляет запрос создания → восстанавливает подтверждённые данные из разрешённых источников.

**Ограничение для полного запуска:** создание документировано публично, но описанное чтение шапки счёта недоступно внешним интеграторам. До выпуска функции нужно согласовать источник номера, окончательной суммы, оплаты, документов и полного состава. Успешный POST не решает эти задачи автоматически.

## 2. Получение доступа

Создать обращение в Wic: категория «Технические вопросы», тип «Подключение к API Биллинга». Если доступа к Wic нет, обратиться к региональному менеджеру. Документация предусматривает выдачу тестового токена по электронной почте; права могут ограничиваться отдельными методами.

| Настройка | Тест | Рабочая среда |
|---|---|---|
| Базовый адрес | `https://api-billy.testkontur.ru` | `https://billy-publicapi.kontur.ru` |
| Код партнёра | `b0000`, общий тестовый партнёр из инструкции | Наш код, подтверждённый Контуром |
| Авторизация | `x-Auth-CustomToken: <тестовый токен>` | Отдельный рабочий токен |
| Тело запроса | `Content-Type: application/json` | Аналогично |

Токены Диадока и других API не считаем доступом к Orders API. Токен хранится в серверной конфигурации, не в React/PHP-странице и не в репозитории. Тестовые и рабочие связи клиентов/счетов хранятся раздельно.

### Готовый текст обращения

> Просим подключить нашу партнёрскую систему Voovi к Orders API для выставления счетов Контура. Код рабочего партнёра: [указать]. Контакт для подключения: [указать]. Продукты первого этапа: [перечислить].
>
> Нужны тестовый доступ, тестовые клиент/ЛС, перечень доступных продуктов и правила получения рабочего доступа. Планируем использовать публичное создание POST /public-orders/v0/bills/{id}; поиск/создание абонентов; получение/регистрацию ЛС; справочник продуктов; pcat scale, offers и calculate; delivery/settings; recipientSettings; публичное чтение тарифов. Просим подтвердить права на методы из раздела 3 этой инструкции.
>
> В Voovi будем сохранять полный состав счёта: тарифы, модификаторы, свойства, участников, цены, скидки, налоги, сроки и состояния. В дальнейшем нужны документы и автоматизация агентского вознаграждения.
>
> Просим указать разрешённый внешнему партнёру способ получить по billId: номер и дату счёта, окончательный итог, полный подтверждённый состав, состояние/дату оплаты и последующие корректировки. GET /orders/v0/bills/{id} в документации помечен внутренним. Есть ли другой API или дополнительное подключение?
>
> Также просим предоставить способ получения пользовательской ссылки, PDF счёта и других связанных документов; правила обновления/аннулирования; источник условий и фактических начислений АВ. Как восстанавливать результат после тайм-аута/409 и обнаруживать уже автоматически выставленные счета продления? Как передавать оптовое количество в публичном создании, где quantity не объявлен? Как учитывается принадлежность продажи менеджеру/партнёру для АВ? Просим подтвердить форматы orderType для calculate и публичного создания: примеры и enum в документации местами расходятся.

Обращение подготовлено для отправки пользователем; секретный токен в текст обращения добавлять не требуется.

## 3. Последовательность вызовов

Все адреса ниже относительны выбранной площадке, все вызовы требуют заголовка авторизации.

| Шаг | Метод | Результат / действие |
|---|---|---|
| 1 | `GET /orders/products/info` | Выбрать внешний `productId`; локальный ID продукта Voovi его не заменяет |
| 2 | `GET /abonents/v0/abonents?inn=<ИНН>&kpp=<КПП>` | Найти и проверить плательщика; при необходимости отдельно получателя |
| 3 | `POST /abonents/v0/abonents` | Только если подходящего абонента нет: создать по реквизитам |
| 4 | `GET /pcat/v0/scale?productId=<productId>` | Получить сетку, допустимые модификаторы, свойства и поддержку опта |
| 5 | `POST /pcat/v0/offers` | Получить предложения конкретному клиенту, допустимые сценарии и цены |
| 6 | `POST /orders/v0/delivery/settings` | Проверить обязательность получателя и ЛС для выбранных тарифов |
| 7 | `POST /pcat/v0/recipientSettings` | Проверить, должен ли получатель совпадать с плательщиком |
| 8 | `GET /abonents/v0/abonents/ProductsSupportsRegistration` | Если нужен ЛС: проверить поддержку поиска непривязанных/регистрации по продукту |
| 9 | `POST /abonents/v0/abonents/{id}/accounts/{productId}` | При необходимости получить существующие или зарегистрировать ЛС |
| 10 | `POST /pcat/v0/calculate` | Получить предварительный расчёт выбранного состава |
| 11 | Локальная транзакция Voovi | Сохранить операцию, состав, billId и GUID новых пакетов до отправки |
| 12 | `POST /public-orders/v0/bills/{id}` | Создать счёт с сохранёнными идентификаторами |
| 13 | `GET /public-orders/v0/tariffs?abonentId=<GUID>&abonentCategory=1&partnerCode=<код>` | Найти доступные пакеты, сопоставить по billId и GUID пакетов |
| 14 | Согласованный с Контуром источник | Получить шапку, документы и финансовые состояния; способ пока не подтверждён |

Поиск абонента возвращает массив: возможны дубли, головная организация и филиалы. Не выбирать первую запись автоматически. Для создания обязательны `name`, `inn`, `clientType`: 1 — юрлицо, 2 — ИП, 3 — физлицо; КПП заполняется по типу клиента. При конфликте создания проверять причину и существующего абонента.

Метод ЛС на шаге 9 не имеет описанного тела запроса и возвращает `accountIds[]`. Несколько результатов требуют выбора по контексту продажи. Для продления нужен правильный существующий ЛС. Привязка уже известного ЛС — отдельный `POST /abonents/v0/abonents/{id}/accounts` с `productId` и `accountId`.

## 4. Подготовка состава и расчёт

### Получить доступные предложения

`POST /pcat/v0/offers`

```json
{
  "abonent": {"abonentId": "<GUID плательщика>"},
  "productId": "<productId из справочника>",
  "partner": {"code": "b0000"},
  "scenarioTypes": [1],
  "returnAllAvailable": true
}
```

`returnAllAvailable: true` запрашивает все доступные предложения, без необходимости заранее знать целевые тарифы. Выбираем `tariffId` из доступных, сохраняем ограничения и выбранные свойства. Наличие тарифа в scale не подтверждает возможность продать его этому клиенту.

Цена определяется каталогом: `basePriceType=1` — фиксированная, 2 — открытая с `minimumCost`. `customPrice` допустим только для открытой цены. Тарифную зону можно указать через `priceZone.fiasId`; без неё применяется определение зоны биллингом по данным плательщика. Контекст зоны должен совпадать в подготовке и создании.

### Проверить доставку

`POST /orders/v0/delivery/settings` принимает JSON-массив строк `tariffId`. Значения `recipientRequired`: 1 — обязательны получатель и его ЛС; 2 — получатель опционален, без него используются коды активации; 3 — получатель не требуется.

`POST /pcat/v0/recipientSettings` принимает объект `{"tariffIds":["<tariffId>"]}` и возвращает, в частности, `recipientMustBePayer`.

### Рассчитать стоимость

`POST /pcat/v0/calculate`. Пример для одного тарифа с обязательным получателем:

```json
{
  "payer": {"abonentId": "<GUID плательщика>"},
  "positions": [
    {
      "productId": "<productId из справочника>",
      "orderType": 1,
      "tariff": {
        "tariffId": "<доступный tariffId>",
        "quantity": 1
      },
      "recipient": {"abonentId": "<GUID получателя>"},
      "deliverySettings": {"accountId": "<GUID ЛС получателя>"}
    }
  ]
}
```

Добавить обязательные `settings` и `modifiers` выбранного тарифа; убрать получателя/ЛС, если по правилам они не нужны. Для первого теста предпочтителен простой тариф без обязательных дополнительных свойств, если такой доступен.

Расчёт возвращает массив позиций с ценами, скидками и вложенными модификаторами. Храним ответ целиком. Предварительную стоимость не выдаём за подтверждённый итог уже созданного счёта.

Ограничения: общее описание предусматривает расчёт одного продукта; схема требует одинаковый `orderType` у всех позиций расчёта. Для нескольких продуктов или разных сценариев не обещаем единый точный расчёт без отдельной проверки. Оптимальная нагрузка calculate — один запрос в секунду.

В схеме calculate `orderType` — число 1–4; один пример использует строку. Используем число по схеме и проверяем на тестовой площадке. В публичном создании используется строковое имя сценария по описанию и примеру; его enum оформлен неоднозначно. Это расхождение документации, а не проверенный нами результат вызова.

## 5. Запрос создания

`POST /public-orders/v0/bills/<новый сохранённый billId>`

```json
{
  "partner": {"code": "b0000"},
  "payer": {"abonentId": "<GUID плательщика>"},
  "tariffs": [
    {
      "productId": "<productId из справочника>",
      "tariff": {
        "orderPackageId": "<новый сохранённый GUID пакета>",
        "tariffId": "<доступный tariffId>"
      },
      "recipient": {"abonentId": "<GUID получателя>"},
      "deliverySettings": {"accountId": "<GUID ЛС получателя>"},
      "scenario": {"orderType": "Create"}
    }
  ]
}
```

Это шаблоны, не готовые запросы: все строки в угловых скобках заменяются реальными данными тестовой площадки. Код `b0000` используется только в тесте. Не копируем демонстрационные тарифы и GUID из документации как действующие данные нашего партнёра.

Верхние обязательные поля — `partner`, `payer`, `tariffs`; у позиции — `productId`, `tariff`, `scenario`; у тарифа — `orderPackageId`, `tariffId`.

Каждому новому тарифу и модификатору нужен отдельный GUID пакета. Вложенные `modifiers`, выбранные `settings` (`type`, `values[]`) и допустимый `customPrice` передаются по правилам каталога. Указанную в Voovi произвольную сумму нельзя подставить вместо цены фиксированного тарифа.

Сценарии: `Create` — покупка и обычное продление; `Change` — смена; `Rebuy` — докупка; `EarlyProlongation` — досрочное продление. Для последних трёх в `scenario.orderPackageId` передаётся GUID **прежнего** пакета из offers. Он отличается от GUID **нового** пакета в `tariff.orderPackageId`.

**Расчёт и создание имеют разные JSON-схемы:** `positions` против `tariffs`, числовой `orderType` против объекта `scenario`, количество против GUID пакета. В публичной схеме тарифа `quantity` отсутствует; опт требует согласованного способа передачи. Для первого теста используем одну единицу. Передачу позиционных/комплектных скидок проверяем отдельным этапом; `discount.percent` допускает 0 ≤ значение < 100.

Отображаемый номер и общая сумма счёта в теле публичного создания не задаются. Локальный номер Voovi не заменяет billId Контура.

## 6. Ответ, повторы и восстановление

| Результат | Обработка в Voovi |
|---|---|
| 201 | Создание подтверждено; сохранить ответ и перейти к получению реквизитов. Тело и заголовки успешного ответа спецификацией не определены |
| 400 | Сохранить ошибку валидации, показать причину, исправить состав до новой отправки |
| 409 | Документ с GUID существует; сверить с нашей операцией и внешними данными. Не считать номер/сумму полученными |
| Тайм-аут / обрыв | Результат неизвестен. Сохранить состояние неопределённости, восстановить результат или повторить тот же запрос с теми же GUID по согласованным правилам |

Не генерировать новый billId при сетевом повторе. GUID и неизменяемый отправленный состав хранятся до запроса; двойное нажатие не создаёт вторую операцию. Если состав изменился после неопределённого результата, сначала выяснить судьбу первой операции.

Публичное чтение тарифов использует индекс с задержкой до 30 секунд. После 201 временно пустой результат не означает отсутствия счёта: выполняем ограниченную сверку с увеличением интервалов. Метод возвращает `tariffs` и `censoredTariffs`; скрытые поля означают неполноту доступа. Сопоставляем доступные пакеты с сохранёнными `billId` и `orderPackageId`. Активация пакета не подтверждает оплату.

GUID защищает от технического повтора одной операции. Отдельно проверяется бизнес-дубль: например, Контур уже автоматически выставил клиенту продление с другим GUID.

## 7. Что сохранить в нашей базе с первой версии

Это требования к реализации, не утверждение о доступности всех данных в публичном API. Можно добавлять новые связанные таблицы в текущую БД, сохраняя выбранный постепенный переход к PostgreSQL.

| Группа | Данные |
|---|---|
| Операция | Среда, локальный ID, инициатор, billId, GUID пакетов, состояние, точный отправленный состав, попытки, время, HTTP-результаты и ошибки |
| Участники | Партнёр, плательщик, получатели, реквизиты на момент выставления, productId/accountId и связи с карточками Voovi |
| Состав | Дерево тарифов/модификаторов, внешние ID, названия, свойства, сценарий, прежний и новый пакеты, сроки |
| Финансы | Версия предварительного расчёта, цены, скидки, налоги и окончательные данные отдельно; источник и время подтверждения |
| Счёт и состояния | Номер, дата, итог, история оплаты/корректировок — по подтверждённому источнику; отсутствующие данные остаются неизвестными |
| Исходные данные | Снимки использованных offers/scale/calculate и запросов/ответов создания/сверки, время получения; без секретного заголовка авторизации |
| Документы и АВ | Связи с версиями файлов, источниками и версиями правил АВ, расчётами и фактическими начислениями — по мере подключения источников |

Для денежных значений — точные десятичные типы. Структурированные данные нужны для поиска и расчётов, исходные JSON — для восстановления истории. Текущие поля номера/суммы/ссылки внешнего счёта служат совместимым отображением на старых экранах, а не заменой полного хранения.

Внешний состав Контура сохраняется отдельно от позиций услуг Савоира. Между ними нужны явные связи; услуги Савоира не отправляются в Контур как произвольные тарифы.

## 8. Что пока не подтверждено и что считать результатом

| Возможность | Статус по проверенной документации |
|---|---|
| Создать внешний счёт по тарифам | Публичный метод описан; наш токен ещё не проверен |
| Прочитать доступные пакеты | Публичный метод описан; полнота зависит от прав |
| Получить номер/итог/оплату через GET Bill | Сам метод описан, но явно закрыт для внешних интеграторов |
| Получить пользовательскую ссылку/PDF | В этой спецификации способ не найден |
| Получить правила и фактические начисления АВ | В этой спецификации источник не найден |

Это ограничения изученного контракта, а не утверждение об отсутствии других возможностей у Контура.

Первый технический результат: на тестовой площадке создан ровно один счёт с сохранённым составом и GUID; подтверждены получатель/ЛС и выбранные параметры; повтор не создаёт дубль; доступные пакеты сопоставлены с операцией. Полная готовность функции дополнительно требует согласованного получения реквизитов, состава, документов и финансовых состояний. АВ запускается после получения правил и источника фактических начислений.
