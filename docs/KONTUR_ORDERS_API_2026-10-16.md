# Выставление счетов Контура через Orders API и связь с Voovi

Исследование 16.10.2026 по [официальной документации](https://developer.kontur.ru/doc/orders.public) и опубликованной на странице OpenAPI 3.0.1, info.version=1.0. Просмотрены описания и схемы методов, включая ограничения для внешних интеграторов. Запросы к самому биллингу с токеном не выполнялись, счета не создавались. Ниже отдельно обозначены подтверждённые возможности, пробелы документации и предлагаемая архитектура.

Практическая инструкция повторно сверена 24.10.2026: [доступ, порядок вызовов, примеры и текст обращения в Контур](KONTUR_INVOICE_RUNBOOK_2026-10-24.md).

**Дополнение 25.10.2026:** ограничения чтения ниже относятся к изученному Orders API. После получения внешнего скрипта [другой доступный accounting API](KONTUR_ACCOUNTING_FEED_REVIEW_2026-10-25.md) реально вернул номер, окончательный итог и состав нашего BillId. План внедрения использует этот источник и существующую схему Voovi; получение номера больше не требует предполагать доступ к закрытому GET Bill в Orders API.

## 1. Вывод для нашего проекта

**Цель уточнена:** хранить в Voovi полноценный внешний счёт, все его позиции/пакеты, свойства, цены, скидки, участников, состояния и документы, с основой для автоматического расчёта и сверки АВ. Заполнение номера, суммы и ссылки — только совместимость со старым интерфейсом. Целевая модель и критерии готовности: [KONTUR_BILLING_DOMAIN_2026-10-16.md](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/docs/KONTUR_BILLING_DOMAIN_2026-10-16.md).

Создавать внешний счёт непосредственно из Voovi возможно: для партнёров опубликован `POST /public-orders/v0/bills/{id}`. Он принимает состав тарифов Контура, плательщика, партнёра и параметры продажи.

Для такой интеграции нужно подтвердить не только создание, но и чтение полного состава, финансовых состояний, получение документов и источники данных АВ. По этой документации нельзя подтвердить весь цикл для обычного внешнего токена:

- У публичного создания описаны ответы 201/400/409, но нет схемы тела успешного ответа и заголовков с реквизитами.
- Чтение `GET /orders/v0/bills/{id}` возвращает модель Bill с номером, суммой и оплатой, но явно недоступно внешним интеграторам.
- Поиск счетов по плательщику/номеру также помечен как внутренний.
- В модели Bill нет URL страницы оплаты/просмотра или PDF. В этой спецификации вообще нет метода получения печатной формы счёта.

Публичный сценарий создания документирован. Для полной автоматизации нужно согласовать с Контуром и проверить тестовым токеном получение шапки, всех тарифов/модификаторов/свойств, подтверждённых цен/скидок, состояний и документов. Правила и фактические начисления АВ требуют отдельного источника: в изученной спецификации такой контракт не найден. Нельзя считать эти возможности доступными по аналогии с внутренними методами.

Источник: [публичное выставление](https://developer.kontur.ru/doc/orders.public/method?type=post&path=%2Fpublic-orders%2Fv0%2Fbills%2F%7Bid%7D), [чтение Bill с ограничением](https://developer.kontur.ru/doc/orders.public/method?type=get&path=%2Forders%2Fv0%2Fbills%2F%7Bid%7D).

## 2. Доступ и площадки

| Назначение | Значение |
|---|---|
| Тест | `https://api-billy.testkontur.ru` |
| Рабочая площадка | `https://billy-publicapi.kontur.ru` |
| Авторизация каждого вызова | HTTP-заголовок `x-Auth-CustomToken` |
| JSON-запросы | `Content-Type: application/json` |
| Тестовый партнёр из инструкции | код `b0000` |

Токен запрашивается через Wic: категория «Технические вопросы», тип «Подключение к API Биллинга». Если доступа к Wic нет, обращение может создать региональный менеджер. Для тестирования предоставляются тестовый токен, партнёр и пользователь. Доступ может открываться ко всему API или к отдельным методам.

Это другой API и другой тип авторизации, чем уже используемые в проекте Диадок и Контур.Бухгалтерия/Эврика. Наличие их настроек не подтверждает доступ к Orders API.

Предложение для реализации: отдельные настройки URL, токена и кода партнёра; токен только на сервере Django, без передачи в JavaScript или PHP-HTML. Тестовая и рабочая интеграции должны иметь раздельные идентификаторы и состояние.

Источник: разделы «Точки входа» и «Доступ к API» [общего описания](https://developer.kontur.ru/doc/orders.public).

## 3. Главные сущности и соответствия

| Контур | Смысл | Voovi / требуемое дополнение |
|---|---|---|
| Abonent | Клиент с реквизитами | `ogrn.id`; нужна сохранённая связь с `abonentId` |
| Account | Лицевой счёт по продукту, GUID | Нужна связь клиента и `productId` с `accountId`; у клиента может быть несколько ЛС |
| Partner | Сервисный центр, выставляющий внешний счёт | Отдельная настройка, code либо GUID; не `users.otdel` |
| Product | Продукт Контура, строковый ID | Нужное соответствие с `produkti`; локальный числовой ID не подходит |
| Tariff | Тариф каталога Контура | Нужное соответствие с локальным тарифом/набором; `tarif.id` и `sync_id` не становятся внешними ID автоматически |
| OrderPackage | Пакет конкретного приобретения тарифа, GUID | Сохранять отдельно для каждой внешней позиции |
| Order | Изменяемая корзина | Отдельная внешняя сущность, если разрешён сценарий корзины |
| Bill ID | GUID внешнего счёта | Генерируем и сохраняем до первого POST |
| Bill number | Отображаемый номер Контура | `schet.nomerschetks` после подтверждённого получения |
| Bill amount | Итог Контура в рублях | `schet.priceks` после подтверждённого получения |
| Ссылка для пользователя | Адрес просмотра/оплаты | `schet.url`; источник пока не подтверждён |

Эта таблица показывает только идентификаторы и совместимость. Внешний счёт и его состав хранятся самостоятельными сущностями; `nomerschetks`, `priceks` и `url` — краткое представление для старых экранов.

Внутренние `schet.ns`, `rand` и годовая нумерация Voovi остаются самостоятельными. GUID Контура нельзя подменять отображаемым номером Voovi или внешним номером Контура.

## 4. Практический публичный сценарий

### Шаг 1. Найти плательщика и получателя

`GET /abonents/v0/abonents?inn=...&kpp=...`

Поиск возвращает массив, включая возможные дубли, головную организацию/филиалы и варианты КПП. Нельзя без проверки считать первую запись точным совпадением. При наличии известного ЛС документация предлагает также искать по `accountId` и сопоставлять результаты.

Если подходящего абонента нет: `POST /abonents/v0/abonents`. Обязательные поля схемы: `name`, `inn`, `clientType`; `kpp` передаётся по типу клиента. Значения clientType: 1 — юридическое лицо, 2 — ИП, 3 — физическое лицо. При 409 нужно разбирать причину и, если передан, Location существующего абонента.

Плательщик и получатель продукта могут отличаться. Не следует жёстко привязывать оба значения к одной карточке Voovi во всех сценариях.

### Шаг 2. Определить лицевой счёт

Для части тарифов нужен не только `abonentId`, но и `accountId`. В ответе поиска абонента перечислены привязанные ЛС по продуктам.

Есть `POST /abonents/v0/abonents/{id}/accounts/{productId}` — получение существующего или регистрация ЛС. Регистрация/поиск непривязанного ЛС поддерживаются только отдельными продуктами. Их перечень выдаёт `GET /abonents/v0/abonents/ProductsSupportsRegistration`. Привязка известного ЛС: `POST /abonents/v0/abonents/{id}/accounts`.

Общая инструкция содержит и внутренние методы Портала для работы с ЛС; нельзя предполагать их доступность нашему токену. Для неподдерживаемого продукта может потребоваться заранее созданный и привязанный ЛС.

### Шаг 3. Получить каталог и доступные предложения

| Метод | Назначение |
|---|---|
| `GET /orders/products/info` | Продукты и их внешние ID |
| `GET /pcat/v0/scale` | Тарифная сетка, связи основных тарифов и модификаторов, настройки |
| `POST /pcat/v0/offers` | Доступные конкретному абоненту тарифы и сценарии, ограничения и цены |

В запрос offers передаются `abonent`, `productId`; возможны `partner`, `priceZone.fiasId`, `scenarioTypes`, целевые тарифы и другие настройки. `orderId` нужен только для проверки дополнения уже существующей корзины.

Наличие тарифа в справочнике ещё не означает, что его можно продать выбранному клиенту. Offers возвращает доступные и недоступные тарифы, допустимые свойства и пакеты для смены/докупки.

Цена бывает фиксированной или открытой. В `initialCost` это `basePriceType=1` либо 2. Для открытой цены есть нижняя граница `minimumCost`; произвольную сумму Voovi передать для любого тарифа нельзя.

### Шаг 4. Уточнить получателя и параметры

`POST /orders/v0/delivery/settings` принимает массив тарифных ID. Для каждого возвращает `recipientRequired`:

- 1 — обязательны получатель и его лицевой счёт;
- 2 — получатель опционален; при отсутствии используются коды активации;
- 3 — получателя передавать не требуется.

Есть также `POST /pcat/v0/recipientSettings` для проверки, должен ли получатель совпадать с плательщиком. Настройки товара/сертификата передаются массивом `settings` с `type` и `values`; конкретные допустимые варианты определяются каталогом и offers.

### Шаг 5. Рассчитать стоимость до создания

`POST /pcat/v0/calculate` принимает **BillCreateForm**, где поля `payer`, `positions`, `promotions`, `priceZone` и при необходимости `vendorId`. Возвращает позиции с ценами, модификаторами и применёнными скидками, в том числе стоимости с налогом и без него.

В общем описании указано ограничение расчёта тарифами одного продукта. При нескольких продуктах публичное выставление разрешено, но нельзя без дополнительной проверки обещать единый точный межпродуктовый предварительный расчёт всех комплектных скидок.

Формат расчёта отличается от публичного POST выставления:

- calculate: `positions[]`, `orderType` у позиции, `quantity` у тарифа;
- public create: `tariffs[]`, объект `scenario`, обязательный GUID `tariff.orderPackageId`.

Нужен явный преобразователь данных. Нельзя отправлять один и тот же JSON в оба метода.

Для calculate описана оптимальная нагрузка 1 запрос/с: пересчёт ввода нужно ограничивать и объединять, а не запускать на каждый символ. Это рекомендация по нагрузке из документации, не универсальная квота всех методов.

### Шаг 6. Выставить счёт

`POST /public-orders/v0/bills/{billId}`

`billId` — новый GUID, генерируемый нашей системой **один раз до первой попытки**. У каждого тарифа и его модификатора отдельный GUID `orderPackageId`.

Обязательные верхние поля: `partner`, `payer`, `tariffs`.

| Поле позиции | Заполнение |
|---|---|
| `productId` | Внешний ID продукта |
| `tariff.tariffId` | Доступный ID тарифа Контура |
| `tariff.orderPackageId` | Новый GUID приобретаемого пакета |
| `tariff.settings[]` | Свойства и выбранные значения из каталога |
| `tariff.modifiers[]` | Вложенные модификаторы с собственными GUID |
| `tariff.customPrice` | Только при разрешённой открытой цене |
| `tariff.discount.percent` | Позиционная скидка; по схеме 0 ≤ процент < 100 |
| `recipient.abonentId` | Получатель, когда требуется/выбран |
| `deliverySettings.accountId` | ЛС получателя, когда требуется |
| `priceZone.fiasId` | Тарифная зона при явном выборе |
| `scenario.orderType` | Сценарий продажи |
| `scenario.orderPackageId` | Старый пакет, участвующий в смене/докупке/досрочном продлении |

Внешние сценарии:

- `Create` — и первичная покупка, и обычное продление;
- `Change` — смена тарифа;
- `Rebuy` — докупка;
- `EarlyProlongation` — досрочное продление.

`schet.shetold` нельзя напрямую передать как scenario.orderPackageId: это локальный номер, а API ждёт GUID внешнего пакета. GUID нового пакета в `tariff` и GUID прежнего пакета в `scenario` имеют разные роли.

В схеме `express.OrderTariffForm` **нет quantity**. В calculate оно есть (1–500 при поддержке опта). Поэтому локальное `kvo > 1` требует отдельного сопоставления с внешними пакетами/оптовой моделью, а не механического копирования поля. Это вопрос для тестового прогона и поддержки Контура.

Глобальные скидки задаются `discounts[]`: собственный GUID, ключ скидки/акции, список GUID пакетов, при необходимости значение и ID продуктов. Локальную скидку Voovi, особенно 100%, нельзя автоматически переносить как внешнюю позиционную.

### Шаг 7. Обработать результат

| Ответ | Что подтверждено |
|---|---|
| 201 | Публичный метод сообщает успешное создание; тело/заголовки не описаны |
| 400 | Ошибка валидации |
| 409 | Счёт с переданным GUID уже существует |

При тайм-ауте неизвестно, успел ли Контур создать счёт. Повтор должен использовать прежний billId и те же пакеты/состав. Новый GUID на каждый повтор создаёт риск второго реального счёта.

409 не надо автоматически выдавать за полный успех с известными реквизитами: нужно сверить внешнее состояние и убедиться, что существующий документ соответствует этой операции. В публичном ответе не обещан Location.

## 5. Второй сценарий: корзина, v1 и v2

Документация также описывает:

1. `POST /orders/v1/orders/{orderId}` — создать корзину.
2. `POST /orders/v1/orders/{orderId}/tariffs` — добавить тарифы.
3. PUT/DELETE тарифов, настройки скидок и доставки.
4. `GET /orders/v1/orders/{orderId}` — получить состав и рассчитанную стоимость.
5. `POST /orders/v1/bills` с orderId/billId — синхронно выставить; ответ 201 содержит billId и Location API-ресурса.
6. Либо `POST /orders/v2/orders/bills` — запустить асинхронное выставление; ответ 202.
7. `GET /orders/v2/orders/{orderId}/status` — отслеживать процесс.

Но **создание корзины v0 и v1, а также изменение шапки корзины v1 прямо помечены недоступными внешним интеграторам**. Другие методы могут не содержать этой пометки, однако без доступного создания/получения заказа вся цепочка для нас не подтверждена. Нельзя выбирать v2 только потому, что номер версии выше.

202 означает запуск, а не готовность счёта: валидация может завершиться ошибкой позже. В статусе есть orderId, необязательный billId, status, время и ошибка. Числовые значения состояний нужно получать из `GET /orders/v2/orders/statuses`: опубликованная модель не задаёт полный enum готовности/ошибки. Не следует придумывать коды.

Статус выставления v2 — не статус оплаты. Возвращаемый Location — адрес API-ресурса, не обещанная пользовательская ссылка для `schet.url`.

## 6. Номер, итог, ссылка и оплата: что реально можно получить

| Нужные данные | Есть ли описание | Ограничение |
|---|---|---|
| GUID счёта | Генерируем сами | Сохранять до запроса |
| Отображаемый номер | `Bill.billNumber` | Чтение Bill помечено внутренним |
| Окончательный итог | `Bill.amount`, рубли | То же ограничение |
| Предварительная цена | pcat calculate | Не равнозначна подтверждённому Bill.amount |
| Ссылка просмотра/оплаты | Не описана | Нужен отдельный контракт |
| PDF | Не описан | Нужен отдельный контракт |
| Оплата | `Bill.paymentState`, `paidDate` | Чтение Bill помечено внутренним |
| Состав доступных внешних пакетов | `GET /public-orders/v0/tariffs` | Проверка прав, часть данных может скрываться; индекс может отставать до 30 с |

`paymentState` модели Bill: 0 — не оплачен, 1 — оплата снята, 2 — оплачен, 3 — условно оплачен. Значения не совпадают с булевым `oplachenks` Voovi. При будущем подключении чтения нельзя считать любое ненулевое значение оплатой; также нужно учитывать снятие оплаты.

Публичное чтение тарифов принимает abonentId, категорию плательщик/получатель, partnerCode либо partnerId, опциональный productId. В полных данных есть billId, amount конкретного тарифа, accountId, state и сроки. Это не полноценное чтение шапки счёта: billNumber, URL и paymentState оно не обещает. Активация тарифа не заменяет подтверждение оплаты.

В проверенной спецификации нет webhook-контракта, потоковой ленты оплат или методов исправления/аннулирования уже выставленного Bill. Это означает отсутствие описания здесь, а не доказательство отсутствия таких возможностей в других API Контура.

## 7. Целевая интеграция в Voovi

Это проектное предложение, а не существующее поведение. Подробная модель уточнена с учётом требования хранить все данные: [полный внешний счёт, АВ и документы](/Users/admin/Documents/Develop/Projects/SAVOIR/voovi/docs/KONTUR_BILLING_DOMAIN_2026-10-16.md).

Нужны три уровня хранения: структурированные сущности для работы системы, исходные снимки запросов/ответов и версий каталога, файлы документов с метаданными. В состав сущностей входят шапка счёта, позиции/пакеты и их дерево модификаторов, свойства, цены/налоги/скидки, плательщик/получатели/ЛС, история состояний, операции интеграции, версии расчёта АВ и фактические начисления.

Серверный клиент и обработчик размещаются в Django API. Перед первым POST сохраняются операция, billId, GUID пакетов и состав. Повторы используют ту же операцию; при неопределённом результате сначала восстанавливается связь. Все новые данные и операции проектируются с локальной транзакционностью, отдельно от сетевого вызова и старого многошагового PHP INSERT.

Существующие `nomerschetks`, `priceks`, `url` синхронизируются как краткое представление на старых экранах. Внешний состав не обязательно совпадает с услугами SAVOIR; нужны явные связи счетов/позиций и контроль распределения сумм.

Расчёт АВ должен быть воспроизводимым по позициям, ролям, фактам оплаты/исполнения и версии правил. Ожидаемое АВ отделяется от подтверждённого начисления и сверяется с ним. Состав счёта без правил и источника фактических начислений не определяет сумму вознаграждения. Документы хранятся самостоятельными версиями файлов; доступ к их получению необходимо подтвердить.

Дополнительно в проекте уже найдены `bills`, `av`, `avkontur`, `av_ci`, фоновая синхронизация bills → schet → av и импорт отчёта вознаграждений. Перед выбором окончательных таблиц нужно разобрать эти источники и потребителей. Новая интеграция должна использовать согласованный источник истины, сохраняя совместимость существующих экранов и отчётов.

## 8. Пример публичного запроса

Шаблон, не готовые реальные реквизиты. Строки в угловых скобках заменяются результатами каталога/поиска. GUID в примере условные; в реальной операции генерируются и сохраняются один раз. Вызов не выполнялся.

```http
POST https://api-billy.testkontur.ru/public-orders/v0/bills/7d4cbcab-25cc-43e5-aa11-fbca70cf207a
x-Auth-CustomToken: <тестовый токен из серверной конфигурации>
Content-Type: application/json
```

```json
{
  "partner": {"code": "b0000"},
  "payer": {"abonentId": "<GUID плательщика>"},
  "tariffs": [
    {
      "productId": "<productId из каталога>",
      "tariff": {
        "orderPackageId": "35149e6a-e84d-4eb9-8b73-a6e16e99316b",
        "tariffId": "<tariffId из доступного предложения>"
      },
      "recipient": {"abonentId": "<GUID получателя>"},
      "deliverySettings": {"accountId": "<GUID ЛС получателя>"},
      "scenario": {"orderType": "Create"}
    }
  ]
}
```

Recipient/deliverySettings оставлены для случая обязательного получателя. Settings, modifiers и customPrice добавляются только по требованиям выбранного тарифа. В теле нет произвольного отображаемого номера и общей суммы: они определяются биллингом, а не переносятся из внутреннего счёта Voovi.

## 9. Что выяснить у Контура до реализации полного цикла

1. Какие методы доступны нашему партнёрскому токену и поддерживается ли выдача через корзину/v2?
2. Как внешнему интегратору получить **billNumber, окончательный amount, paymentState и paidDate** своего Bill? Возможна ли выдача прав на GET Bill или существует другой публичный метод?

5. Как моделировать количество и оптовые тарифы в express.OrderTariffForm, где quantity не объявлен?
6. Какие наши продукты поддерживают создание/регистрацию ЛС внешним токеном?

9. Как обнаруживать уже автоматически выставленные Контуром счета продления и избегать бизнес-дублей с другим GUID?
10. Есть ли дополнительные квоты, webhook или другой рекомендуемый способ синхронизации состояния?

Эти вопросы можно передать одним техническим обращением с кодом партнёра и нужным списком методов, без пересылки самого секретного токена.

## 10. Проверка интеграции, когда будет тестовый доступ

Сначала подтвердить чтение каталогов/клиента и права. Затем на специально выделенных тестовых данных проверить: новый счёт, продление Create, докупку, обязательный ЛС, свойства КЭП, скидки, количество, несколько продуктов, ошибку 400, повтор с тем же GUID, тайм-аут после отправки и восстановление локальной связи. После этого отдельно проверить получение реквизитов/ссылки и статусы оплаты, если соответствующий доступ будет выдан.

Тест успешного POST сам по себе не подтверждает готовность интеграции. Нужны восстановимый полный состав, история данных, воспроизводимость АВ, сверка фактических начислений, получение документов и защита от повторных счетов/начислений.
