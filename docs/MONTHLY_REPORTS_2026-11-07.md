## Конфигурация и секреты

Все настройки находятся в **общем ENV соответствующей среды**: `configs/env/local.env` для локального запуска и `configs/env/prod.env` для будущего production-развертывания. Эти существующие файлы хранятся в приватном Git-репозитории по указанию владельца. В них добавлены существующие Google OAuth client ID, client secret, refresh token, ID двух таблиц, настройки VK и параметры месячных заданий. Отдельного ENV-файла отчетов нет. В Python и логи секреты не встроены. Браузерная авторизация при работе worker не требуется. При отзыве refresh token нужно повторное согласие владельца Google-аккаунта и замена значений в общем ENV.

Переменные:

- `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, `GOOGLE_OAUTH_REFRESH_TOKEN` — общий доступ обоих отчетов.
- `MONTHLY_MOVEMENT_SPREADSHEET_ID`, `MONTHLY_PAYMENTS_SPREADSHEET_ID` — таблицы прежних отчетов.
- `GOOGLE_SHEETS_BATCH_ROWS=500`, `GOOGLE_SHEETS_BATCH_BYTES=1000000`, `GOOGLE_SHEETS_MIN_INTERVAL=1.25` — пределы пачки и частоты.
- `MONTHLY_REPORTS_ENABLED=0` — автозапуск и постановка задач только после явного включения.
- `MONTHLY_REPORTS_EMAIL_ENABLED=1`, `MONTHLY_REPORTS_EMAIL_TO` — письмо о готовом отчете оплат; проверки используют того же получателя. SMTP — существующие Django ENV.
- `MONTHLY_REPORTS_VK_ENABLED`, `MONTHLY_REPORTS_VK_ACCESS_TOKEN`, `MONTHLY_REPORTS_VK_PEER_ID` — уведомления двух отчетов. Если отдельный токен/получатель не задан, используется существующая конфигурация VK.
- `MONTHLY_REPORTS_STATE_DIR` — при необходимости другой каталог результатов. По умолчанию это `monthly_reports` в постоянном томе reminders.

Compose использует прежнее подключение общего ENV среды, без дополнительных env_file. В `local.env` автозапуск выключен (`MONTHLY_REPORTS_ENABLED=0`), в `prod.env` включен (`MONTHLY_REPORTS_ENABLED=1`) по указанию владельца. Изменения `prod.env` сейчас выполнены только в локальном checkout: на сервер они не разворачивались.

## Запуск

Из контейнера API либо worker. По умолчанию — только SELECT, без Google, писем, VK, постановки задач и записи результатов:

```sh
python manage.py monthly_reports checks --month 2026-10 --dry-run
python manage.py monthly_reports movement --month 2026-10 --dry-run
python manage.py monthly_reports payments --month 2026-10 --dry-run
```

`--details` включает полный предварительный отчет/тела уведомлений; он может содержать персональные данные клиентов. Без `--month` используется предыдущий календарный месяц в Москве.

Явное выполнение, включая Google и разрешенные уведомления:

```sh
python manage.py monthly_reports movement --month 2026-10 --execute
python manage.py monthly_reports payments --month 2026-10 --execute
python manage.py monthly_reports checks --month 2026-10 --execute
```

Автозапуск: установить `MONTHLY_REPORTS_ENABLED=1` в общем ENV нужной среды и пересоздать API/worker-контейнеры с обновленной конфигурацией. Затем:

```sh
python manage.py monthly_reports --install-schedule
python manage.py process_tasks
```

`process_tasks` также сам регистрирует календарь при старте. Ручной асинхронный запуск: `monthly_reports payments --month 2026-10 --enqueue` при включенном флаге. Обычная очередь финансовых заданий и остальные расписания сохраняются.

## Google: пачки и повторы

Один HTTP-сеанс и обновляемый OAuth access token. Строки делятся на диапазоны максимум по 500 строк и 1 МБ UTF-8; идентификаторы остаются строками. Используется `values:batchUpdate` с `RAW`, а не append по строке. Поэтому текст, начинающийся с `=`, не выполняется как формула. Между запросами минимум 1.25 секунды; предусмотрены ограниченные повторы с exponential backoff, jitter, учетом Retry-After для 429, quota-ошибок 403 и временных ошибок сервера. Недостаточные права/отозванные ключи не повторяются бесконечно.

Оба задания сериализуют Google-запись общей блокировкой. Пачки загружаются в скрытый `_voovi_upload_<sheetId>`. После всех пачек видимый лист заменяется **одним атомарным batchUpdate**: очистка старых значений и копирование нового результата. ID видимого листа и ссылки сохраняются. Сбой посреди загрузки оставляет прежний видимый отчет. Для нового периода до первой успешной публикации может существовать пустой лист; сообщение об успехе не отправляется. Рабочий лист не удаляется, а переиспользуется — число временных листов не растет при повторе одного периода.

Официальные контракты: [квоты Sheets](https://developers.google.com/workspace/sheets/api/limits), [values.batchUpdate](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/batchUpdate), [OAuth offline access](https://developers.google.com/identity/protocols/oauth2/web-server#offline).

## Отличия от старых скриптов

### Проверки

- Отбираются активные **отгруженные** позиции прошлого месяца по `akt_date=YYMM`; группировка по `rand`.
- Отсутствующая сумма поставщика проверяется у всех отобранных отгруженных позиций отдела 24 **независимо от номера, ссылки и BillId**. NULL, пустая строка и пробелы требуют уведомления; ноль — заполненная сумма.
- Исполнитель описи требуется при положительном количестве описей в прежнем наборе тарифов маркировки.
- Текстовое, отрицательное или дробное количество описей — отдельная диагностика и уведомление с ID позиций. Ошибка не останавливает проверки остальных строк; итог запуска `partial` сохраняет замечания.
- Общий запрет нескольких тарифов и требование заново выставить отгруженный счет исключены.

Прежняя проверка относилась не ко всем счетам сайта: она выбирала отгрузки предыдущего месяца с `tarif.savoir=''` и `(produkti.id=319 OR tarif.markirovka='2')`. Затем считала **все неудаленные строки** соответствующего `rand`. Если строк больше одной, отправляла письмо с требованием поместить счет в черновик, выставить заново и отдельно решить вопрос с оплатой. Проверки разных тарифов или запрещенных сочетаний не было: даже две строки одного тарифа считались нарушением. Сам скрипт только уведомлял и счета не менял. Новая реализация не считает количество строк основанием для перевыставления.
- Проверки ничего не меняют в оплатах, отгрузках, зарплате или составе счета.

### Движение заявок

Как и прежде, это текущий портфель принципала 12 с отметкой отгрузки в выбранном месяце, **не исторический снимок всех статусов на конец месяца**. Исправлены перепутанные «Черновик»/«Отказ», сортировка дат и размножение строк из-за соединения со всеми тарифами продукта. Выводятся конкретные позиции, rand и ID; шапки нескольких позиций не суммируются автоматически. Повтор заменяет лист, не дописывает те же строки.

Денежные колонки суммы поставщика и SAVOIR преобразуются в Decimal перед экспортом, включая десятичную запятую и разделители тысяч (обычный/неразрывный пробел). Google получает числовые значения, а не строки. ИНН и номера счетов остаются текстом с сохранением ведущих нулей. Пустая сумма остается пустой; поврежденная сохраняется текстом и перечисляется в диагностике, не подменяется нулем.

### Оплаты

Сохранены разделы трех банков, наличных, направлений услуг, частичных оплат, нераспределенных поступлений и оплаченных неотгруженных счетов. Добавлены отдельные связанные возвраты и диагностика.

Реальные суммы поступлений/разнесений считаются через Decimal, не через float/int. Исходящие платежи не являются доходом. Остаток входящего платежа = поступление минус разнесение минус связанные возвраты с датой списания до конца периода. Отсутствие таблицы `payment_refund_links` останавливает построение, а не игнорирует возвраты. Суммы не размножаются соединением каждого движения со всеми тарифами или кассовыми документами.

Дополнение по возвратам: отрицательная сумма KVO учитывается как возврат независимо от старого типа. Возвратный тип с положительной суммой также вычитается; знак нормализуется один раз через абсолютную величину. Для возврата, ссылающегося на входящий платеж, используется дата движения KVO и счет получателя исходного поступления. Возврат от распределенных денег уменьшает распределение и одновременно расходует поступление, не вычитается из остатка второй раз. Если возвраты одного поступления представлены сразу в KVO и `payment_refund_links` без надежного взаимного идентификатора, остаток помечается неопределенным до проверки пересечения — суммы не складываются вслепую.

Наличные учитываются по `kvobop`, включая исторические записи без ключа. Наличие `payment_nal` или `chec`, статус и дата кассового документа не являются условием вывода. Касса определяется по принципалу активного состава счета; если он не определяется однозначно, движение сохраняется в «Другие счета / кассы». Добавлены показатели возвратных движений за период и разнесения за вычетом возвратов.

**Стоимость счета/тарифов — отдельный раздел**, с явной подписью о текущих тарифах. Она не подменяет сумму поступления при частичной оплате. Если в одном счете несколько направлений, фактическая сумма попадает в «Смешанный состав — требуется распределение», а не целиком в каждое направление. «Неотгруженные» использует текущее состояние отгрузки и движения до конца периода; не выдается за историческое состояние.

Поврежденные нечисловые суммы, отсутствующие банковские источники и неоднозначные ключи движения не исправляются и не превращаются в ноль: строки перечисляются в диагностике, остаток затронутого платежа выводится как неопределенный там, где установлен источник. Отрицательная числовая сумма не считается повреждением. Отчет с диагностикой имеет результат `partial`, уведомления содержат указание на замечания.

## Результаты, уведомления, повтор

`<job>-YYYY-MM.json` хранится в постоянном каталоге результатов. Успешный Google-экспорт повторно не выполняется; уведомления можно завершить отдельным повтором команды. Для осознанной перестройки листа — `--execute --rebuild`. Подтвержденные письма при этом повторно не отправляются.

До начала перестройки сохраняется `export_pending=true`. Если построение или публикация завершились ошибкой, обычный повтор (без `--rebuild`) продолжает новую выгрузку. Прежняя ссылка сохраняется для справки, но не считается подтверждением новой публикации. Флаг снимается только после успешного ответа Google и сохранения результата. При неопределенном результате повторная запись тех же диапазонов безопасна относительно дублирования строк.

Письма используют существующий журнал reminders: правило + rand + месяц + получатель. `sent` не повторяется; `unknown` требует проверки доставки. Для VK сохраняется состояние перед вызовом и стабильный random_id; неизвестная доставка не повторяется автоматически. В DEBUG существующий SMTP-механизм отключает реальные письма. Сообщения об успехе не отправляются после неудачной Google-выгрузки.

`partial` само по себе **не вызывает повтор**: диагностические замечания и неизвестная доставка возвращают `retry_required=false`. Для подтвержденной ошибки SMTP или недоступности отправки — `retry_required=true`: задача повторяет тот же месяц. Ошибка построения/Google также передается в очередь. Повторы идут по штатному расписанию очереди: примерно 6, 21, 86, 261 секунд и далее `(attempts ** 4) + 5`, до лимита 25 попыток по умолчанию. Уже подтвержденные Google-экспорты и письма не повторяются. Следующий календарный месяц регистрируется независимо от результата текущего.
