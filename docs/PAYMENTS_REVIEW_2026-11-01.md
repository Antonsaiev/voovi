## 1. Исходящий возврат можно ошибочно разнести как поступление — высокий приоритет

Новая история создаёт ссылку на источник банковского возврата так же, как на
входящую платежку. Страница и ручной обработчик не проверяют направление
`Payment.type_oplat` перед созданием входящей записи оплаты.

Воспроизведение actual `_allocate_payment` под моками: источник с
`payment_type_oplat='2'`, частичная сумма 50 ₽ → создано намерение вставки входящей
`kvobop` типа 14 на 50 ₽. SQL и HTTP в этой проверке запрещены.

Места: `analitic/payments/allocations.py:97`, `payments/views.py:99,166`,
`analitic/utils/func.py:115–163`. Серверный пробел существовал раньше;
новая ссылка делает его доступным обычным переходом из истории.

Исправление: перед входящим разнесением проверять направление исходного платежа
на сервере; исходящий источник показывать без возможности разнести его как приход.

## 2. Гонка с записью серверного файла может потерять полную выписку — высокий приоритет

Между `_preflight` и `_claim` производитель может начать перезапись того же имени.
Проверка пройдена для прежнего содержимого, а в обработку переименовывается уже
новый незавершённый файл. Ошибка незавершённости затем обрабатывается как ошибка
формата: префикс архивируется, claim удаляется. Производитель может дописать
полный файл в уже удалённый inode.

Воспроизведение с настоящим открытым файлом: `files=1`, `payments=0`, `errors=1`,
`pending=0`, `retries=0`; исходника и claim нет, в архиве лишь неполный префикс.

Места: `s.voovi.ru-api/basic/banking/files.py:97,135,159,234`.
В архивных серверных скриптах есть неатомарные `open(...,'wb')` и `shutil.copy`.
Их фактический действующий cron в этом локальном аудите не проверялся.
Новая ручная загрузка `.uploading → .ready.txt` публикуется атомарно и этим
воспроизведением не затронута.

Исправление: повторно проверять захваченный файл; незавершённый claim сохранять
для повторной обработки, не архивировать с удалением. По возможности серверный
производитель тоже должен публиковать файл атомарно.

## 3. Не все финансовые POST проверяют право B — высокий приоритет

Общий middleware проверяет сессию пользователя, но не право раздела.
`oplata_go` и `toggle_invoice_payment_checks` не проверяют B самостоятельно.
Проверка права на открытие расширенной страницы этого не заменяет.

Воспроизведения под моками для пользователя с `access='C'`:
частичный разнос вызывает `InsertKvobop` типа 14 и возвращает 302;
переключение чека вызывает `Chec.update(ogrn='12', isset='0')` и возвращает 200.
Реальные записи не создавались. Пробелы существовали до текущего банковского diff.

Места: `analitic/payments/views.py:166,799`, `analitic/middleware/middleware.py`.
Исправление: проверять право до финансовых чтений/изменений в каждом обработчике;
согласовать правило с существующими правами раздела.

## 4. Возврат может заменить ещё не обработанный приходный чек — высокий приоритет

Доступность переключения определяется по `ogrn`, без проверки, обработан ли чек
кассой. Обработчик меняет существующие строки и ставит `isset='0'`.
Поэтому приход, ещё ожидающий обработки, можно заменить возвратом. Банковский
staging с `payment.status=3` тоже не защищён от этой операции.

Места: `analitic/utils/func.py:714`, `analitic/payments/views.py:817–841`.
Это прежняя операция InvoiceSearch, доступная также через новую ссылку на номер.

Исправление: запретить переключение ожидающего/публикуемого чека; отделить
подтверждённое состояние кассы от подготовки и повторной отправки. Простого
`isset=1` недостаточно: это значение используется и для staging банка.

## 5. Два подтверждения «Возврат» могут превратиться в повторный приход

Клиент показывает подтверждение конкретного действия, но отправляет только
`schet_rand`. Сервер повторно вычисляет переключение из текущего состояния.
Если два менеджера подтвердили возврат, первый запрос ставит возврат, а второй
может переключить его обратно на приход. Блокировка строк не сохраняет намерение.

Места: `analitic/templates/payments/invoice_seach_payment/index.html:100–106`,
`analitic/payments/views.py:824–841`.

Исправление: передавать явно ожидаемое действие и проверять состояние под
блокировкой; повтор одинакового действия не должен выполнять противоположное.

## 6. Повторное изменение скидки приводит к дрейфу копеек

Новая финансовая правка восстанавливает базу из уже округлённой сохранённой суммы
строки. Воспроизведение чистой функцией:

`100,01 ₽ → скидка 50% → 50,01 ₽ → скидка 0% → 100,02 ₽`.

Место: `s.voovi.ru-api/basic/banking/receipts.py:139–167`.
Исправление: хранить точную неизменяемую исходную стоимость для повторных правок;
не восстанавливать её из округлённого результата и не заменять сегодняшним прайсом.

## 7. Изменение количества выездов может заменить сохранённую цену

Для смены количества обычного тарифа используется сохранённая сумма, а для
выезда — поле `goroddd`, даже если фактическая распределённая стоимость была иной.

Чистое воспроизведение: сохранённый счёт 100 ₽ = тариф 80 ₽ + выезд 20 ₽,
`goroddd=25`, один выезд. Смена только количества на два даёт итог 130 ₽;
масштабирование сохранённой цены дало бы 120 ₽.

Место: `s.voovi.ru-api/basic/banking/receipts.py:150–157`.
Исправление: при неизменной цене масштабировать сохранённую стоимость выезда;
явное изменение цены обрабатывать отдельно.

## 8. Чеки, печать и доли ЗП используют разные основы стоимости

Чек новых счетов использует сохранённые суммы строк. PDF и расчёт долей ЗП
продолжают брать текущий `tarif.price` и распределять по нему сохранённый итог.
Общий итог уже не удваивается, но распределение между тарифами меняется.

Проверка общих расчётных функций: сохранённые строки 30/70 ₽ при итоге 100 ₽;
после изменения прайса на 60/70 PDF получает 46,15/53,85 ₽, расчёт долей ЗП —
46,153846…/53,846153… ₽, тогда как чек сохраняет 30/70 ₽. Если ставки тарифов
различаются, меняется и результат начисления ЗП.

Места: `s.voovi.ru-api/utils/SqlQuerySELECTgeneral.py:384–405`,
`s.voovi.ru-api/utils/create_pdf/billing_calc.py:51–56`.
Эти потребители не изменялись текущим банковским diff; разрыв остался в общей логике.

Исправление: для новых счетов использовать единый сохранённый построчный состав
во всех потребителях. Исторические счета без таких данных обрабатывать отдельно,
не изменяя автоматически их суммы или прежние начисления.

## 9. Авария финализации может создать две постоянные цепочки банка

Библиотека сохраняет следующий повтор до удаления прежней задачи.
Прерывание в этом промежутке оставляет обе записи. Восстановление разблокирует
старую, и она создаёт ещё одного преемника.

Воспроизведение на тестовой очереди: после восстановления остаются два
`repeat=300` с одинаковым `run_at`. Собственные тестовые Task/CompletedTask удалены.
Финансовая блокировка защищает от одновременного разнесения, но не устраняет
дубли цепочки расписания.

Места: установленный `background_task/tasks.py:47–51`,
`s.voovi.ru-api/basic/banking/runtime.py:105`.
Исправление: атомарная либо идемпотентная финализация очереди. Не следует
оборачивать всё тело импорта и файловые операции одной длинной SQL-транзакцией.

## 10. Посторонний повреждённый счёт мешает найти подходящий

При поиске без номера до отбора точного совпадения суммы загружаются тарифы всех
положительных счетов клиента. Отсутствующий тариф одного постороннего счёта
останавливает выбор и переводит платёж в ручную обработку.

Воспроизведение: правильный счёт на 1 000 ₽ выбирается; добавление старого счёта
на 200 ₽ с отсутствующим тарифом мешает выбрать тот же правильный счёт.

Места: `s.voovi.ru-api/basic/banking/service.py:304,336`.
Исправление: изолировать повреждение кандидата, сохранив согласованное правило
первого подходящего счёта и проверку ИНН получателя.

## 11. Два экрана могут показывать разную сумму оплат

Новая история учитывает все движения KVO, включая старые записи без ключа или
родительской платежки. Старый InvoiceSearch такие строки отбрасывает.
Например, 400 ₽ с найденной платежкой + 600 ₽ исторической оплаты дают 1 000 ₽
в новой истории, но лишь 400 ₽ в результате поиска. Проверка готовности общего
чека при этом использует все KVO и может признать счёт полностью оплаченным.

Место: `analitic/utils/func.py:641–662`.
Исправление: читать бухгалтерские движения независимо от наличия исходной
платежки и явно отделять приход, возврат и итог за вычетом возвратов.

## 12. Безопасный отказ поиска выглядит как бесконечная загрузка

У AJAX-поиска нет обработчика ошибки. Старый неоднозначный номер вызывает
безопасный HTTP 400, но на странице остаётся «Загрузка, подождите».
То же происходит при сетевом сбое.

Место: `analitic/templates/payments/invoice_seach_payment/index.html:29–45`.
Исправление: показать причину отказа/сбой и оставить возможность повторить поиск.

## 13. Учётная дата чека возврата может отличаться от даты движения

Движение возврата использует дату списания, а подготовщик чека предпочитает
дату поступления. Для списания 31 октября и поступления 1 ноября сохраняются
разные даты. Это учётная дата подготовленной строки, не утверждение о фактической
дате регистрации чека кассой.

Место: `s.voovi.ru-api/basic/banking/receipts.py:211–212`.
Исправление: для возврата сначала выбирать дату списания, для прихода — поступления.

## Не подтверждено для установленной кассовой программы

В соседних исходниках AgentKKT количество преобразуется через `int(kol)`.
Дробные значения вроде `1.5` такой код не обработает. Однако соответствие этих
исходников реально установленному EXE не доказано: бинарник и его рабочий
манифест в локальном проекте отсутствуют. Это отдельная проверка совместимости,
а не подтверждённый отказ установленной кассы. Настоящие чеки не пробивались.

## Согласованные правила сохранены

Не считаются дефектами: выбор первого подходящего счёта; пропуск авторазнесения
при существующей KVO; отсутствие проверки ИНН при явно указанном номере;
определение получателя по ИНН; автоотгрузка по первой позиции; прежние условия
отметки оплаты поставщика; полный итог при ручном разнесении без галочки;
автовозврат только точной суммы неотгруженного счёта; отсутствие зависимости
банковского разнесения от Контура. Выписка без платежей допустима.

Удаление из нового блока распределений убрано, блок служит для просмотра.
Прежняя отдельная операция InvoiceSearch сохранена и проверялась отдельно.
