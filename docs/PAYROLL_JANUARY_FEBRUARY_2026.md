# Повторное начисление января и февраля 2026 года

Проверка 31.10.2026 на действующей локальной базе Docker `voovi`. Production не затрагивался. Перед тестом сохранены полная SQL-копия начислений, исходные строки обоих месяцев, состояние очереди и файлов задач, контрольные суммы всех 234 890 начислений и счетов.

## Условия проверки

По уточнению пользователя из нового расчёта и сохранения ЗП исключено округление к двум знакам. Используется Decimal и существующие поля DECIMAL(30,12). Это относится также к базе тарифной строки, долям расхода, остаткам шагов, окладам и годовым частям. Отображение денежных итогов может по-прежнему использовать два знака.

Для сопоставления с историей временно изменена только локальная ставка правила № 265: с 12% на 6%. Название правила «Налог 6 %» не соответствовало исходной текущей ставке 12%; исторические начисления по нему сделаны по 6%. При 12% получатели получают другое распределение, хотя общий итог счёта может оставаться прежним.

Обычный worker остановлен на время теста. Откат и начисление запущены через настоящий авторизованный API с подтверждающей фразой; задания выполнены штатным обработчиком `background_task`. Внешние HTTP, VK и email при проверке заблокированы. Июльский тест из предыдущего отчёта проверял восстановление только что рассчитанных строк; здесь сравниваются **исторические** строки с новым расчётом.

По получателям при отображении двух знаков: сотрудник № 2 — 155 455,52 → 155 455,50 ₽; сотрудник № 4 — 67 069,50 → 67 069,51 ₽; статья расходов № 7 — 18 720,97 → 18 720,98 ₽. У остальных получателей отображаемые суммы совпали.

Причины подтверждены построчно. Например, `264127A68`, правило 390: прежние 1 390,62 ₽ при базе 2 781,25 ₽ и ставке 50%; точный результат 1 390,625 ₽. У счёта `262A881` прежние сохранённые базы двух строк дают 2 999,995 ₽ вместо сохранённого итога счёта 3 000 ₽; новый расчёт распределяет ровно 3 000 ₽ и сохраняет дробные доли. Подгонка результатов под прежние неточные значения не выполнялась.

Дополнительная независимая проверка воспроизвела прежнее хранение каждой суммы через IEEE754 FLOAT32 и его прежнее читаемое представление с шестью значащими цифрами. **Все 2 123 суммы совпали с историей**, без исключений. То же верно для всех значений `full_summ_schag`, `summ_poln_schet`, `summ_one_schet`: совпали все **8 492 денежные ячейки**. Эта операция выполнена только для сравнения; в новый расчёт или INSERT потеря точности FLOAT не добавлялась. Она подтверждает, что разница связана с прежним хранением, а не с изменением формул.

Единственное текстовое изменение: в месячном правиле 186 название получателя «Неизвестно» заменилось актуальным «Уборка офис», сумма 6 000 ₽ сохранилась. Остальные изменения касаются только точности денежных полей.

Один старый кандидат `2511A1725` оказался неоднозначным: две строки одного `rand` относятся к разным клиентам. Это нулевой счёт февраля 2025 года, попавший в годовое окно поиска. В исходных начислениях января и февраля 2026 года его не было. Он пропущен без остановки последующих счетов; 151 январский счёт восстановлен полностью.

## Общий вывод сравнения

При одинаковой ставке 6% совпали все **4 657 финансовых ключей** и все **18 628 денежных значений** при приведении к прежней точности хранения. При сохранении новых точных дробей общие суммы и отдельные суммы получателей немного отличаются. Поэтому состав и математическая логика воспроизведены, но утверждать абсолютное равенство всех чисел до любого знака нельзя.

## Изменения кода

- `s.voovi.ru-api/utils/funczp.py` — дробные базы, шаги, остатки, месячные правила; годовая разбивка в пределах 12 знаков хранения.
- `utils/SqlQueryINSERTzp.py` — сохранение без округления `sum` до копеек.
- `utils/payroll_amounts.py` — распределение дробных сумм с сохранением общего итога.
- `utils/SqlQuerySELECTgeneral.py`, `utils/func.py` — точный режим чтения баз только для расчёта ЗП; обычные документы и оплаты используют прежний режим.
- `basic/views.py` — числовой JSON для Decimal в расчёте ЗП, совместимый с прежними клиентами.
- Тесты расчёта, дробного количества, хранения, распределения и API обновлены и дополнены. Полный набор API — **719 тестов, все успешны, без пропусков**. Дополнительно прошли 19 серверных тестов аналитики и 22 сценария интерфейса.

Новых таблиц, полей и миграций для сохранения долей копейки не требуется. Схема уже содержит DECIMAL(30,12).

## Возврат исходного состояния

После обоих сравнений исходные начисления возвращены с исходными `id`, всеми полями и счётчиком AUTO_INCREMENT. Контрольные суммы всех 234 890 строк `money_distribution` и всех строк `schet` совпали с началом теста. Другие месяцы при откате не изменялись; тестовые задания и файлы состояния убраны, прежнее состояние задач восстановлено.

Правило № 265 возвращено на исходные **12%**, его полная строка совпала с резервной копией. Обычный worker возобновлён. Тестовые пересчитанные суммы не оставлены в рабочей локальной базе; в коде сохранено новое правило расчёта с долями копейки. Production не изменялся.
