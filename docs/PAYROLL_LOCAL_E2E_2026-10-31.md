# Проверка начисления ЗП на локальных данных — 31.10.2026

Этот этап предшествует последующему решению сохранять доли копейки. Повторная проверка исторических января и февраля и актуальное уточнение точности описаны в [PAYROLL_JANUARY_FEBRUARY_2026.md](PAYROLL_JANUARY_FEBRUARY_2026.md).

Проверка выполнялась на действующей локальной базе `voovi` в Docker, не на production. Сохранены SQL-копия `money_distribution`, контрольные суммы всех исходных начислений и счетов, прежнее состояние задач ЗП. Обычный worker временно остановлен. Тестовые задания ставились в настоящую `background_task` и выполнялись штатным обработчиком очереди в контролируемом процессе; внешние HTTP и отправка VK блокировались.

Для проверки календарного запуска менялась только дата внутри тестового процесса: 10.11.2026 для октября и 10.08.2026 для июля. Системные часы и сохранённое регулярное расписание не изменялись.

## Найденная и исправленная ошибка

В `s.voovi.ru-api/utils/payroll_month_calc.py` проверка сравнивала `Schet.cher` со строкой `'0'`. Реальная модель возвращает число `0` (`IntegerField`). В результате обычный отгруженный счёт ошибочно отклонялся как черновик.

Сравнение исправлено на числовое. В `utils/test_payroll_month_calc.py` фикстуры приведены к реальному типу, добавлена отдельная проверка допуска обычного счёта и запрета черновика. После исправления повторён запуск по реальным данным и весь набор API: **710 тестов без ошибок и пропусков**.

Кандидаты включают предыдущие одиннадцать месяцев для возможной годовой разбивки. Это не число счетов, по которым обязательно должно появиться начисление.

Все 18 отгруженных октябрьских счетов имеют нулевую сумму Савоира, поэтому тарифные начисления по ним отсутствуют. Октябрьский итог состоит из 13 месячных правил: пять окладов суммарно 89 000 ₽ и восемь нулевых удержаний. Результат независимо сопоставлен с действующими правилами.

Июльский итог содержит 994 тарифные записи по 85 счетам и 13 месячных записей. Нулевые строки и счета без начисления по текущим настройкам не записывались.

## Проверки сумм и повторов

- SQL-итоги обоих месяцев совпали с `ViewZp`, суммой колонок способов оплаты и суммой получателей. Проверено и отображение в настоящей странице отчёта.
- В независимом согласованном снимке дополнительно сверены суммы каждого получателя, организации и группы тарифов с SQL `GROUP BY`: расхождений нет.
- 376 реальных строк проверены независимой десятичной формулой процентного начисления и конечного остатка, без вызова общего калькулятора: расхождений нет. Для 23 строк с конечным остатком сумма шагов точно совпала с суммой тарифной строки.
- В многотарифном счёте `264129A21528` отдельно распределены строки на 2 200 и 1 900 ₽; полный итог счёта не применяется целиком к обеим строкам.
- Проверены точность новых сумм до копейки, ровно один получатель, включённые правила и организации, связи `id_schet / ns / rand`, отгрузка исходного счёта.
- Повтор расписания во время обработки вернул ту же задачу без второго задания в очереди. Повтор сохранения уже записанного тарифного расчёта добавил 0 строк.
- Через настоящий API проверены повтор сохранения, удаление и восстановление начислений отдельного счёта. Состав и суммы восстановились. Для окладов проверены повтор без дублей, удаление и повторное добавление: 13 записей на 89 000 ₽.
- Неверная подтверждающая фраза, некорректный месяц, устаревший просмотр и запрос без авторизации отклоняются. Откат во время начисления того же месяца возвращает конфликт. Интерфейс не разрешает отправить неполную подтверждающую фразу.

## Откат и восстановление через интерфейс

Из страницы отчёта отправлен подтверждённый откат июля. Через фоновую очередь удалено ровно 1 007 записей, июльский итог стал нулевым. Контрольная сумма всех остальных месяцев сохранилась.

Ручное восстановление через ту же страницу повторно добавило 1 007 записей на 702 148 ₽, без ошибок. Каноническое сравнение всех полей строк, кроме заново выданных `id`, подтвердило полное совпадение состава с результатом планового начисления. Контрольная сумма остальных месяцев снова совпала. После перезагрузки страницы активная задача и её прогресс восстановились без нового начисления; после завершения итог обновился автоматически.

После проверок удалены все тестовые начисления, восстановлены исходный счётчик `AUTO_INCREMENT` и прежние файлы состояния задач, убраны тестовые задания и записи об их выполнении. Все **234 890 исходных строк** начислений и все строки `schet` побайтово совпали с первоначальными контрольными суммами. Тестовые 89 000 ₽ октября и 702 148 ₽ июля в рабочей локальной базе не оставлены.

Обычный worker возобновлён. Все семь сервисов работают, сохранены 10 регулярных задач, неуспешных задач нет. Расписание трёх новых задач сохранилось: проверка 01.11.2026 02:00, каталог 01.11.2026 05:30, начисление 10.11.2026 20:00 по Москве. Production не изменялся.

## Диагностика и справочник

Проверка счетов запускалась с запретом любых SQL-записей. За октябрь проверены 18 кандидатов, все пропущены по условиям диагностической проверки оплаты. За июль: 449 кандидатов, 122 проверены, 327 пропущены, выявлены три ошибки данных:

- `264130A21632`;
- `264129A21179`;
- `264129A21204`.

У этих счетов не заполнен необходимый для их настройки расход. Значения не подставлялись автоматически. Диагностический отчёт не изменяет счета, отгрузки или начисления; ошибки отдельных счетов не остановили проверку.

Обновление каталога проверено на настоящей локальной таблице внутри откатываемой транзакции и на ранее полученном ответе API: 95 → 185 продуктов, добавлено 90, обновлено 43, 52 без изменений. Второй вызов: 0 добавлений и 0 обновлений. Прежние UUID сохранены. Затем транзакция отменена, справочник вернулся к исходным 95 строкам.

Действующих правил годовой разбивки в этой базе нет. Единственное историческое правило отключено; оно не включалось для теста. Годовые части, сохранение существующих месяцев, конкурирующие записи и откат при сбое проверены интеграционными тестами в отдельной тестовой БД.

Дополнительно прошли **19 серверных тестов аналитики**, **16 сценариев фонового интерфейса** и **6 сценариев отображения отчёта**. Проверка не доказывает корректность всех возможных финансовых настроек; найденные незаполненные расходы требуют решения по исходным данным.
