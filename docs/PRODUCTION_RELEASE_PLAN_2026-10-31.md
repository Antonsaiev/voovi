## 5. Передать общую очередь одному обновлённому worker

Оба проекта используют одну `voovi.background_task`. По решению пользователя старый `apisvoovi_tasks` останавливается. На время замены кода также останавливается прежний экземпляр `voovi_prod_svoovi_api_tasks`; после проверки запускается только его обновлённая версия.

Старый web/API продолжает ставить свои задания в ту же очередь. Их выполняет обновлённый worker актуальным кодом. Существующие имена `basic.tasks.task_update_schets`, `task_update_data_av`, `task_evrika_bills_synchronization`, `report_active_task` и прежние аргументы совместимы. У складской задачи новый `scheduled=False` необязателен, поэтому старые вызовы с одним `id_otdel` поддерживаются.

Не добавлять namespace, отдельную queue, новые сервисы или таблицы. Команда обновлённого worker остаётся `python manage.py process_tasks`, без `--queue`.

Перед остановкой дождаться окончания текущих задач, проверить `locked_at` и выполняющиеся процессы, сохранить снимок очереди. Исключить возврат `apisvoovi_tasks` через restart policy, автозапуск сервера или общий `compose up` старого проекта. Разовая остановка не должна быть отменена последующим запуском старой обвязки. Изменение касается только запуска worker; старые web-сервисы и маршруты сохраняются.

По чтению production-очереди сейчас есть одно суточное `basic.tasks.task_update_data_av` и четыре одноразовых `task_update_schets` с 16–21 попыткой. Проверить аргументы, причины ошибок и ближайшее время повторов; решить по каждой записи, нужен ли повтор или снятие конкретного дубля. Не очищать очередь целиком и не сбрасывать attempts массово. Сохранённое расписание АВ подхватит новый worker; вторую такую запись создавать не нужно. Неизвестные прежние имена библиотека пропустит, но их нужно отдельно учесть, чтобы задания не остались забытыми.

Старый API в этой выкладке не перезапускать: его `AppConfig.ready()` заново регистрирует АВ на 04:25 с `remove_existing_tasks=True`. После будущего перезапуска старого API проверить, что расписание АВ осталось единственным. Исполнять его всё равно будет только обновлённый worker.

Реальную оплату, создание Контура, кассовую команду или начисление ЗП не выполнять автоматически ради проверки инфраструктуры: такие действия проверяются отдельно на согласованных документах.

При откате остановить обновлённый worker, приостановить изменяющие действия Docker-версии и вернуть её согласованный комплект прежних образов/env/mount. Старые сайты не заменять. Сохранить текущую БД, документы, очередь и состояние. Не восстанавливать старый дамп поверх новых пользовательских данных и не возвращать отдельно старый cursor. Старый `apisvoovi_tasks` и замещённые cron автоматически не включать: обратная передача требует сверки последней успешной обработки и выбора одного исполнителя.

## Что необходимо до выполнения

1. Опубликовать полный проверенный релиз.
2. Исправить production-адреса нового env под voovi.voovi.ru/analitic.voovi.ru и сохранить действующие файлы/mount.
3. Проверить совместимость прежней очереди с одним обновлённым worker, остановку `apisvoovi_tasks` и исключение его повторного автозапуска. Переименование задач и разделение очередей не требуются.
4. Передать замещаемые cron новому расписанию, сохранить статистику и инициализировать отсутствующий cursor подтверждённым `639290572440863787`; отдельно определить момент массовой сверки старых связей.
5. Провести репетицию и выбрать короткое окно замены только Docker-проекта.

Production-базу повторно изменять не требуется. Никакой выкладки этим планом не выполнено.
