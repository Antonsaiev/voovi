# Повторные письма о статусах — 03.11.2026

Источник установлен: inctoha.php отправлял письмо при каждом просмотре карточки, если schet.status расходился с последней строкой schet_status. Такое уведомление не имело признака отправки. Старый сайт /var/www/voovi/data/www/voovi.ru содержит тот же механизм.

Исправление PHP 0af5c1a:

- Вызов письма в inctoha.php закомментирован с пояснением. Просмотр карточки больше не отправляет уведомление по историческому расхождению.
- Проверка в getstatusschet.php при реальном изменении оставлена. Почтовому помощнику передаётся rand.
- send_mail.php хранит отметку в log/status-notices: ключ rand + два статуса; при отсутствии rand — сохранённый номер. Файловая блокировка не допускает конкурентной отправки. JSON сохраняется атомарно; sending после неизвестного результата не повторяется автоматически. Известная неудача повторяется не раньше часа. При недоступном журнале письмо не отправляется. Повреждённый журнал требует проверки.
- Русская тема кодируется MIME. Статусы, суммы, оплаты и другие записи БД не изменяются.

Тест tests/status-notice.test.php проверяет повтор, разные rand с одним номером, изменившееся расхождение, равные статусы, отказ отправки и задержку повтора, занятую блокировку и повреждённый журнал. Отправка подменена функцией; реальных писем нет. Тест выполнен локально и на живом production PHP. Проверен PHP-синтаксис.

Исправление применено к новой PHP-версии и узко к трём файлам старой. Сохранены резервные копии /root/voovi-releases/status-mail-20261103/new и legacy, инструкции отката в README.md. Не восстанавливать поверх текущей базы старый дамп. Docker-образ PHP пересобирается из исправленного Git, чтобы исправление сохранялось при пересоздании контейнера.

Это другой механизм, в jobs/schetmain.py. После сохранения новости выполняется follow_up по BillId. Ищет точную связь bills_voovi_links либо для старых записей однозначный номер schet.nomerschetks без новой связи. Исключает del и cher. При отсутствии группы отправляет no_pay_no_voovi / pay_no_voovi / partially_paid, затем ставит соответствующую отметку schet_automation. Дополнение 03.11.2026 по требованию пользователя: любая из прежних отметок no_pay_no_voovi / pay_no_voovi / partially_paid теперь запрещает новое уведомление об отсутствии счёта во всех состояниях оплаты. Переход неоплачен → оплачен или условно оплачен не вызывает повтор. Новых таблиц/полей нет, прежние отметки сохранены. Если отправка известным образом не удалась и отметка не поставлена, следующий запуск может повторить попытку. Изменение не затрагивает финансовую обработку и отдельные сообщения о реально привязанных счетах. Четыре регрессионных теста проверяют все сочетания прежних отметок/новых состояний, последовательные переходы, повтор после неудачи и независимость других маркеров. ## Подтверждённая причина повторной рассылки — дополнение 03.11.2026

Найден второй источник: локальный apisvoovi_tasks был запущен с настоящим SMTP и получателем infosavoir@yandex.ru. Его отдельная локальная БД не содержала production-отметок; поэтому на те же новости отправлялось ещё одно уведомление. Имя хоста обоих worker — apisvoovi_tasks, по одному Message-ID хост не различался.

Сопоставление точное: письмо по 26935376640 имеет Date 03.11.2026 07:30:38 UTC (10:30:38 МСК); локальный API прочитал отметку в 10:30:38.614 и записал её в 10:30:39.065. По 26935256438, 26934793362 и 26935646912 локальный API получил 204 и создал отметки 10:30:19/28/31. Production позже прочитал прежние флаги и не отправлял их повторно. Письма найдены через IMAP в том числе в «Удаленные», без изменения прочитанности и содержания почты.

Локальный worker остановлен для устранения инцидента, затем запущен с KONTUR_AUTOMATION_NOTIFICATIONS_ENABLED=0. Production использует 1. Общая проверка runtime.notifications_enabled блокирует email/VK и постановку новых вторичных уведомлений независимо от --notifications при запрете окружения. Ранее накопленные локальные follow-up также не могут отправлять письма. Отметки не сбрасываются; production-обработка новостей, оплаты, отгрузка и ЗП не отключаются.

Три новых автономных теста проверяют приоритет запрета окружения над разрешением задачи, сохранение production-поведения и совместимость старой конфигурации без нового параметра. Полный набор 1101 тест, 0 ошибок/падений, 72 пропуска. На живом локальном worker дополнительно проверено отсутствие вызовов реальной почты/VK при notifications=True и флаге 0. Все тестовые отправки подменены.
