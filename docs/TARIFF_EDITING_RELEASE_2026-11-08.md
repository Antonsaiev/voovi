# Исправление редактирования тарифов — 8 ноября 2026

Исправлены четыре согласованных пункта текущей реализации. Общие тарифы нескольких
продуктов не разрабатывались.

| Пункт | Результат |
|---|---|
| API менял группу/модель в существующей строке | Изменение создаёт новую версию с прежним sync_id. Историческая строка сохраняет свою группу, модель и цену, получает del=1. Ответ содержит ID новой версии. |
| Родитель и версия расходились | Обновляются одной транзакцией. При чтении/сохранении текущая версия является источником группы, модели и описания. Последующее сохранение исправляет прежнее расхождение родителя; массовая правка старых тарифов не запускалась. |
| Сбой мог оставить тариф без активной версии | tarif переведена с MyISAM на InnoDB, parent уже InnoDB. Запись родителя, новой версии и архивирование прежней откатываются вместе. До обновления схемы код отказывает перед записью. |
| Сохранение прежних значений создавало версии | PHP/API возвращают текущую версию. Повтор неизменённого запроса не добавляет строк; PHP не пишет событие «Тариф изменён» при отсутствии новой версии. |

Интерфейс складских моделей использует новый ID из API-ответа при следующих
изменениях. Видимое значение обновляется после успешного ответа; при ошибке
восстанавливается. Цена и название в API остаются read-only.

## Проверки

- 11 API-интеграционных сценариев и 8 PHP-сценариев прошли на выделенной локальной
  MariaDB 10.2 и в production-образах на отдельной MariaDB **5.5.68**.
- Проверены новая группа/модель, неизменность старой версии, синхронизация родителя,
  явный NULL модели, повтор запроса, отсутствие изменений, отказ на MyISAM,
  откат ошибки INSERT, ошибки архивирования и ошибки обновления родителя.
- В PHP проверены реальные отказы БД: переполнение колонки в строгом режиме
  и тестовый BEFORE UPDATE trigger. В Django ошибки внедрялись на границах SQL
  внутри настоящей InnoDB-транзакции.
- Сквозная проверка API → PHP на отдельной базе: изменение модели через API,
  затем цены через PHP сохранило модель в новой версии и прежние значения
  обеих исторических версий. Повтор сохранения PHP не создал новую строку.
- 69 проверок распределения сумм, расчётов и банковского worker прошли локально.
  Отдельные invoice-flow интеграционные тесты требуют своей базы и не запускались
  как успешная проверка на SQLite; ошибочный запуск с неподходящей базой был
  остановлен их защитой. Синтаксис PHP и JavaScript складского шаблона проверен.

## Применение

Локальная и production-таблица tarif переведены в InnoDB после резервной копии.
В production перед обновлением оба worker завершены плавно с кодом 0;
на время изменения схемы остановлены web/API/аналитика текущего Compose-проекта.
Прежние внешние экземпляры приложений и Apache не обновлялись.

После ALTER все **10069 строк tarif**, **775 родительских карточек** и агрегаты
ссылок счетов на **3483 ID тарифов** совпали с исходными снимками. Новых тарифов
при обновлении схемы не создавалось. Сохранена выполненная ранее архивация:
771 активная версия, ноль групп с несколькими активными версиями.

На production сохранение без изменений проверено через PHP и API на тарифе ОФД
9895: возвращён тот же ID, общее число строк осталось 10069. Цены/группы/модели
рабочих тарифов этим тестом не изменялись. Обновлён только служебный updated_at
родительской карточки при синхронизации метаданных. Ошибки намеренно создавались
только на отдельной тестовой базе.

Сохранены полный SQL-дамп tariff/parent, JSON строк, исходная схема, image ID,
журналы сборки/тестов/выкладки, инструкция отката и acceptance.json:
`/root/voovi-releases/tariff-editing-20261108/`.

Код и схема: [TARIFF_VERSION_WRITES.md](TARIFF_VERSION_WRITES.md),
`database/migrations/2026-11-08_tariff_versions_innodb.sql`.
Откат кода не требует возвращать MyISAM; InnoDB совместим с прежними читателями.
