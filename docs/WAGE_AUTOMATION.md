# Скрипты ЗП в общем Django worker

Перенос архива `wage_sampling.2026-10-31_18_55_38.zip`. Выполнение — в существующем сервисе `svoovi-api-tasks`, через `django-background-tasks`. Нового сервиса, cron, таблиц, полей и отдельной конфигурации не добавлено.

## Расписание

Все даты и время — Москва, `Europe/Moscow`.

| Задача | Когда | Период и действие |
| --- | --- | --- |
| `task_check_payroll_invoices` | 1-го и 15-го числа в 02:00 | 1-го проверяет предыдущий месяц, 15-го — текущий. Проверка заполнения и настроек оплаченных счетов; без записи начислений и изменения отгрузок. |
| `task_accrue_payroll` | 10-го числа в 20:00 | Ставит начисление за предыдущий календарный месяц в общую очередь ЗП. |
| `task_update_kontur_products` | Ежедневно в 05:30 | Обновляет существующий `productskbkontur` через общий клиент API Контура. |

Регистрация находится в `s.voovi.ru-api/basic/tasks.py`, вызывается существующей командой `process_tasks` при старте worker. Уже установленное расписание не переносится и не дублируется. Первый запуск ставится на ближайшую будущую разрешённую дату. Для календарных задач очередь повторяется раз в сутки, а тело выполняется только в разрешённые числа месяца. Если worker был выключен весь разрешённый день, пропущенное начисление автоматически на следующий день не запускается: его можно выполнить кнопкой в отчёте.

После выкладки кода нужно перезапустить `svoovi-api-tasks`. Прежние внешние cron для этих же скриптов необходимо отключить перед включением нового расписания. Производственный сервер этим переносом не изменялся.

## Начисление и ручное восстановление

`save.py` не перенесён вторым независимым расчётом. Расписание вызывает `PayrollMonthJobs.queue_scheduled()`, а ручная кнопка — тот же сервис через авторизованный API с подтверждающей фразой. Автоматическому серверному вызову не назначается случайный менеджер; получатели берутся из правил расчёта.

Кандидаты — отгруженные счета выбранного и предыдущих одиннадцати месяцев, относящиеся к организациям с включённой ЗП. Для каждого тарифа сохраняются отдельные правила расчёта. Повторная проверка баланса оплаты не добавлена: готовность к начислению подтверждает отгрузка. Связь с Контуром не требуется.

Если выбранный месяц по счёту уже содержит начисления, счёт пропускается. Иначе рассчитывается вся разбивка и записываются все отсутствующие месяцы, включая будущие части и другие ранее откатанные месяцы. Каждый существующий месяц сохраняется целиком, даже если исторически заполнен лишь частично. Оклады и удержания добавляются только за выбранный месяц.

Пример: по годовому счёту сохранены январь–март, апрель удалён, май–декабрь ещё не начислены. Восстановление апреля добавит апрель–декабрь, сохранив январь–март. Откат апреля по-прежнему удаляет только апрель.

Проверка наличия месяцев и все новые вставки одного счёта выполняются в одной транзакции под общей блокировкой ЗП, совместимой с MariaDB 5.5. Повторный или параллельный запуск не добавляет их ещё раз. Ошибка вставки откатывает все новые части этого счёта; ошибка расчёта одного счёта не прерывает остальные. Успешные счета не откатываются из-за ошибки другого счёта.

Расчёт использует действующие настройки и цены. Это не точное воспроизведение прежних удалённых проводок: если правила или получатели менялись, новые части могут отличаться. Сохранённые месяцы не пересчитываются.

По последующему уточнению пользователя расчёт ЗП сохраняет доли копейки: промежуточного округления к двум знакам нет. Локальная база использует DECIMAL(30,12); production сохраняет прежние четыре FLOAT. Код поддерживает оба варианта, включая оклады и годовую разбивку. При FLOAT точность сохранённого значения ограничивает сама БД. Предпросмотр и обычное отображение денежных итогов сохраняют прежний формат.

Состояние автоматической задачи и результат доступны в обычном отчёте ЗП; завершение также отправляется через общий безопасный отправитель VK. Недоступность VK не отменяет начисления и не вызывает повтор финансовой операции.

## Диагностика счетов

Вместо `test_schet.py` используется `utils/payroll_checks.py`. Отбираются активные счета за месяц выдачи или отгрузки в организациях с включённой ЗП. Нет номера — показывается проблема, но номер не присваивается. Для полностью оплаченных счетов проверяется общий расчёт и его настройки. Остальные счета пропускаются только в диагностике; это не дополнительное ограничение начисления.

Ошибки и предупреждения о минусовых начислениях собираются в результат; в VK отправляется сводка со ссылками на клиентов. При отсутствии проблем пустое уведомление не отправляется. Подробности остаются в общем журнале. Ошибка одного счёта не останавливает проверку остальных; общий сбой БД передаётся очереди для повтора.

## Справочник Контура

`utils/kontur_products.py` использует `KonturClient.products()`, без обращения к прежнему внутреннему HTTP-сервису. Новый API возвращает `id`, соответствующий старому `CsProductId`; это не прежний ключ `uuid`. Сопоставление учитывает существующие GUID и код биллинга, сохраняет прежние `uuid` и обновляет изменившиеся поля. Новые продукты добавляются. Отсутствующие и архивные продукты не удаляются; доступность продажи этим справочником не определяется.

Весь ответ и все соответствия проверяются до первой записи. Неоднозначное сопоставление не заменяет чужой продукт. Обновление выполняется в транзакции InnoDB и допускает повтор без дублей.
